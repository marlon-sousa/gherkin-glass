# Architecture

How gherkin-glass's code is organised. [BEHAVIOUR.md](BEHAVIOUR.md) says what the tool does; the [design notes](design/) say why the larger choices were made; this document says how the code is laid out and written. Every contributor follows it. The layout below is the shape of the pipeline redesign agreed in [#45](https://github.com/marlon-sousa/gherkin-glass/issues/45), to which the code was moved layer by layer, each layer keeping every page byte for byte ([design note 0045](design/0045-the-pipeline.md)). Two parts still differ from it. The versions page is built from the versions the output folder holds, which only the site writer knows, so it is rendered from the site writer's list of them rather than as a node of the converter's tree. And the needs of the site stage are built in steps that the site tree's policy calls in turn, such as the tags found, then named, then given their pages, and they share building blocks with one another, such as a feature's anchors, which the tag pages use too, so their faces hold those steps and blocks rather than one entry point each; the stage itself re-exports only the site tree.

It was agreed in [#23](https://github.com/marlon-sousa/gherkin-glass/issues/23), modelled on the architecture of [acter](https://github.com/marlon-sousa/acter/blob/main/docs/ARCHITECTURE.md) and adapted to a program that runs once and turns files into files. Changing a rule here starts as an issue, like any other change.

Besides any difference named above, the build this document describes, one `build` that starts from nothing or from the last build and the paths that changed, with the input tree and the site tree as "The two trees" describes them, was agreed in [#73](https://github.com/marlon-sousa/gherkin-glass/issues/73) and [#74](https://github.com/marlon-sousa/gherkin-glass/issues/74) ([design note 0073](design/0073-a-build-starts-from-its-trees.md)), and the code is moved to it layer by layer. Until the layer the note names for each, the code still differs from it in these ways:

- the site tree holds only the version the build makes, not the versions the output folder already holds, until layer 3, and each page holds what it shows in its own value rather than in page and content nodes below it, until layer 4;
- the input is walked by the gherkin parser, with no input tree, until layer 5;
- `ghg serve --watch` starts watching before the first build and walks the whole input again for each burst, and the `serving` stage, not `collecting`, decides which paths of a burst call for a rebuild, until layer 7;
- every build reads, parses and converts every file, until layer 8, and renders every file, until layer 9.

Two places still describe the code as it is today. In this document, "Folders and files", rule 4, still says the `serving` stage decides which changes call for a rebuild, and does not yet say that an entity holding the parts of several stages, `BuildSnapshot` and `BuildStart`, sits at the top of `entities/`. In BEHAVIOUR.md, rule 65 still says the folders watched are those `ghg serve` started with, and rule 68 that a watch that cannot start ends `ghg serve`, until layer 6 gives them their new text.

## The guiding principle

Ports and adapters. The pure part of gherkin-glass, which decides what the site contains, knows nothing of the disk. It defines the seams it needs from the world as traits, the ports, and the code that touches the world implements them, the adapters. The composition root is the one place that chooses the concrete adapters and hands them in, and the one door into the library. Dependencies point inward only.

## The repository

- **One crate**, `gherkin-glass`: a library, `src/lib.rs`, and the binaries built on it: `ghg`, from `src/main.rs`, and the cargo plugin `cargo-ghg`, from `src/cargo_ghg.rs`, which runs the same code as `cargo ghg` ([#18](https://github.com/marlon-sousa/gherkin-glass/issues/18)). The library's composition root, `src/composition_root.rs`, wires the real adapters in, and each binary only hands its entry point the process's arguments. Nothing in the crate is heavy enough to earn a crate of its own.
- **`clippy.toml`** and **`deny.toml`**: what clippy allows in tests, and what `cargo deny` allows of the dependencies.
- **`xtask/`**, the crate behind `cargo xtask build`, `cargo xtask check` and `cargo xtask comment-ratio` ([#4](https://github.com/marlon-sousa/gherkin-glass/issues/4)). It orchestrates the build and is never shipped.
- **`askama.toml`**, at the crate's root, which names the folders askama reads the templates from: the templates live beside the nodes that render them, in `src/policies/rendering/`, as "The pipeline" describes, replacing the `templates/` folder at the crate's root, where askama looks by default. They are the views: everything a page says is placed in them, except the folder tree, which the script builds from shared data ([#7](https://github.com/marlon-sousa/gherkin-glass/issues/7)).
- **`script/`**, the TypeScript of the pages' behaviour, an npm package with its own `package.json` and lockfile. Its compiled output is committed, so building the crate needs no Node ([#4](https://github.com/marlon-sousa/gherkin-glass/issues/4)).
- **`assets/`**, the files the binary embeds and writes into every site: the stylesheet, and the script compiled from `script/`.
- **`messages/`**, the Fluent catalogue of gherkin-glass's own interface text, one folder per language, embedded in the binary, and **`i18n.toml`** at the crate's root, which tells the `fl!` macro where the catalogue is and which language it checks against (see "Interface text").
- **`action.yml`** and **`action/`**, the GitHub Action that installs `ghg` and builds a site with it ([#17](https://github.com/marlon-sousa/gherkin-glass/issues/17)): a composite action whose steps run the bash scripts in `action/`, each saying its role in a comment on its first lines, as a module does.
- **`project-site/`**, the project's own site ([#19](https://github.com/marlon-sousa/gherkin-glass/issues/19)): the example suite it shows, with its site as ghg builds it, the list of fixtures it leaves out, and the scripts that gather its input and publish each release to the `gh-pages` branch, which `.github/workflows/site.yml` runs.
- **`.claude/skills/`**, the procedures an agent follows to review a change, write a commit, follow a stack and keep this document true. They add no rule of their own: each points at the rules it follows.
- **`tests/`**, the crate's integration tests, and `tests/fixtures/`, the feature files every rule of BEHAVIOUR.md is checked against.

## Module roles

Every module plays exactly one of eight roles, and says which on the first line of its `//!` doc comment, such as `//! Policy: the anchor rule.` The other files play none and say so instead: `lib.rs`, the facade; `composition_root.rs`, the composition root, a module of the library; the two binaries, `main.rs` and `cargo_ghg.rs`, which only call it; and the test-only module of shared test helpers, `test_support/mod.rs`, which says `Test support:`.

1. **Entity or value**: data and the invariants it keeps, such as a parsed feature, a node of the site tree, or the settings of a build.
2. **Policy**: a pure computation, the same output for the same input every time. Correcting doc strings, making anchors, building the site tree, the page addresses and the accents' contrast check are policies, and so is rendering a node into a string. A policy is a part of a service: each area of `policies/` answers one need of the domain and serves one service, as a rule, and seldom more than one.
3. **Port**: a trait the domain needs the world to implement, such as listing a folder of the input or writing a file of the site.
4. **Adapter**: an implementation of a port that touches the world. Listing a folder, reading a file, parsing it with the `gherkin` crate and writing a page are adapters.
5. **Service**: a named stage of the pipeline in the domain's own words, such as parsing the feature files or writing the site. It coordinates policies, entities and ports, and touches the world only through the ports it was given, so a test can run it entirely in memory with fake ports.
6. **Controller**: the orchestrator. It runs the services of a use case in order, such as building a site, and returns the result, or the error of the stage that stopped. It prints nothing.
7. **Handler**: the delivery layer, a way in. It turns what came in, such as the command line, into a call to the controller, and the controller's result, and what it tells the handler's listener, into what the person at the terminal reads, including the exit status. Deleting a handler loses no behaviour, only the way in.
8. **Error**: what stops a run, such as a feature file that cannot be read, a key of the configuration that is wrong or a port that is taken, in `errors/`, whichever role raises it. An error is data, like an entity, and it also says itself: its `Display` is the sentence a person reads, from the interface text catalogue, as "How the code runs" describes.

The question that classifies a module: **does it do anything nondeterministic, such as reading or writing files, reading the environment or the clock?** If yes, it is an adapter, behind a port. If no, it is one of the other seven, or pure code of one adapter, as the next paragraph says. If it still fits none, it does two things and is split until each part fits one. A pure function never gets a trait around it only to be faked: it is already testable.

Policies hold the domain's pure decisions. Pure code that only one adapter uses to speak its protocol or its library, such as the content type of an HTTP answer or the answer to a request's path, is part of that adapter: a private submodule in the adapter's folder, with the adapter's role line, tested there. It is pure, so it needs no port to be tested. An adapter splits into as many private submodules as it needs.

Layering goes one way. Handlers call the controller, and use policies and entities for what is theirs alone, such as reading the arguments, and the `Terminal` port for what they say while a command still runs; the controller calls services, and may call an entity's own methods to carry one service's output to the next, such as handing the gherkin parser the files the input tree has with nothing parsed; services use entities, policies and ports; adapters implement ports, and use only ports, entities and errors, never a policy, a service, the controller or a handler. Errors are used by every role, and use only entities and the interface text catalogue; entities may hold errors in turn, such as the errors met while collecting the input, so these two depend on each other, and errors on the catalogue too. Nothing reaches around a service into another module's internals.

## The pipeline

gherkin-glass is shaped as a compiler is: it collects its sources already parsed, converts them into one tree, and writes its output by walking the tree ([#45](https://github.com/marlon-sousa/gherkin-glass/issues/45)).

### How a run flows

1. **The binaries** each call an entry point of the library with the process's arguments. `cargo-ghg` drops the word cargo adds first, so that both hand over the same arguments.
2. **The command line handler** reads the arguments, with the policies of `configuration`, and calls the controller.
3. **`SiteController`**, the one controller, has two methods, `build` and `serve`, and one way to build a site, which both use:
   1. **A build** is given where it starts, `BuildStart`, a closed set of two: from nothing, with the settings, or from the last build and the paths that changed since. What a build made is a `BuildSnapshot`: the settings it was built with, its input tree, its site tree and the site rendered from them, whose files are shared with what the server serves, not copied; it holds no site tree and no site while no build from nothing has got that far. Both are entities at the top of `entities/`, since they hold the parts of several stages, which "Folders and files", rule 4, is still to say. From the last build, the input collector first makes the new input tree from the last one and the paths, and says whether they concern what a build reads (rule 65); when they do not, the build goes no further: the settings are not read again, and nothing is built or said. When they do, the controller gets the settings again, with the last build's destination, and when they differ from the last build's, the build hands that case back to its caller, which builds from nothing with them, as for everything changed, so that a kept page never sees settings other than those it was rendered with. That case only guards a change of the configuration file reported as paths, since the server service reports one as everything changed. From nothing, the build first has the site writer check the output folder when the destination is a folder, then has the input collector make the input tree. Either way, the controller then takes from the input tree the files with nothing parsed, hands them to the gherkin parser, and gives the results back to the input tree. When the tree then holds no error, it calls the converter and the site writer, in that order, each given its tree from the last build, or none from nothing.
   2. **What a build leaves for the next one.** Built, it leaves the new `BuildSnapshot`, with what the build has to say. Stopped by the input, it leaves the new input tree, which holds every error found, beside the site tree and the site it started from, none when it started from nothing, so that the next build parses again only what changed and still reports every problem. It also leaves the settings it was given, so that the input folder a later burst is judged against is the one watched. Given paths that concern nothing a build reads, or stopped by the settings read again, it leaves the last build with the new input tree, so that the tree still holds every entry of the input. Stopped by the settings from nothing, it leaves the last build as it was, and the watch stays as it was, so that a fix to the configuration file is still seen.
   3. **`ghg build`** gets the settings from the settings service and builds once, from nothing.
   4. **`serve`** gets the settings once, with the destination its mode gives, and builds with them from nothing, unless `--no-build` says not to. Once that first build is done, it asks the server service to serve the site the site writer says it wrote, or the output folder as it is, and tells the listener the server listens. Without `--watch`, it waits until it is stopped. What stops the first build is said before a watch that could not start.
   5. **With `--watch`**, `serve` only then asks the server service to start watching, so a change saved during the first build is not seen, which no rule of BEHAVIOUR.md promises. It reads the changes the server service hands back one at a time, as from a channel, every burst waiting merged into one. For everything changed, which a change to the configuration file always is, it gets the settings again, stops the watch, dropping the bursts it still held, since a build from nothing reads everything, and starts it again, on the input folder they name and the configuration file, then builds from nothing with them, so that a change saved during that build starts another; every build from nothing under `--watch` but the first, the one a build from paths hands back when the settings differ included, restarts the watch the same way. The configuration file is watched apart from the input folder, so that its watch can start again when the input's cannot; how is left to layer 7 of the note. When the watch cannot start again, `serve` does not stop: the build from nothing does not run, and the last build is kept as it was. It tells the listener, which prints the sentence of BEHAVIOUR.md rule 68, and it keeps serving the last site that built and keeps watching the configuration file, so that a change to it tries again; a watch that cannot start when `serve` starts still stops it, as rule 68 says. For paths, it builds from the last build and those paths. It tells the listener of each rebuild served or stopped, and of nothing when the paths concern nothing a build reads.
4. **The command line handler words the result**: it prints the report and decides the exit status, from the error the controller returns, with a closed set of statuses that is its own, private to it. Since `serve` runs until it is stopped, the handler gives it a listener, a trait the controller defines and the handler implements, which the controller tells when the server listens, when each rebuild is served or fails, and when the watch cannot start again, and the handler words each.

The **destination** is part of the settings, a closed set of two, a folder or memory, and the server serves from the same place, so nothing is copied:

| Command | Builds into | Serves from |
|---|---|---|
| `ghg build` | the output folder | nothing |
| `ghg serve` | the output folder | the output folder |
| `ghg serve --no-build` | nothing | the output folder, as it is |
| `ghg serve --watch` | memory, again on each change | memory |

With memory, the output folder is neither checked nor written, and a version name changes nothing, as BEHAVIOUR.md rule 66 says.

### The services

1. **The settings service** reads the configuration file through the `ConfigReader` port and, with the policies of `configuration`, checks it key by key and resolves it against the command line into the settings, the destination among them.
2. **The input collector** makes the new input tree, `input_collector.collect(…)`, from nothing or from the last tree and the paths that changed; it, not the gherkin parser, chooses what to parse. From nothing, it walks the whole input: for each folder it lists the entries through the `InputFolders` port, reads the folder's `.ghg-ignore` through the same port when there is one, and has the policies of `collecting` parse its rules and say which entries are allowed; it lists the allowed folders, and every allowed file's node starts with nothing parsed. From the last tree and the paths, it makes a new tree, copying over each node of the last one that the paths do not concern and making again those they do, each path relative to the last build's input folder, and those outside it left aside:
   - A `.ghg-ignore` made, changed or removed comes first: its folder's rules are parsed again, and only that folder and everything below it is judged against them again, since its rules apply there and nowhere else (BEHAVIOUR.md rule 3); one in a folder not allowed changes nothing in the tree. A file they no longer allow is marked not allowed, with nothing parsed, and a folder they no longer allow is marked not allowed, with no children. A file they now allow is allowed, with nothing parsed, and a folder they now allow is walked as from nothing.
   - Every other path is looked up by listing again, through the same port, the nearest folder above it that has a node and is allowed, so that folders made since get their nodes, and a path that names a folder with a node that is allowed lists that folder again, so that one that could not be listed before can be; a path under a folder not allowed changes nothing. A file gone loses its node, and a folder gone loses its node and everything below it. A file made or changed that the rules allow has nothing parsed, and a file made that they leave out gets a node marked not allowed. A folder made or moved in is walked as from nothing, its `.ghg-ignore` included.
   - From the last tree and the new one, the policies of `collecting` then say whether the paths concern what a build reads, as rule 65 says: one of them names a `.ghg-ignore`, a file allowed before the change or after it, or a folder whose allowed files, at any depth below it, differ before and after.

   A folder that cannot be listed keeps the error in its node, and so does a `.ghg-ignore` that cannot be read or holds a rule that is not valid, until a later change lets them be read (rule 14). Over every allowed file and folder of the new tree, changed or not, the policies of `collecting` then find from their paths alone the files whose pages clash with each other, with a folder's page or with a page of the site's own, and the folders whose paths differ only in the case of their letters (rules 37, 78, 101 and 142), and the tree keeps each such error with its file or folder, in place of any the last tree's node held, since they are found again on every build.
3. **The gherkin parser** only parses: it is given a list of files, and whether the settings refuse blocks with no name, and returns one result for each file, knowing nothing of the input tree. It parses each through the `FeatureParser` port, whose adapter, `GherkinCrate`, wraps the `gherkin` crate, in parallel with `rayon`, collecting into a `Vec` so that file order is kept whatever order the threads finish in. The policies of `collecting` find each file's language, correct what was parsed, such as the doc strings and the step keywords, and find the blocks that need a name. Each result is the file's feature or its errors.
4. **The converter** has no port. From the new input tree, the last site tree, the settings and what the output check found, the versions already built when the destination is a folder, it makes the new site tree anew with the entry point of the `site` stage, which alone names the kinds of page, in this order: first the inputs every page may use, computed from every feature, such as the tag pages' names, which are kept unique across the whole site, and which the version's node keeps, so that the next build can compare them; then the feature pages, where a page is converted again when its input node's revision differs from the one it was converted from, or when an input every page may use and it uses changed, a page whose input node is gone or no longer allowed is left out, a new node gets a page, and every other page is copied from the last site tree; then the views, computed again from the new tree's feature pages and folders, which parse nothing. Only allowed, parsed file nodes give pages, so the new site keeps nothing of an entry the rules no longer allow, and the site served, swapped in whole, keeps nothing of it either. The settings are not among the inputs it compares, since a change to them starts from nothing. It cannot fail: every clash is found while collecting.
5. **The site writer** has two methods. `check`, which the controller calls before the input collector makes the input tree, so before the input is read (rules 38 and 124), has the `output_safety` policy judge what the `OutputFolders` port finds in the output folder. `write` walks the new site tree and renders each file node with the policies of `rendering`, except a file node equal to the file node with the same path in the last site tree, whose rendered file it keeps from the last site, so that the marker can list every file before one is written; it then checks again, clears and marks the folder, and writes each file through the `FileWriter` port. It returns what the build has to say of the site, such as the size of its search documents, with the site written. That port has two adapters, chosen by the destination: `FolderFiles` writes into the output folder, and `MemoryFiles` keeps the site in memory for the server, swapping the whole site in at once, so that no half-built page is ever served. The port's `site` method gives the site written, as the server serves it: the output folder for `FolderFiles`, and the files taken whole for `MemoryFiles`, which `write` returns. With memory as the destination, `check` and the clearing and marking do nothing, since there is no folder.
6. **The server** serves a folder or a site in memory through the `PreviewServer` port and, when asked to watch, watches the input and the configuration file through the `ChangeWatcher` port, until it is asked to stop, as a build from nothing does before it starts the watch again, and hands back the changes, as from a channel. With the policies of `serving`, it merges every burst waiting into one `InputChanges`, an entity of `serving` and a closed set of two: everything, when the watcher says it may have missed some or a burst names the configuration file, and otherwise the paths they named, joined. Which of those paths call for a rebuild is the input collector's to say, from the input tree, so the server needs neither the walk nor the files a build read.

Each stage returns its own error, from `errors/`, and the handler turns it into its sentence and its exit status. A file that cannot be written is the site writer's own error, not an input error.

### The two trees

A build keeps two trees, which the next build starts from. Each is an `ego_tree::Tree` whose nodes are one enum of typed kinds, stored by value, such as `SiteNode::Folder(Folder)`, `SiteNode::Rule(RuleBlock)` or `SiteNode::Scenario(ScenarioBlock)`, so that each kind's data stays typed and keeps its derives. A node finds what it inherits through its ancestors, such as a scenario's tags and backgrounds from its rule and its feature, or a page's breadcrumb and depth from its folders, so that nothing is copied into a node or passed down as a flag. Which kind may sit under which is kept by one builder module per tree, an entity's private module, whose typed adds are the only way to put a node in the tree, with a test. Each build makes its trees anew, copying over the nodes it keeps from the last ones, and never removes a node from a tree, which with ego-tree would leave it in the tree's `Vec`; it only fills in the values of the trees it made ([design note 0073](design/0073-a-build-starts-from-its-trees.md)).

#### The input tree

The input collector's tree, in `entities/collecting/`, an `ego_tree::Tree` of `InputNode`, holds the input as the walk found it. A folder node holds its name, whether it is allowed, the error met listing it if it could not be listed, the parsed rules of its `.ghg-ignore` if it has one, with the error met reading it or the errors of the rules that are not valid, and the error of a folder whose path differs from another folder's only in the case of its letters. A folder the rules leave out stays a node marked not allowed, with no children, since it is never listed, so that BEHAVIOUR.md rule 2 leaves it out with everything in it and rule 14 never fails a build on it. A file node holds its name, whether it is allowed, and the errors of its page, if it clashes; an allowed one has nothing parsed until its result comes back from the gherkin parser, then holds its revision and what parsing gave, its feature or its errors, behind an `Arc`, so that copying the node into the next tree copies no feature. A revision comes from a counter the tree keeps and never reuses, so that a file removed and made again is never taken for the one before it. A file's modification time is not used, since it cannot be trusted to say a file changed.

The tree is an entity, data and the invariants it keeps, and touches no port. Its own methods hand out the files with nothing parsed, and take their results back: each result goes into its file's node, through ego-tree's `NodeMut::value` on the tree this build made, so nothing is detached and the last build's tree stays as it was, and the node is marked parsed with a new revision. A result is made only from a file the tree handed out, which carries its node, so a result for a path the tree did not hand out cannot be given back, and the type holds that refusal. The tree also hands out every input error its nodes hold, the folders' and the files', sorted as rule 15 says, so that a rebuild reports every problem, not only the changed file's.

#### The site tree

The converter's tree, in `entities/site/`, an `ego_tree::Tree` of `SiteNode`: the site, then its versions, then each version's folders, the input folder and every folder of the input with an allowed file in it or at any depth below it (rule 77), then each folder's files, then each file's nodes. The site holds the parts of the frame every page shares; each version holds the files in no folder of the input, its assets, its folder tree's data, its search documents and its views. The versions not being built hold only their names, from what the output check found, so that the versions page is a node like any other page. A folder node makes a folder, and the converter makes its folder page and its part of the folder tree's data from its children, so the hierarchy is built once. Its nodes are of three sorts.

1. **Shared nodes** are rendered once for each build: the parts of the frame that are the same on every page, the skip link, the options with the folder tree's checkbox and the Theme control, the folder tree's empty landmark and the themes' stylesheet; the folder tree's data; the search documents; and the assets.
2. **Page nodes** are rendered for each page, since they depend on it: its head, with its language, its title and the path back to the root in the links to the stylesheet and the script; its breadcrumb; and its search box, whose root path also depends on the page's depth. A feature page's node also keeps its source path and the revision of the input node it was converted from.
3. **Content nodes** make up each kind of page, one kind of node for each kind of thing, so that each holds only what its kind can have. A feature page is made of the feature, its rules, backgrounds, scenarios, outlines and examples, their steps, and the steps' tables and doc strings. The folder pages, the step sentences page, the tag index, the tag pages and the versions page are made of their own content nodes the same way.

The step sentences page, the tag index and the tag pages, the search documents, the folder pages and the folder tree's data are views the converter computes from the tree once its feature pages are made, and adds to it.

**No type of the `gherkin` crate is in the site tree.** The input tree keeps them in its file nodes, as the gherkin parser's results gave them, `ParsedFeature` holds a `gherkin::Feature`, and the policies of `collecting` work on them. The converter's first pass is the one place that reads them: it turns each feature into content nodes, making the anchors and the step highlighting as it goes, since both need the blocks in file order. Every later pass reads only the site tree's own nodes, and rendering never sees a type of the `gherkin` crate.

### Rendering

Every node renders its own piece of a page through one trait, the rendering trait of `policies/rendering/`, and a page is the pieces of the nodes it is made of; a file node also says where its file goes. Each implementation sits beside its template, and one match on the node's kind hands each node to its own. A file node is equal to the last site tree's when the two have the same kinds, the same values and the same shape below them, found by a method of the site tree entity that walks both together with ego-tree's `traverse`, since its node references compare by identity, not by value ([design note 0073](design/0073-a-build-starts-from-its-trees.md)). The converter puts into a file node's own nodes everything its file shows, beyond what its path and the settings decide, such as the titles a folder page lists or the tag pages a feature page links to, so two equal file nodes with the same path render the same file. The site writer walks the tree and writes each file without knowing its kind, so a new kind of page adds one implementation and its template, and changes no service. Askama, serde for the pages' data, the folder tree's data and the search documents, and the theme's stylesheet are used only in `rendering`; the tree's nodes are plain data.

## Folders and files

1. **`lib.rs` is a facade with one door**: only `mod` declarations and a `pub use` of the two entry points, one for `ghg` and one for `cargo-ghg`, both in `composition_root.rs`, and no logic. gherkin-glass is a command, not a library: the library exists only so that both binaries share the code and the tests can reach it, so its crate documentation says it is not a stable API and that the way to use gherkin-glass is the `ghg` command. Handlers, the controller, services, ports, adapters, entities and policies are details, and none of them is exported. A real API, if one is ever wanted, starts as an issue that designs it.
2. **The visibility ladder**: private by default, `pub(crate)` when another module of the crate needs it, and bare `pub` only for the two entry points. The `unreachable_pub` lint, set in `Cargo.toml`'s `[workspace.lints]`, catches a `pub` that is not re-exported, and CI makes the warning an error; a `pub use` in `lib.rs` of anything but the entry points is a review finding.
3. **`module.rs` with a `module/` folder, never `mod.rs`**, so that every file's name says what it holds, which also reads better in a screen reader's list of editor tabs. One concept per file, named after it. A module earns a folder when it has private internals of its own, or when rule 7 splits it. The one exception is the test-only module of shared test helpers, `src/test_support/mod.rs`, so that everything that supports the tests sits in one folder of its own, apart from the fixtures under `tests/fixtures/`.
4. **Folders are named by role, then by area**: `handlers/`, `controllers/`, `services/`, `ports/`, `adapters/`, `entities/`, `policies/` and `errors/` at the top. Inside `entities/` and `policies/`, the areas are the pipeline's stages, one folder each, so that where a module is says which stage it serves: `configuration`, the settings of a build; `collecting`, the feature files read and parsed; `site`, the site tree and how it is built; `rendering`, in `policies/` only, the site writer's policies: the nodes rendered beside their templates, and whether the output folder is safe to write; and `serving`, the server's: what it serves, the watch, and which changes call for a rebuild. A stage's needs are areas of their own inside it, such as `policies/site/tags/` or `policies/site/feature_pages/`. An area's module, such as `policies/site.rs` or `policies/site/tags.rs`, has its role's role line, saying what the area covers, and holds only its `mod` declarations and re-exports. A module that every area uses, or a policy that serves more than one service, such as `policies/interface_text.rs`, stays at the top of its role's folder. `handlers/`, `controllers/`, `services/`, `ports/`, `adapters/` and `errors/` hold few enough modules to read at a glance, and have no areas. The path says the role, then the area, before the file is opened, and the file's name says the concept. An area's folder belongs to one role: a concept that spans roles is several files, one in each role's folder, under the same area's name in each role that has areas. There is no `utils.rs` or `helpers.rs`.
5. **Unit tests live with the code**, in a `#[cfg(test)] mod tests` at the bottom of the file whose code decides what they check, where they can see private items without exporting them. A test module that grows long, past about 150 lines as a guide, is a file of its own: `#[cfg(test)] mod tests;` at the bottom of `module.rs`, with the tests in `module/tests.rs`. The tests in `tests/` reach the code only through the two entry points or by running a binary, as `tests/command_line.rs` does; a test that needs an internal type is a unit test.
6. **Import a symbol, then use it by its bare name**: `use askama::Template;` then `#[derive(Template)]`, never `askama::Template` written inline. A type's own associated items, such as `Feature::parse_path`, and `crate::` or `super::` paths a macro needs, are the import-then-use pattern already and stay as they are.
7. **A file holds one thing, and its length is a signal.** A file holding two things or more, at any length, keeps one and moves each other to a private submodule of its own, in the file's `module/` folder. A file past about 200 lines, counting its code and its documentation but not its test module, is the signal to look for the seams it splits along. The limit is a guide for the reviewer's judgement, not a gate, and no check counts lines: a file past it may stay when it holds one thing well, such as one whose lines all belong to one type, with its own `impl` blocks and the private helpers only it uses, or one a little past the limit that otherwise fits well, while a short file with several responsibilities splits.
8. **Every module is a file of its own.** Inline `mod` blocks are only for tests.
9. **A module with submodules decides its public face**: its submodules are private, and it re-exports what the rest of the crate uses, so that a path names one module level, such as `crate::policies::site_tree`. A role's module re-exports the face of each of its areas, so that moving a module from one area to another changes none of its callers. Each need of the domain is one policy, an area of `policies/` or of a stage in it, and its face is its entry point and nothing else, as `lib.rs` exports only its two: the function or type its caller uses, such as the converter's `site_tree`. A stage's module re-exports the entry points of its needs, such as `configuration`'s reading of the arguments, which the command line handler uses, and its resolving of the settings, which the settings service uses.
10. **Helpers that the tests of several modules share** live in a test-only module of their own, `#[cfg(test)] mod test_support;`, never copied from one test module to another.

## Writing the code

- **Formatting is plain `rustfmt`**, with no configuration file.
- **Nothing panics while a build or a server runs.** Every failure is a value, a `Result` or an error reported. Clippy denies `unwrap_used`, `expect_used`, `panic`, `indexing_slicing`, `todo` and `unimplemented`, as `Cargo.toml`'s `[workspace.lints]` sets, and `clippy.toml` allows them in tests. A file in `tests/` whose helpers use them expects those it uses at its top, with `#![expect(..., reason = "…")]`, since clippy counts its helpers as code outside tests. An exception that cannot fail, such as a regular expression written in the code, says so with `#[expect(clippy::expect_used, reason = "…")]`.
- **No `unsafe` code**: `Cargo.toml`'s `[workspace.lints]` forbids it, for the crate and `xtask`.
- **Reuse before writing.** Look first at the standard library and the APIs already at hand, then at the crates already depended on, then at well-known crates. Write it ourselves only when none fits, or when a crate would replace only a couple of lines. A crate is judged by what it replaces across the code, not only by its first use.
- **Derive what a derive produces.** Error types derive with `thiserror`, with `#[from]` instead of a hand-written `From`. `Debug`, `Clone`, `Copy`, `Default`, `PartialEq`, `Eq`, `Hash` and the orderings derive from the standard library. `Display`, `From`, `Into`, `AsRef` and a plain `new` that only assigns every field derive with [`derive_more`](https://crates.io/crates/derive_more) whenever it produces the same code, and the dependency is added with the first impl it replaces. An impl is written by hand only when it needs logic.
- **Types hold every constraint they can.** An enum for a closed set of values, never a string or a `bool` standing for one; a newtype for an identifier or a value with rules of its own. A doc comment stating a constraint that the type could enforce means the type is wrong.
- **A struct with one field is a tuple struct** only while all of its code is derived. Once it has a method or a hand-written impl, its field has a name, so code reads `self.path`, never `self.0`. A newtype never derives `Deref`, which is for smart pointers.
- **A chain of iterator adapters reads as a sentence of names**, such as `.filter(is_feature_file).map(page_address)`, and the details live in the functions it names. A closure in a chain is one call, one method call or one field read, such as `|step| &step.value`; a closure that compares, negates, matches, computes or builds a value becomes a named function.
- **Iterating to get a result uses adapters, not a `for` loop.** A search is `find`, `find_map`, `position`, `any` or `all`; a check of every item that fails on the first bad one is `try_for_each`; building a value is `count`, `sum`, `fold` or `collect`. A `for` loop stays only when its body acts on each item, such as writing a file or asserting in a test.
- **Every line does something.** No line that changes nothing, such as a conversion to the type a value already has.
- **Platforms diverge by size.** A `#[cfg]` on one line or one function is fine; a whole module that would be gated is an adapter of its own, behind the port the domain already has, chosen in the composition root. An answer per platform that is a value, not a call to the world, is a policy taking the platform's name, such as `std::env::consts::OS`, so that every platform's answer is tested on every platform.

## Comments

A comment says only what the code cannot:

- the module's role line;
- a measured fact, with what it was measured against, such as "Chromium, through Playwright 1.63.0, fails a `fetch` from a `file://` page";
- an invariant or a hazard the code does not enforce itself;
- what an absent value, an error or a rejection carries.

One sentence, where it applies, once. Why a decision was taken, what else was considered and what came before belong in the issue and the pull request, which keep them, not in the code. A field, a function or a test whose name already says what it is gets no doc comment.

Four more rules apply to every comment:

- A measured fact names the program and its version, never a date.
- A fact appears once in the repository. A second document that needs it says "see" with a path, and code that needs it relies on it without repeating it.
- No `TODO` comments, and no bold.
- Code never cites an issue, a pull request or a document, with one exception: a test cites the rule of docs/BEHAVIOUR.md it checks by its number, such as `// Rule 110: the parts are the step's text.`, so that each rule leads to its test.

## Dependencies between parts

No dependency injection framework. Every collaborator is received through a constructor, as a trait object or a generic, and only the composition root names the concrete adapters. Nothing else constructs its own collaborators. Tests hand in fakes written for the purpose, such as an input held in memory and an output that records what was written.

- **A handler holds the controller, and the controller each service, behind a trait**, a driving port, named after what it stands for with `Api`, such as `SiteApi` implemented by `SiteController`, or `ConverterApi` implemented by the converter, so that the tests of each hand in fakes of the layer below. Only the composition root names the concrete controller and services. It builds one controller for `ghg build` and `ghg serve`, whose site writer holds both adapters of the `FileWriter` port, so that the destination in the settings chooses between them.
- **A service earns its place**: it coordinates at least two of a port, an entity and a policy for a named stage. A single pass-through gets no service, and its caller calls the target directly. The converter has no port, and earns its place with the entities and policies of `site`, so that the controller calls services only.
- A pure function never gets a trait around it only to be faked.
- **Adapters translate, they don't decide.** An adapter turns the types of the crate it wraps into our entities and errors, and reports what it sees. Any choice about what matters to the domain is a policy that a service calls, never one the adapter calls itself: which folders of the input are entered and which files are kept is the input collector's to decide, and the adapter only lists a folder and reads a file. A type an adapter uses only for its mechanism, such as `notify`'s events or `tiny_http`'s requests, never appears in a port, an entity, an error, a policy or a service. The exceptions are the standard library's types, and the types of a crate that models the domain itself, such as `gherkin`'s, which the domain uses because they are what it is about; even those stop at the converter's first pass, and no node of the site tree holds one.

## How the code runs

- **Synchronous throughout.** gherkin-glass reads, computes and writes, then exits; it needs no async runtime. `rayon` runs the steps that may be parallel, parsing and rendering ([#3](https://github.com/marlon-sousa/gherkin-glass/issues/3)), and nothing else.
- **Errors** are `thiserror` types in `errors/`, and `anyhow`, if it is ever needed, only in the composition root. Their names end in `Error`, such as `InputError`, with `Errors` for a report of several and `ErrorKind` for what is wrong apart from where. An error carries data, such as a path, a line and its kind, and its `Display` is the sentence a person reads, so that all of an error's words are in one place and the handler prints it as it is. Each variant names, with `#[error(fmt = Self::…)]`, an associated function in the error's own `impl` that calls `fl!` with the variant's fields, or a function of `errors.rs` when several errors say the same thing; thiserror 2 allows `fmt` on enums only, so a struct writes its `Display` by hand. Words passed through from another program are `#[error("{message}")]`, an error that only wraps another is `#[error(transparent)]`, and one that shows only its kind is `#[error("{kind}")]`. A part of an error worded by the error that holds it, such as a `ConfigError`, which needs its file's path, or a `ListenErrorKind`, which needs the host and port, has no `Display` of its own. Context such as a path is put into the error where it is made, with `map_err`; `#[from]` is only for an error that carries nothing more, and a cause kept whole stays reachable as `#[source]`. No `#[error]` text is written for developers only. Every message a person reads must make sense spoken by a screen reader: a path, a line and a sentence, never a dump of a type ([#3](https://github.com/marlon-sousa/gherkin-glass/issues/3)).
- **Page addresses always use `/`**, on every platform, including Windows. Turning a file's path into a page's address is a policy that takes the path's parts, not the platform's separator, so every platform's answer is tested on every platform.

## Interface text

gherkin-glass's own words, such as "Collapse all", "Skip to content", "From the background:", the tree's labels and every message on the command line, are in English only for now, but are written so that translating them later changes no code ([#4](https://github.com/marlon-sousa/gherkin-glass/issues/4), [#23](https://github.com/marlon-sousa/gherkin-glass/issues/23)).

- **The catalogue is in [Fluent](https://projectfluent.org/)**: one `.ftl` file per language, `messages/en/gherkin-glass.ftl` for English, the only language for now. A translation is a new file beside it, which translators can work on in Weblate, whose documentation lists Fluent as a supported format since its version 4.8.
- **It is embedded with [`rust-embed`](https://crates.io/crates/rust-embed)**, a struct deriving `RustEmbed` over `messages/`, **loaded with [`i18n-embed`](https://crates.io/crates/i18n-embed)**, with its `fluent-system` feature, **and read with the `fl!` macro of [`i18n-embed-fl`](https://crates.io/crates/i18n-embed-fl)**. All three are MIT; the Rust `age` crate (rage) is built the same way.
- **What `fl!` checks at compile time**: that every message used exists in the English catalogue, the fallback language `i18n.toml` names, with exactly the arguments it takes, so a missing message is a build error and not a broken page. It checks only English, not the translations, and only arguments passed by name, so arguments are always passed by name, never as a map.
- **Fluent's isolation marks are turned off**, with `set_use_isolating(false)`. By default Fluent wraps every placeholder in the invisible characters U+2068 and U+2069, which would end up in the pages, the accessible names, the golden files and the terminal. Feature text placed inside a message is isolated by the HTML instead, with `<bdi>`, wherever it is in the markup.
- **Every interface string comes from the catalogue, by its id.** Templates receive their text from Rust code that uses `fl!`, errors their words from their own `Display`, as "How the code runs" says, and none of the templates, the Rust code or the script writes interface text inline.
- **A message is a whole sentence with named placeholders**, such as `feature-page-title = { $feature }, a feature in { $folder }` in Fluent's syntax, never pieces joined together, since word order differs between languages.
- **Counts are plural forms of one message**, chosen by the number with a Fluent selector, such as `scenario-count = { $count -> [one] one scenario *[other] { $count } scenarios }`, never a word with an `s` added, since languages have different plural rules. A count only the script knows, such as the number of search results, cannot be chosen by Fluent, since the page is written before it is known: it is written as a label and a number, `Results: { $count }.`, which needs no plural form.
- **The script receives its messages from the page**, written by the template, so that the script itself holds no words.
- **The parser's own messages are passed through as they are**, since they are the `gherkin` crate's, not ours.

The feature's own text is never interface text: it is shown as written in the file, in the file's language.

## The pages' script

The TypeScript in `script/` follows the same roles, each file declaring its role in a header comment. It uses no framework, and one runtime dependency only: [MiniSearch](https://www.npmjs.com/package/minisearch), bundled into the script, which runs search ([#15](https://github.com/marlon-sousa/gherkin-glass/issues/15)).

- **The views are the templates.** Everything a page says, its headings, anchors, links and text, is in the HTML the templates write. The script adds behaviour to it, and never writes content, with two agreed exceptions: the folder tree, built from the site's shared tree data ([#7](https://github.com/marlon-sousa/gherkin-glass/issues/7)), and what search finds, its status and its results ([#15](https://github.com/marlon-sousa/gherkin-glass/issues/15)).
- **Adapters** are the parts that touch the DOM, the browser's storage, the network or the clock: the disclosure buttons, the tree, the reader options, the theme switch, the search box, fetching the search documents, and waiting for the reader to pause. Each sits behind a small interface in `ports/`.
- **Policies** are the pure parts: which state a block starts in, given the configured default and what the reader chose before; how a remembered choice is keyed by page and anchor.
- **`src/main.ts`** is the composition root, as `composition_root.rs` is for the crate.
- **Sources live in `script/src/`, and tests in `script/test/`**, a tree that mirrors it, so a test of `src/adapters/tree.ts` is `test/adapters/tree.test.ts`.
- **What `script/` compiles to is one ES module.** Sites are served over HTTP, never opened from disk ([#26](https://github.com/marlon-sousa/gherkin-glass/issues/26), [design note 0026](design/0026-sites-are-served.md)), so the script may be a module and may fetch. The data the pages share, such as the folder tree's ([#7](https://github.com/marlon-sousa/gherkin-glass/issues/7)), is JSON written for each site and fetched by the script, at an address resolved against the script's own, such as `new URL("tree.json", import.meta.url)`, so that it works from a page at any depth and on a site served below a path such as GitHub Pages' `/<repository>/`.
- **The reload script `ghg serve --watch` adds to each page is not part of any site.** It is a few lines of plain JavaScript beside the server's adapter, `src/adapters/preview_http/reload.js`, embedded with `include_str!`, so that it needs no build step.
- **One line of script is not in `script/`**: the classic script in every page's head that applies the remembered theme before the page is drawn, which a module, run only once the page is read, cannot do ([#10](https://github.com/marlon-sousa/gherkin-glass/issues/10), [design note 0010](design/0010-themes.md)). It reads the key the theme policy keeps the choice under, and a test of the script checks that the two agree.
- **A reader option that cannot act is disabled**, and says so to a screen reader, rather than acting and then refusing.

## Tests

Cheapest first:

1. **Policy tests**, pure and in memory: the anchor rule, doc string corrections, page addresses, contrast, the state a block starts in.
2. **Service, controller and handler tests** with fakes of the layer below: a service's stage with fake ports, such as the input walked in memory; a whole build through the controller with fakes of the driving traits of the services, checking the order it calls them in, what it hands each and every problem reported; and a handler's wording with a fake controller.
3. **Rebuild tests**, unit tests of the controller with the real services over fake ports: scripted sequences of changes over an input held in memory, through the `MemoryFolders` fake of the test support, such as editing a feature, adding a tag that renames another tag's page, adding a file in a new folder, allowing a folder through a `!` rule and forbidding it again, and removing a file. After every step, the site built from the last build is compared, byte for byte, with the site built from nothing. They are one `rstest`, with a case per sequence, named for what it changes.
4. **Fixture tests** of a policy or a service: its code checked against a fixture under `tests/fixtures/`, read through the real adapters, or on scratch folders on the disk, in the tests of the module whose code it checks, in their `tests/against_fixtures.rs` when the module has other unit tests too.
5. **Golden fixture tests**: each fixture under `tests/fixtures/` built into a site, and its pages compared with the expected HTML committed beside it, which shows the rules of BEHAVIOUR.md the fixture covers; and so is the example suite of `project-site/`, against `project-site/expected`.
6. **The browser check** ([#2](https://github.com/marlon-sousa/gherkin-glass/issues/2)): every fixture's site and the example suite's served with `ghg serve --no-build` ([#26](https://github.com/marlon-sousa/gherkin-glass/issues/26)), as a reader would get it, and each page opened with Playwright, checked with axe-core in each theme, its borders and focus outline measured against WCAG's 3:1 for what is not text, and driven with the keyboard.
7. **The script's own tests**, of its policies and adapters, in `script/test/`.

`cargo xtask check` runs all of them, and CI runs the same command.

How a Rust test is written:

- **A test's name states the rule it checks**, as a sentence, such as `a_feature_in_portuguese_keeps_its_keywords`.
- **A setup that three or more tests of one module start the same way** becomes a helper of those tests, named for what it makes; when the tests go on differently, the helper makes only the part they share.
- **Policies over arbitrary text have property tests**, with [`proptest`](https://crates.io/crates/proptest), such as the anchor rule and step highlighting never panicking on any input.
- **A rule checked on several inputs is one parametrised test**, written with [`rstest`](https://crates.io/crates/rstest), with a named case per input, such as `#[case::a_rule_s_background("rule-background.feature")]`, never a run of asserts or a loop over a table. Each case's name says what its input is. A loop over every value of a closed set, such as every step kind, stays a loop, so that a new value is checked without a new case.

## What a contributor needs

Plain `cargo build` and `cargo test` need only Rust: the toolchain `rust-toolchain.toml` pins, and the minimum version `rust-version` names for the second test run, as AGENTS.md describes. Node, at its pinned version, is needed for `cargo xtask build` and `cargo xtask check`, which install the Node packages from the lockfile, and the browser the check uses, themselves.
