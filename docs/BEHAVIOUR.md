## Reading the input

Before anything is built, gherkin-glass finds the feature files under the input folder and reads every one of them. If any file cannot be read, the build stops and nothing is written.

### Which files are read

1. By default, a file is read when its name ends in `.feature`. Every other file is left out. Fixture: `tests/fixtures/input-files`.
2. By default, every hidden file or folder, one whose name starts with a dot, is left out with everything in it, even a file whose name ends in `.feature`. Fixture: `tests/fixtures/input-files`.
3. A file named `.ghg-ignore` changes these defaults, and nothing else does. It uses the [gitignore syntax](https://git-scm.com/docs/gitignore#_pattern_format) and may sit in any folder of the input. Its rules apply to the paths in that folder and everything below it, as a `.gitignore` file's rules do. Fixture: `tests/fixtures/input-files`.
   - A rule leaves out what it matches, such as `drafts/` or `old-*.feature`.
   - A rule starting with `!` reads again what the defaults or an earlier rule leave out, such as `!*.story` for files ending in `.story`, or `!.github/` for a hidden folder.
   - When several rules match a path, the last matching rule of the `.ghg-ignore` file nearest to the path decides. The defaults decide only when no rule in any `.ghg-ignore` file matches.
   - A path left out with its folder cannot be read again by a rule, because the folder is not looked into, as in git.
   - A `.ghg-ignore` file is never read as a feature, whatever the rules say.
4. No other file decides what is read: not `.gitignore` files, not `.ignore` files, not git's own exclude files, and not the ignore files of the folders above the input. Fixture: `tests/fixtures/input-files`.
5. Symbolic links are not followed, whether they point to a file or to a folder. Fixture: created by the test, since a symbolic link cannot be relied on in a checkout on every system.

### What is read

6. Each file is read as UTF-8 with the [`gherkin`](https://crates.io/crates/gherkin) crate: its feature, backgrounds, rules, scenarios, scenario outlines and their examples, steps, data tables, doc strings, tags and descriptions. Fixture: `tests/fixtures/constructs`.
7. A file written in any spoken language Gherkin supports is read with that language's keywords, given by a `# language:` line at the top of the file. A file without one is read in English. Fixture: `tests/fixtures/constructs`, which has a file in Portuguese.
8. Comments, the lines starting with `#`, are not kept.

### Doc strings

A doc string is the text between two delimiter lines, `"""` or three backticks, under a step. gherkin-glass keeps it as the author wrote it, as [Gherkin's own reference](https://cucumber.io/docs/gherkin/reference/#doc-strings) describes. Fixture: `tests/fixtures/doc-strings`.

9. Text after the opening delimiter, such as `json` in `"""json`, is the doc string's media type, kept apart from its content. A doc string without it has no media type.
10. The content is the lines between the opening and the closing delimiter, joined by line breaks, without a line break before the first line or after the last. A line of the content that starts with `#` is content, not a comment. From a `#` anywhere in a line of the content, a delimiter later on that line does not close the doc string.
11. Each line of the content loses as much of its leading indentation as the opening delimiter has, counting a space or a tab as one character. A line indented less loses all of it. A line indented more keeps the difference.
12. Inside a doc string opened with `"""`, an escaped delimiter `\"\"\"` reads as `"""`. Inside one opened with three backticks, three escaped backticks read as three backticks.
13. A file whose lines end in a carriage return and a line feed is read as if they ended in a line feed alone.

### Files that cannot be read

14. A file that cannot be read fails the build: a feature file that cannot be parsed, such as an empty file or one with only comments, or that cannot be read, such as one that is not UTF-8; a `.ghg-ignore` file with a rule that is not valid, whose other rules still apply; and a folder of the input that cannot be listed, the input folder itself included. There is no option to carry on without it. Fixture: `tests/fixtures/unreadable`.
15. Every such file is reported before the build stops, not only the first. The report has one line per problem, sorted by path, folder by folder, so that a folder's contents stay together, and then by line. Names are compared by their character codes, so capital letters come before small ones. The report is the same on every run. Fixture: `tests/fixtures/unreadable`.
16. Each line reads `<path>:<line>: <message>`, where the path is relative to the input folder, with `/` between folders on every system, the line is where the parser stopped, or the file's last line when it stopped past the end, and the message is the parser's. When the parser has no message of its own, only the list of what it expected, the message is `Syntax error.` A problem with no line, such as a file that cannot be read, reads `<path>: <message>`. A file that cannot be read has the message `cannot be read: <reason>`, a folder that cannot be listed `cannot be listed: <reason>`, a file that changed while it was being read `changed while it was being read`, and a `.ghg-ignore` rule that is not valid the `ignore` crate's message, where the reason is the operating system's words. A problem with the input folder itself shows its path as it was given, and an input folder that does not exist, the default `features` among them, reads `<path>: the input folder does not exist. Create it, or name another with input in ghg.toml or with --input.` Fixture: `tests/fixtures/unreadable`.

## The command line and its configuration

The command is `ghg`. How it builds a site is set by a configuration file, `ghg.toml`, kept with the feature files, and by options on the command line, which override it, so that a site builds the same way locally and in CI. Every sentence it prints is gherkin-glass's own interface text, except the messages of the libraries and the operating system it passes on, which are named where they appear.

### Commands

17. `ghg build` reads the input, as [Reading the input](#reading-the-input) describes, and when every file can be read, writes a site without versions into the output folder, as [Pages](#pages), [Folder pages](#folder-pages) and [The site's data](#the-sites-data) describe, unless it read no feature file, as [A build with no feature file](#a-build-with-no-feature-file), rule 229, describes. A version of a site is built with `ghg version add`, as [Versions](#versions), rule 120, describes, and a preview with `ghg preview add`, as [A preview](#a-preview), rule 211, describes. When it has written the site, it prints nothing to standard output and exits with status 0. Standard error is empty too, unless the site has no title, from `--title` or the configuration's `title`: then it holds the hint `The site has no title, so its home page is called Feature files. Set title in ghg.toml, or give --title.`; and unless the site's data is large, when it holds the warning of [Search](#search), rule 150. Either way the status is still 0. Fixtures: `tests/fixtures/configuration/default` and `tests/fixtures/pages`.
18. `ghg --help`, or `-h`, prints the commands and their options to standard output and exits with status 0, as it does after a command, such as `ghg build --help`. `ghg --version`, or `-V`, prints `ghg` and its version, such as `ghg 0.1.0`, the same way. Fixture: `tests/fixtures/configuration/default`.
19. A mistake on the command line stops the run before anything is read. It prints one message to standard error, naming what was typed wrong when something was, and exits with status 2. The mistakes are: no command; a command ghg does not have; `ghg version` or `ghg preview` without one of its subcommands, `add` and `remove`, or with a subcommand it does not have, as [Versions](#versions), rules 120 and 257, and [A preview](#a-preview), rules 211 and 258, describe; an option the command does not have; an option without its value, or with an empty one, such as `--input=`; a value given to an option that takes none, such as `--help=yes`; an option given more than once, but `--keep-in-output`, which [What the output folder keeps](#what-the-output-folder-keeps), rule 224, describes, and `--tag-link`, which rule 233 describes; an argument the command does not take; `--only` with `--no-build`, as [A site of only some feature files](#a-site-of-only-some-feature-files), rule 204, describes; a version's or a preview's name that cannot be one, as [Versions](#versions), rule 121, describes; a pattern of `--keep-in-output` that is not valid, as [What the output folder keeps](#what-the-output-folder-keeps), rule 226, describes; a value of `--message-format` other than `human` and `json`, as [A report for programs](#a-report-for-programs), rule 231, describes; and a value of an option that gives a key's setting that the key would refuse, as rule 234 describes. Fixture: `tests/fixtures/configuration/default`.
20. When the configuration file or the input stops a build, the report goes to standard error, one line per problem, nothing goes to standard output, and the status is 1. A configuration file with a problem stops the run before the input is read. Fixtures: `tests/fixtures/configuration/mistaken` and `tests/fixtures/unreadable`.

### The options of ghg build

An option's value follows it, as `--input specs`, or is joined to it by `=`, as `--input=specs`. Paths on the command line are relative to the current folder. One more option, `--only <file>`, builds a site of only the feature files a list names, as [A site of only some feature files](#a-site-of-only-some-feature-files), rule 204, describes, and another, `--keep-in-output <pattern>`, names what ghg leaves alone in the output folder, as [What the output folder keeps](#what-the-output-folder-keeps), rule 224, describes. `ghg build` takes `--message-format <format>`, which says how it reports how it ended, as [A report for programs](#a-report-for-programs), rule 231, describes, and `ghg serve` does not. `ghg version add` and `ghg preview add` take the options of `ghg build`, as rules 120 and 211 describe, but `ghg preview add` takes no `--replace-existing-version`, since a preview added again always replaces the last one.

21. `--config <file>` reads that configuration file instead of `ghg.toml` in the current folder. A file given this way that cannot be read, because it does not exist or for any other reason, stops the run with `<file>: cannot be read: <reason>`, the file shown as it was given and the reason in the operating system's words. Fixture: `tests/fixtures/configuration/configured`.
22. `--input <folder>` reads that folder as the input, whatever the configuration file's `input` says, `--output <folder>` writes the site into that folder, whatever the configuration file's `output` says, and `--title <text>` is the site's title, whatever the configuration file's `title` says. `--front-page <file>` is the front page's template, whatever the configuration file's `front_page` says, as [The front page](#the-front-page), rule 183, describes. Fixtures: `tests/fixtures/configuration/configured`, `tests/fixtures/pages` for `--title`, and `tests/fixtures/front-page` for `--front-page`.
232. Every other key of the configuration file has an option of `ghg build` and `ghg serve`, its name with `-` for `_` and two dashes before it, `tag_links`'s being `--tag-link`, as rule 233 describes. Each option wins over its key, as rule 25 says. `--source-link <address>` is the address of each feature file's source, whatever `source_link` says, with the same `{path}` and `{line}`, as [Pages](#pages), rule 47, describes. `--allow-unnamed`, `--collapse-rules`, `--collapse-scenarios`, `--show-tree`, `--inline-backgrounds` and `--replace-existing-version` each take `true` or `false`, as their keys do, so that an option can turn off what the file turns on, such as `--collapse-rules false` over `collapse_rules = true`. `--accent-light <colour>` and `--accent-dark <colour>` are the accent colours, whatever `accent_light` and `accent_dark` say, written as [The accent colours](#the-accent-colours), rule 118, describes. Fixtures: `tests/fixtures/pages`, built with `collapsed.toml` and the options that give back `expected`, `tests/fixtures/backgrounds`, built with `unchecked.toml` and `--inline-backgrounds true`, `tests/fixtures/highlighting`, built with `plain.toml` and both accents, `tests/fixtures/configuration/unnamed` and `tests/fixtures/configuration/unnamed-allowed`, built with `--allow-unnamed`, and `tests/fixtures/pages`, built twice with `--replace-existing-version`.
233. `--tag-link <pattern> <address> <text>` is one link from tags to another site, the three parts of a table of `tag_links`, in that order, as [Tags](#tags), rule 106, describes, such as `--tag-link '@issue-(\d+)' 'https://github.com/owner/repo/issues/$1' 'Issue $1'`. Its three values follow it; joined to it by `=`, as in `--tag-link=<pattern>`, it has only the one. It is given once for each link, in the order the links are tried, and the links given replace the configuration's whole `tag_links`, as `--keep-in-output` replaces `keep_in_output`. Fixture: `tests/fixtures/tags`, built with `plain.toml` and the links of its `ghg.toml`.
234. A value of the options of rules 232 and 233 that the key of the same meaning would refuse is a mistake on the command line, as rule 19 describes: it stops the run before anything is read, with status 2. An empty value of any of them, and a `--tag-link` with fewer than three values, is an option without its value, as rule 19 says, such as `The option --source-link needs a value.` or `The option --tag-link needs a value.` Any other such value prints the sentence rule 26 gives for the key, with the option's name in place of the key's and no `<file>:<line>: ` before it. So a value of an option of `true` or `false` that is neither reads `--collapse-rules must be true or false.`, a colour that is not one reads `--accent-light must be a colour in hexadecimal, in quotes, such as "#0b4f9c".`, an accent with too little contrast reads as rule 119 says, such as `--accent-light is #777777, which reaches only 4.00:1 against the light theme's background #f2f2f2. It needs at least 7:1.`, and a `--tag-link` whose pattern is not a regular expression, or is too large, or whose address or text names a group the pattern does not have, reads as rule 108 says, with `--tag-link` in place of `tag_links.pattern`, `tag_links.address` and `tag_links.text`, such as `--tag-link names the group 2, which the pattern does not have.` Of one `--tag-link` with all three values and several of these mistakes, the message is of its pattern's before its address's, and of its address's before its text's. Fixture: `tests/fixtures/configuration/default`.

### The configuration file

23. Without `--config`, the configuration file is `ghg.toml` in the current folder, and only there: the folders above are not searched. When there is none, every setting takes its default, and that is not a problem. A `ghg.toml` that is there but cannot be read, such as a folder of that name or a file that is not UTF-8, stops the run with `ghg.toml: cannot be read: <reason>`, as rule 21 describes. Fixture: `tests/fixtures/configuration/configured`.
24. The file is written in [TOML](https://toml.io/). Paths in it, and the defaults of the keys that take a path, are relative to the folder the file is in, whichever folder ghg runs from. Without a file, the defaults are relative to the current folder. It may set these keys, and the features that need more add them here as they are built:

    | Key | Takes | Default | What it sets |
    | --- | --- | --- | --- |
    | `input` | text | `features` | The input folder, the folder of feature files to read. It must exist, as rule 16 says. |
    | `allow_unnamed` | `true` or `false` | `true` | Whether features, rules and scenarios may have no name, as [Anchors](#anchors), rule 35, describes. |
    | `output` | text | `site` | The output folder, where the site is written, as [Pages](#pages), rule 38, describes. |
    | `source_link` | text | none | The address of each feature file's source, as [Pages](#pages), rule 47, describes. Without it, pages have no link to their source. |
    | `collapse_rules` | `true` or `false` | `false` | Whether rules start collapsed, as [Pages](#pages), rule 51, describes; checked by `tests/fixtures/pages`. |
    | `collapse_scenarios` | `true` or `false` | `false` | Whether scenarios, scenario outlines, backgrounds and the scenarios an outline's examples produce start collapsed, as [Pages](#pages), rule 51, describes; checked by `tests/fixtures/pages`. |
    | `title` | text | `Feature files` | The site's title, as [Folder pages](#folder-pages), rule 81, describes; checked by `tests/fixtures/pages`. |
    | `show_tree` | `true` or `false` | `true` | Whether the folder tree is shown on a window 48em wide or wider when a reader first opens the site, as [The folder tree](#the-folder-tree), rule 88, describes; checked by `tests/fixtures/pages`. |
    | `inline_backgrounds` | `true` or `false` | `true` | Whether pages start with the backgrounds inside each scenario expanded and those in their own place collapsed, or the opposite, as [Backgrounds](#backgrounds), rule 97, describes; checked by `tests/fixtures/backgrounds`. |
    | `tag_links` | a list of tables, each written `[[tag_links]]` | none | The links from tags to other sites, as [Tags](#tags), rule 106, describes; checked by `tests/fixtures/tags`. |
    | `accent_light` | a colour, as text | `"#0b4f9c"` | The light theme's accent colour, as [The accent colours](#the-accent-colours) describes. |
    | `accent_dark` | a colour, as text | `"#8cc4ff"` | The dark theme's accent colour, as [The accent colours](#the-accent-colours) describes. |
    | `replace_existing_version` | `true` or `false` | `true` | Whether an earlier build in the output folder is replaced: a site without versions, as [Pages](#pages), rule 38, describes, or a version of one, as [Versions](#versions), rule 123, describes.     | `keep_in_output` | a list of text | none | The patterns of what ghg leaves alone in the output folder, as [What the output folder keeps](#what-the-output-folder-keeps), rule 224, describes; checked by `tests/fixtures/keep-in-output`. |

    Fixture: `tests/fixtures/configuration/configured`.
25. A setting given on the command line wins over the file's key of the same meaning, and the file's key wins over the default. Fixture: `tests/fixtures/configuration/configured`.
26. A key the file may not set, a table among them, or a value of the wrong type, is never ignored: it stops the run. Every such problem in the file is reported, sorted by line, each as `<file>:<line>: <message>`, the file shown as given and the line that of the key, or for a value that cannot be used, such as one of the wrong type, that of its value. An unknown key reads `ghg has no setting named <key>.`, a key that takes text and was given something else `<key> must be text, in quotes.`, a key that takes `true` or `false` and was given something else `<key> must be true or false.`, a path, an address or a title given as empty text `<key> must not be empty.`, a `keep_in_output` that is not a list of text and a pattern in it that is empty or not valid the messages of [What the output folder keeps](#what-the-output-folder-keeps), rule 226, and a key that takes a colour and was given something else, or an accent colour with too little contrast, the messages of rules 118 and 119. The keys of a table of `tag_links` are named with it, such as `tag_links.pattern`, and rule 108 adds their own messages. A file that is not valid TOML, such as one with a key given twice or text without quotes, is reported once, at the line where the [`toml`](https://crates.io/crates/toml) crate stopped, with that crate's message. Fixtures: `tests/fixtures/configuration/mistaken`, `tests/fixtures/configuration/mistaken-pages`, `tests/fixtures/configuration/mistaken-tags`, `tests/fixtures/configuration/not-boolean`, `tests/fixtures/configuration/empty-input`, `tests/fixtures/configuration/not-toml`, `tests/fixtures/configuration/not-colour`, `tests/fixtures/configuration/faint-accents` and `tests/fixtures/configuration/version-name`, whose `version_name`, a key of gherkin-glass 1, reads `ghg has no setting named version_name.`

## Anchors

Every scenario, scenario outline, rule, background and examples block of a feature has an anchor, made from its name by the rule below, and so does every scenario an outline produces from a row of its examples ([#13](https://github.com/marlon-sousa/gherkin-glass/issues/13)). A scenario outline is any scenario with examples, whatever its keyword. A link to a block keeps working as long as its file, its name and the blocks before it on its page that share its anchor stay as they are; an outline's rows keep theirs as long as the rows before them do. A block's anchor is the `id` of its heading on its feature's page, or, for an examples block, of its item in its outline's list of examples, as [Pages](#pages) describes. A row's anchor is the `id` of the heading of the scenario it produces, as [An outline's examples as scenarios](#an-outlines-examples-as-scenarios), rule 130, describes.

The rule is part of what is promised: changing it is a major version ([CONTRIBUTING.md](../CONTRIBUTING.md), "Releases").

### The anchor rule

27. The name is normalised to Unicode NFC and lower-cased, and the anchor is in NFC. Fixture: `tests/fixtures/anchors`.
28. Apostrophes, `'` and `’`, are removed. Fixture: `tests/fixtures/anchors`.
29. Every run of characters other than letters and digits becomes one `-`, and there is no `-` at either end. Letters and digits are the characters Unicode gives the Alphabetic or Numeric property. A combining mark, such as Devanagari's virama, stays when it follows a letter, a digit or another mark that stays, and so does a zero width joiner or non-joiner between one that stays and a letter or digit, as Persian writes inside words; anywhere else, such as the variation selector after an emoji, it is a gap like any other character. Fixture: `tests/fixtures/anchors`.
30. Letters outside a to z, such as `ã` or `ç`, are kept, not transliterated or percent-encoded: "Saque em conta poupança" becomes `saque-em-conta-poupança`. Fixture: `tests/fixtures/anchors`, which has a feature in Portuguese.
31. A block with no name takes the keyword written in the file instead, made into an anchor by rules 27 to 29, such as `background`, `contexto` or `esquema-do-cenário`. So does a block whose name leaves nothing after rule 29, such as `???`. When the keyword leaves nothing too, as the emoji keywords of Gherkin's `em` language do, the anchor is the block's kind in English: `background`, `rule`, `scenario`, `scenario-outline` or `examples`. Fixture: `tests/fixtures/anchors`.
32. Anchors are unique on a page. Taking the blocks in file order, each takes the anchor rules 27 to 31 make, or, when an earlier block already has it, the first of that anchor followed by `-2`, `-3` and so on that no earlier block has. So an unnamed rule's background, after the feature's, is `background-2`. The `id`s gherkin-glass gives the page's own parts, such as the skip link's target, `ghg_main`, each contain `_`, which no anchor contains, so that no anchor is ever taken by one of them, nor one of them by an anchor. Fixture: `tests/fixtures/anchors`, and `tests/fixtures/pages` for the page's own `id`s.
33. A scenario produced from a row of an outline's examples takes the outline's anchor, then `-row-`, then the row's number, counted from 1 across all the outline's examples blocks in file order, without their header rows, such as `withdraw-cash-row-3`. These anchors are made after every other anchor on the page, in file order, and one that an earlier anchor already has is made unique as rule 32 says. Fixture: `tests/fixtures/anchors`.
34. A feature has no anchor of its own: it is the page. Fixture: `tests/fixtures/anchors`, where a scenario named as its feature takes the anchor unnumbered.

### Blocks without a name

35. Backgrounds and examples blocks may always be unnamed. Features, rules and scenarios, outlines included, may be unnamed while `allow_unnamed` is `true`, its default. When it is `false`, each unnamed feature, rule, scenario and scenario outline is a problem that stops the build, reported with the problems of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as rules 15 and 16 describe, at the line of its keyword. The messages are `The feature has no name, and allow_unnamed is false.`, and the same with `rule`, `scenario` or `scenario outline` in place of `feature`. Fixtures: `tests/fixtures/configuration/unnamed` and `tests/fixtures/configuration/unnamed-allowed`.

## The map of anchors

Every site, every version of one and every preview has a map of its anchors, a file that tells another program the page and the anchor of each block of each feature file, so that it links to a scenario without making its anchor itself ([#168](https://github.com/marlon-sousa/gherkin-glass/issues/168)). Unlike the site's data, its form is promised, as the anchor rule is.

263. The map is `assets/anchors.json` in the folder of the site, the version or the preview it maps: `assets/anchors.json` at the output folder's root for a site without versions, `<version>/assets/anchors.json` for a version, such as `v1.0.0/assets/anchors.json`, and `previews/<name>/assets/anchors.json` for a preview, so that a program reads the map of the version it links to. ghg writes it from the descriptor and the objects, as [The site's data](#the-sites-data) describes, with the shell, and removes it with the shell, as rule 255 describes. Pages never load it, so it adds nothing to what a reader downloads. A site built with `--only` maps only the files it shows, as rule 206 describes, and under `ghg serve --watch` it is served from memory with the rest of the site, as rule 66 describes. Fixtures: `tests/fixtures/anchor-map`, and every fixture's expected site.
264. The map is one JSON list, with one entry for each feature, rule, background, scenario, scenario outline and examples block, in the order of the documents of search, rule 147: the files in the order of rule 15, and within a file the feature, then its blocks in file order. The backgrounds a scenario shows inside it, rule 95, and the scenarios an outline's rows produce are not entries of their own. Each entry is an object with these members:

    | Member | Holds |
    | --- | --- |
    | `path` | The feature file's path below the input folder, with `/` between folders, as rule 16 shows paths. |
    | `kind` | The block's kind, `feature`, `rule`, `background`, `scenario`, `scenario-outline` or `examples`, as rule 148 names kinds. |
    | `name` | The block's name as written, or empty text for a block with no name. |
    | `line` | The line of the block's keyword, counted from 1. |
    | `page` | The name of the feature's page, as rule 36 makes it, such as `catalogue/searching`, which follows the first `#` of the page's address, as rule 235 describes. It is not percent-encoded. |
    | `anchor` | The block's anchor ([Anchors](#anchors)), or empty text for a feature, which is its page. |
    | `rows` | For an examples block, one object for each row of its table but its header, as rule 33 counts them, with the members `line`, the row's line, counted from 1, and `anchor`, the anchor rule 33 gives the scenario it produces; an empty list for an examples block without rows. It is `null` for every other kind. |

    So a program links to a block at `<version>/#<page>#<anchor>`, and to a feature at `<version>/#<page>`, with the page and the anchor percent-encoded as rule 238 encodes them, since a page's name may hold a space, `#`, `?` or `%`. Fixture: `tests/fixtures/anchor-map`.
265. No two entries of one file, rows included, share a line, so that a program matches a report's scenario by its path and its line alone, never by its name. A row's line is that of the row itself in the file, which ghg finds in the file's text, since a comment or a blank line may sit between a table's rows. Fixture: `tests/fixtures/anchor-map`, whose outline's examples table has a comment and a blank line between its rows.
266. The map's form is part of what is promised, like the anchor rule and the addresses: removing a member, or changing what one holds, is a major version, and adding one is not, so a program ignores the members it does not know. It is promised apart from the site's data, so that a conversion of the store, as rule 246 describes, never changes it. Fixture: `tests/fixtures/anchor-map`, whose expected map is committed.

## Addresses

In gherkin-glass 2.0, each version of a site, each preview, and a site without versions, is one file for the browser, its shell, from which the script draws every page, and what follows the `#` of an address names the page ([#173](https://github.com/marlon-sousa/gherkin-glass/issues/173), section 2). An address is part of what is promised, like an anchor: changing how one is made is a major version ([CONTRIBUTING.md](../CONTRIBUTING.md), "Releases").

235. A page's address is its shell's address, then `#`, then the page's name, and, for a block, then `#` and the block's anchor, as [Anchors](#anchors) describes. The shell is `index.html` at the output folder's root for a site without versions, `<version>/index.html` for a version, as [Versions](#versions) describes, and `previews/<name>/index.html` for a preview, as [A preview](#a-preview) describes, so `v1.0.0/#catalogue/searching#searching-by-title` is the block `searching-by-title` of the page `catalogue/searching` of the version `v1.0.0`. A feature file's page is named as rule 36 says; a folder's page is the folder's path below the input folder followed by `/`, such as `catalogue/` or `catalogue/archive/`; and the home page's name is empty, so a version's home page is its shell's address with nothing after the `#`, or with no `#`. Every link from one page to another of the same shell is the `#` and what follows it alone, so that following it draws the page without loading the shell again. A link to a page of another shell, such as one of [A page in other versions](#a-page-in-other-versions), names that shell's `index.html`, as rule 79 says, such as `../v1.0.0/index.html#catalogue/searching`. Fixtures: `tests/fixtures/pages`, and `script/test/policies/address.test.ts`, which reads and writes every form of address of this section.
236. After the first `#`, a second one right away, `##`, followed by an `id`, names an element of the page being shown rather than another page, such as `##ghg_main`, the target of the skip link of rule 86. Such an `id` contains `_`, as rule 32 says of the page's own `id`s, so that no anchor is ever one. Following such a link moves the focus to that element and scrolls to it, draws nothing again, and leaves the address as it was, so that reloading still draws the page being shown; opened as the address of a page not yet drawn, it draws the home page first. Fixtures: `tests/fixtures/pages`, `script/test/policies/address.test.ts`, and the browser check, which follows the skip link on every page.
237. The site's own pages have addresses of the same form, their names without `.html`: `#tags/` for the index of tags and `#tags/<name>` for a tag's page, its name made as rule 100 makes it, as [Tags](#tags) describes; `#steps` for the step sentences, as [Step sentences](#step-sentences) describes; and `#search` for the page of search results, followed by `?q=` and the words searched for, encoded as a form encodes them, a space as `+`, such as `#search?q=free+room`, as [Search](#search), rule 214, describes. Fixtures: `tests/fixtures/pages` and `tests/fixtures/tags`, and `script/test/policies/address.test.ts`.
238. In an address ghg or the script writes, each byte of a page's name and of an anchor other than an ASCII letter, a digit, `-`, `.`, `_`, `~` and `/` is percent-encoded, as rule 47 encodes a path, so `saque em conta poupança.feature` is linked as `#saque%20em%20conta%20poupan%C3%A7a`. The script decodes an address as UTF-8 before it reads it, the words of `?q=` reading `+` as a space, as a form encodes them, so an address written with those characters as themselves, as a browser's address bar may show it, names the same page. Fixtures: `tests/fixtures/pages`, which has a feature in Portuguese, and `script/test/policies/address.test.ts`.
239. An address that names no page of its shell, such as that of a feature file since removed, is drawn as a page whose only `h1` and title read `Nothing is at this address`, the title followed by a comma, a space and the site's title, as rule 81 gives it, and on a version by the version as rule 269 says, with the skip link, the reader options, the folder tree and the search box of every page, as rules 86 to 93 and 151 describe, a breadcrumb holding only the link to the home page, after the link to the versions page on a version, as rule 267 describes, and, under the `h1`, the paragraph `This site has no page at this address.` An address that names a page but an anchor or an `id` the page does not have draws the page, with the focus moved as rule 240 says of an address that names no anchor. Fixtures: `tests/fixtures/pages`, and `script/test/services/navigation.test.ts`.

## How a page is drawn

Every page but the front page is drawn by the site's script, from the site's data, when its address is opened, and the focus is kept where a screen reader expects it ([#173](https://github.com/marlon-sousa/gherkin-glass/issues/173), section 3). The script draws only what ghg worked out, in the data rules 244 to 256 describe: it never makes an anchor, a sentence or an order of its own, and never inserts HTML from data. Where a rule of this document says what a page holds, shows or starts with, it speaks of the page as the script draws it, except where it names the front page or the versions page, which are in their HTML as ghg writes them.

240. While the script draws a page, the focus stays in the page's `main`, which has `tabindex="-1"` and is marked `aria-busy="true"` until the page is drawn, so that it never falls to the top of the document. When the link followed is outside the `main`, such as one of the folder tree, the breadcrumb or a list of search results, the script first moves the focus to the `main`. When the page was reached from another page of the same shell, by a link, by the browser's back or forward button or by a change of the address, the script then waits 150 milliseconds, so that a screen reader has taken in the new page, sets the page's title, says the title in a live region, an element outside the `main` marked `role="status"`, and moves the focus to the page's `h1`, or to the element the address's anchor or `id` names, and scrolls it into view. When the shell is opened at an address, the script sets the title as it draws, says nothing, and moves the focus only to the element the address's anchor or `id` names, if any. Before moving the focus to an anchor's element, it expands every block that element is inside, as rule 55 says. The browser never scrolls to an anchor itself, since no element's `id` is a whole fragment, so the script scrolls on every move, within a page too: following a link to another anchor of the page being shown draws nothing again, and moves the focus and scrolls at once. The wait was measured with one screen reader and one browser, as design note 0173 records. Fixtures: `script/test/services/navigation.test.ts`, and the browser check, `tests/browser/navigation.mjs`, which follows links between pages and to anchors on every fixture's site and checks the focus, the title, the live region and the scroll.
241. Each shell is one `index.html`, written by ghg, whose `html` element's `lang` is `en`, which the script sets to each page's own as it draws it, as rule 42 says, and whose head holds the shell's title, a description of one line, the link to the shared stylesheet and icon and the shared script of rule 39, the classic script of rule 116, and a `style` element with the build's accent colours, as rule 117 describes; and, for a preview, the request of rule 211 not to be indexed. The shell's title is the site's title, as rule 81 gives it, followed, for a version, by a comma, a space and the version, worded as rule 268 says, such as `Itinera conformance, v0.1.1` or `Itinera conformance, main, a development version`, which is the title of the version's home page, as rule 269 gives it. The description reads `The feature files of <title>, shown as pages.`, with the shell's title. Its body holds, in this order, the dialog of rule 182, the skip link of rule 86, the reader options and the folder tree, empty, of rules 87 to 93, the breadcrumb, empty, of rule 85, the search box of rule 151, the `main`, the live region of rule 240, the footer of rule 194, and the paragraph of rule 242. The `html` element's `data-ghg-descriptor` holds the path of the shell's descriptor in the store, as rule 244 names it, such as `versions/v1.0.0.json`, `previews/pr-131.json` or `site.json`; the script finds the store at `../../data/`, resolved against its own address in `assets/<ghg>/`, as rule 39 says, and fetches that descriptor from it. A version's `main` is empty and marked busy as the shell loads; the `main` of a site without versions, and of a preview, holds the front page, as [The front page](#the-front-page) describes, which the script leaves as it is when the address has nothing after its `#`, and puts back when the reader returns to it from another page. Fixtures: `tests/fixtures/pages`, `tests/fixtures/versions` and `tests/fixtures/only`, whose expected shells are committed.
242. A shell's body holds a `noscript` element whose paragraph reads `This site needs JavaScript to show its pages. Turn it on, then load this page again.`, so that a browser with JavaScript turned off says why it shows nothing. Fixtures: `tests/fixtures/pages`, and the browser check, which opens a shell with JavaScript turned off.
243. When the site's data a page needs cannot be fetched or read, the script draws in the `main` the paragraph `This page could not be loaded. Load it again, or check that the site is served.`, sets no other content, and disables the folder tree's checkbox and button, as rule 93 says. Fixtures: `script/test/services/navigation.test.ts`, with a store whose files cannot be fetched.

## The site's data

Every site, every version of one and every preview stores each feature file's content once, in one store at the output folder's root, shared by all of them, from which the script draws their pages ([#173](https://github.com/marlon-sousa/gherkin-glass/issues/173), sections 4 and 5). The store's files are JSON, written for ghg and its script, not for other programs, which read the map of anchors of [#168](https://github.com/marlon-sousa/gherkin-glass/issues/168) instead: their form is described here, member by member, so that ghg and the script work to one description, and so that a later ghg can convert them, but it is not promised to anyone else, and a later version of ghg may change it, converting the store as rule 246 describes.

### Where it is

244. The store is the folder `data` at the output folder's root, which holds:
    - `data/objects/<hash>.json`, the objects, one for each feature file's content, as rules 247 to 251 describe;
    - `data/site.json`, the descriptor of a site without versions, `data/versions/<name>.json`, the descriptor of each version, and `data/previews/<name>.json`, the descriptor of each preview, as rule 252 describes;
    - `data/versions.json`, the list of versions, as rule 253 describes, and `data/pages.json`, the index of pages across versions, as rule 254 describes, on a site with versions only.

    The marker of rule 38 lists every file of the store. Under `ghg serve --watch`, the store is in memory, with one descriptor, `data/site.json`, as rule 66 says. Fixtures: `tests/fixtures/pages`, `tests/fixtures/versions` and `tests/fixtures/only`, whose expected stores are committed.

### Its format

245. Every file of the store, and the marker, holds `format`, the number of the store's format, which is `1` in gherkin-glass 2.0. The marker holds, in this order, `format`, `ghg`, the version of the ghg that last wrote the output folder, and `files`, the path of every file ghg wrote there, with `/` between folders, in the order of rule 15. One number covers the whole store, and the rule of block hashes, rule 251, is part of it. A new member added to a file keeps the number: a reader passes over the members it does not know, and this document says what a missing member stands for. Any other change, a member renamed, removed or holding something else, or a new rule of hashes, raises it. Fixture: `tests/fixtures/pages`.
246. A command that writes the output folder and finds any file of its store, or its marker, in an older format, as after a conversion that was stopped half way, converts the whole store before it writes anything else: every descriptor and every object, from each format to the next in turn, working out again from the stored content and settings what the new format holds, and every shell, written again from its descriptor, and the versions page, from `data/versions.json`, as rule 253 describes, so that the whole output folder is always in one format, the one the script of the ghg that wrote it reads. Converted objects take their new names, and the old ones are removed as rule 255 says. A store in a format newer than the ghg's own stops the run before the input is read, writes and deletes nothing, and reports `<output>: the site's data was written by ghg <version>, in a newer format than this ghg reads, so it is left as it is. Use ghg <version> or later.`, with the version the marker names. Fixtures: `tests/fixtures/store/newer`, whose marker names format 2; the conversion has its fixtures from the first format that converts.

### Objects

247. Each file of the store, and the marker, is written as compact JSON, with no space or line break between its tokens, in UTF-8. In text, only `"`, `\` and the characters below U+0020 are escaped, as `\"`, `\\`, `\b`, `\f`, `\n`, `\r` and `\t`, or otherwise as `\u` and four lower-case hexadecimal digits, and every other character, ASCII or not, is written as itself. Numbers are whole numbers, written without a sign, leading zeros or a point. The members of each object are in the order this section lists them, in a table or in its text, every one of them always there. So the same content always gives the same bytes. An object is named by the SHA-256 of its own bytes, in lower-case hexadecimal, such as `data/objects/3f…a1.json`, so that two feature files whose content is the same, in one version or in two, share one object, and an object already in the store is already there, byte for byte. An object depends only on its feature file, never on the build's settings. Fixtures: `tests/fixtures/pages`, and `tests/fixtures/versions`, two of whose versions share objects.
248. An object holds the feature file's whole content as the `gherkin` crate reads it and rules 6 to 13 correct it, without its lines, and what ghg works out from it alone:

    | Member | Holds |
    | --- | --- |
    | `format` | The format, as rule 245 describes. |
    | `language` | The file's language as its `# language:` line names it, as rule 7 reads it, or `en` without one. |
    | `lang` | The page's `lang`, as rule 42 makes it from the language. |
    | `feature` | The feature, a block as rule 249 describes. |

    Fixture: `tests/fixtures/constructs`, whose objects hold every construct.
249. A block is a feature, a background, a rule, a scenario, a scenario outline or an examples block, each held as an object of JSON with these members:

    | Member | Holds |
    | --- | --- |
    | `kind` | `feature`, `background`, `rule`, `scenario`, `scenario-outline` or `examples`, the block's kind in English, a scenario outline being any scenario with examples, as [Anchors](#anchors) says. |
    | `keyword` | The keyword as written in the file, without its colon, such as `Example` or `Cenário`. |
    | `note` | `true` when the block's content starts with the note of rule 43, because its keyword differs from its kind's word, and `false` otherwise. |
    | `name` | The name as written, or empty text for a block with no name. |
    | `description` | The description as rule 45 shows it: the `gherkin` crate's description, which has its indentation taken off, each line without the spaces at its end, the lines with no text left out, joined by a line feed, such as `A refund gives the money back,\nin the way it was paid.`, or empty text for none. |

    | `blocks` | The blocks directly inside it, in file order: a feature's background, scenarios, scenario outlines and rules, and a rule's background, scenarios and scenario outlines. It is an empty list for every other block. |

    | `runs` | An examples block's runs, one for each row of its table but the header, as rules 129 to 131 describe: each an object with the members `anchor`, the row's anchor of rule 33, and `steps`, the outline's steps with the row's values put in their places, as rule 131 says, each as rule 250 describes. It is an empty list for every other block. |

250. A step is an object of JSON with these members, which hold what ghg works out of it, so that the script draws it as rules 45, 109 to 113 and 133 to 141 describe without doing any of that again:

A block's hash is the SHA-256, in lower-case hexadecimal, of the compact JSON, written as rule 247 says, of a list of what the block's page shows of it from the feature file: its kind, its keyword, its name, its description and its tags, then the list of its steps, each a list of its keyword, its text, its table and its doc string, as rule 250 holds them; an examples block's adds its table, as rule 249 holds it; an outline's adds the list of its examples blocks, each a list of its keyword, its name, its description, its tags and its table; and the feature's adds its language, as rule 248 holds it.     | Member | Holds |

    | `version` | The version's name, or `null` for a site without versions and for a preview. |

    | `title` | The site's title, as rule 81 gives it. |
    | `only` | `true` when the site was built from a list of feature files, as [A site of only some feature files](#a-site-of-only-some-feature-files) describes, and `false` otherwise. |

## Pages

Each feature file becomes one page of the site, which a screen reader can move through by heading, scenario by scenario, and which reads well for everyone. A site is meant to be served over HTTP, by any static web server or host or by `ghg serve` ([#26](https://github.com/marlon-sousa/gherkin-glass/issues/26)), and is not opened from disk ([design note 0026](design/0026-sites-are-served.md)). A page opened from disk says so, as [A page opened from disk](#a-page-opened-from-disk) describes.

### The site

36. The site has one page for each feature file, and one for each folder of feature files, as [Folder pages](#folder-pages) describes. A feature file's page is named by the file's path below the input folder without its last extension, or as it is when its name has none, as for `README`, or when its only dot is its first character, as for `.feature`, which keeps its name. So `billing/refunds.feature` is the page `billing/refunds`, at the address `#billing/refunds`, as [Addresses](#addresses), rule 235, describes, and `stories/read.story`, read through a `.ghg-ignore` rule, is `stories/read`. Folders are separated by `/` on every system. No page is a file of its own: every page of a site, a version or a preview is drawn from its shell. Fixture: `tests/fixtures/pages`.
37. Two files whose pages would have the same name, such as `a.feature` and `a.story`, stop the build. Names are compared exactly, letter by letter, so `A.feature` and `a.feature` are two pages, `#A` and `#a`, since a page is not a file of its own (rule 36). Each such file after the first, in the order of rule 15, is a problem reported with those of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as `<path>: has the same page, <page>, as <first path>.`, where the page is its own. Fixtures: `tests/fixtures/same-page`, and the tests of `src/policies/collecting/page_collisions.rs` for names that differ only in the case of their letters, which a checkout cannot hold side by side on every system.
38. The site is written into the output folder, `site` by default, or the folder `output` or `--output` names. The output folder and the folders in it are made as needed. The output folder is ghg's once ghg has marked it, with a file at its root, `ghg-site.json`, the marker, which holds the format of rule 245 and lists every file ghg wrote there, the site's data, as [The site's data](#the-sites-data) describes, among them, whatever the folder holds: a site without versions, versions of a site, as [Versions](#versions), rule 122, describes, previews, as [A preview](#a-preview) describes, or a site or versions with previews beside them. ghg marks only an output folder that is missing or empty. A marker ghg cannot read, or one that lists a path with an empty, `.` or `..` folder or file name in it, such as `../notes.txt`, which would lead outside the output folder, counts as no marker. Before every build, and before every command that adds or removes a version or a preview, before the input is read, the output folder must be safe. What the patterns of `--keep-in-output` or `keep_in_output` keep is left out of all that follows, as [What the output folder keeps](#what-the-output-folder-keeps), rule 227, describes:
    - An output folder that holds anything and no marker, or a file or a symbolic link in its place, is never written into: the run stops before the input is read, writes and deletes nothing, and reports `<output>: this is not a site ghg built, so it is left as it is. Build into an empty or new folder.`
    - A marked output folder must hold only what ghg wrote there: the marker and the files it lists, with the folders that hold them; a file it lists that is gone is no problem. Anything else, a file, a link or a folder, stops the run the same way, and reports `<output>/<path>: ghg did not write this, so the output folder is left as it is.`, where the path is the first such thing in the order of rule 15, a folder named rather than what is in it.
    - `ghg build`, which builds a site without versions, into an output folder that holds versions stops the same way, and reports `<output>: the output folder holds versions of a site, so add a version with ghg version add, or build into another folder.` An output folder that holds only previews, or nothing, takes either.
    - In a safe output folder, an earlier site without versions is replaced when `replace_existing_version` is `true`, its default, so that nothing of it is left but what another descriptor still references: its descriptor, `data/site.json`, and its shell are written again, and what no descriptor references any more is removed, as rule 255 describes, while previews beside it stay as they are. Nothing is written or removed until the input has been read without a problem and the output folder checked again, right before the site is written, so that a build whose input has a problem leaves the earlier one as it was. The marker is written first, listing every file about to be there and every file still to be removed, then the new objects, the shell, the descriptor and the files made from the descriptors, and what is removed is removed last, after which the marker is written again without what was removed, so that a build stopped half way, such as by a file that cannot be written, leaves only files the marker lists, and the next build, finding them, removes what nothing references, as rule 255 describes, and so finishes the job. When `replace_existing_version` is `false`, the run stops before the input is read, writes nothing, and reports `<output>: a site is already built here, and replace_existing_version is false.`

    Since ghg may remove what it wrote in a marked output folder at any build, anything put there by hand and not kept by a pattern can be lost, so the output folder is never a folder that holds anything else, but what the patterns keep.

    In these reports, `<output>` is the output folder as it was given, and an output folder that cannot be looked into reads `<output>: cannot be read: <reason>`, and one that cannot be emptied or marked `<output>: cannot be written: <reason>`. A file that cannot be written, or a folder that cannot be made for it, stops the build, which reports `<path>: cannot be written: <reason>`, the path being the output folder as it was given followed by the path in it of the file being written, and the reason in the operating system's words, as rule 20 describes. The files written before it stay. Fixtures: `tests/fixtures/pages`, and an output folder that cannot be written, created by the test.
39. Beside the shells, the output folder has `assets/<ghg>/`, where `<ghg>` is the version of the ghg that wrote it, such as `assets/2.0.0/`, holding `gherkin-glass.css`, the stylesheet, `gherkin-glass.js`, the script of the pages, an ES module, and `gherkin-glass.svg`, the icon, a gherkin in a glass, an image only, which carries no text ([#112](https://github.com/marlon-sousa/gherkin-glass/issues/112)), and `THIRD-PARTY-LICENSES.txt`, the name, version and licence of each package the script holds, with the licence's text. All four are built into ghg and are the same in every site a version of ghg builds, so such a folder never changes once written. Every shell links the folder of the ghg that wrote it, and the versions page that of the ghg that last wrote it, by a relative address, as every link in the site is, so that a site works at any address, below a path such as GitHub Pages' `/<repository>/` included; the icon with `<link rel="icon" href="…/assets/<ghg>/gherkin-glass.svg" type="image/svg+xml">`, so that a browser asks the host for no icon of its own. A folder of `assets/` that no shell and no versions page links any more is removed, as rule 255 describes. The script fetches the site's data, as [The site's data](#the-sites-data) describes, at addresses it resolves against its own. Fixtures: `tests/fixtures/pages` and `tests/fixtures/versions`.

### What a page holds

40. A page's content is drawn by the site's script from the site's data when its address is opened: every heading, anchor, link, list and table is in the page before the focus moves to it, as rule 240 describes. The front page is the exception: its content is in its HTML as it is written, as [The front page](#the-front-page) describes, and so is the versions page's, as [Versions](#versions), rule 127, describes. Fixtures: `tests/fixtures/pages`, whose drawn pages are committed beside it as `drawn/`, as [CONTRIBUTING.md](../CONTRIBUTING.md), "Fixtures", describes.
41. The feature's own text, its keywords included, is shown as written in the file. gherkin-glass's own text, such as "Contents", "Collapse all" and the kind of block each heading starts with (rule 43), is in English, whatever language the file is written in. Fixture: `tests/fixtures/pages`, which has a feature in Portuguese.
203. The feature's own text reaches every page as text, never as markup a browser reads, since feature files can be written by people the site's owner does not control: the names of features, rules, backgrounds, scenarios, outlines and examples blocks, descriptions, steps and their parameters, data tables, doc strings and their media types, tags, and the names of files and folders. The site's data holds the text as it is, and the script puts it into a page only as the text of an element or the value of an attribute, never as markup, as rule 40 says. In the HTML ghg writes itself, the front page, the shells and the versions page, every `<`, `>`, `&`, `"` and `'` of it is written as a character reference, such as `&#60;` for `<`, and in an address made from it, such as a source link (rule 47) or a tag's link to another site (rule 107), it is percent-encoded. So a page holds no element and no attribute other than those ghg and its script make, runs no script but ghg's own, and reads the text exactly as the file has it, `&amp;` as `&amp;`. Fixture: `tests/fixtures/hostile`, whose feature files put markup, scripts, event handlers, quotes, apostrophes and ampersands in each of those places, beside a folder whose name has an ampersand and an apostrophe; `tests/markup_as_text.rs` parses every file of HTML it builds, and the browser check, `tests/browser/hostile.mjs`, opens every page of it, its folder tree among them, and searches for its words, in the search box and on the page of search results, and finds them as text and no dialog opened.
42. The page's `lang` is the language of its feature file, as rule 7 reads it, and `en` for a file without a `# language:` line. It is written as Gherkin names the language, such as `pt` or `zh-TW`, except for the names Gherkin gives that are not that language's tag, which are written as the tag: `am`, Armenian, as `hy`; `bm`, Malay, as `ms`; `gj`, Gujarati, as `gu`; `lu`, Luxembourgish, as `lb`; `en-old`, Old English, as `ang`; `en-lol` and `en-tx` as `en`; and `em`, whose keywords are emoji, as `und`, undetermined. Nothing else on the page has a `lang` of its own, so that gherkin-glass's own text is read in the page's language too, except the feature text in the folder tree's items, as [The folder tree](#the-folder-tree), rule 89, describes. Fixture: `tests/fixtures/pages`.
43. A block's heading, other than those of rules 95, 129 and 130 and the group of rule 45, starts with the block's kind in gherkin-glass's own words, `Feature`, `Background`, `Rule`, `Scenario`, `Scenario outline` or `Examples`, whatever keyword the file uses, then a colon, a space and its name, such as `Scenario: Withdraw cash`, so that a file that mixes Gherkin's words for a kind reads the same as one that does not ([#119](https://github.com/marlon-sousa/gherkin-glass/issues/119)). A scenario outline is any scenario with examples, as [Anchors](#anchors) says, whatever its keyword. The heading never names the keyword written in the file, so a block written with `Example:` reads `Scenario: Booking a free room`, and one written with `Cenário:` reads `Scenario: Fora da regra`. When that keyword differs from the kind's word, other than in the case of its letters, the block's content starts, before its tags and its description, with a note, as [The note of a keyword](#the-note-of-a-keyword), rule 196, describes, such as `Note: in the Gherkin feature file, this scenario is defined with the keyword "Example".`; the feature's, under the page's `h1`; and an examples block's, inside what its button shows (rule 45). So `Scenario Outline:` has no such paragraph. A block without a name reads its kind alone, such as `Background`, except an examples block, which reads `Examples` and its place among its outline's examples blocks, named or not, counted from 1, such as `Examples 3` for the third, even when it is the outline's only block. Every button and link that reads a block's heading reads the same text. Wherever a heading's text is shown, in a heading, a button, a breadcrumb or a link, the name is isolated from the words around it with a `<bdi>` of its own, as rule 130 says of its headings, and so is the keyword in the note that names it. The feature's heading is the page's only `h1`. The page's title is the feature's heading, a comma, a space and the file's path below the input folder, such as `Feature: Withdraw cash, banking/withdraw.feature`. Fixture: `tests/fixtures/pages`, with its `kinds.feature`.
44. The feature's background and its rules are `h2`. In a file with a rule, the scenarios outside every rule are in the group of rule 45, whose heading is `h2`, and are `h3`, as a rule's scenarios are; in a file without rules, they are `h2`. A rule's background is at the same level as the rule's scenarios, `h3`. A background inside a scenario, as [Backgrounds](#backgrounds), rule 95, describes, is one level below the scenario, `h3` or `h4`, and so is the heading of the scenario's own steps after them, and the heading of the runs of each of an outline's examples blocks, inside its item in the list of the outline's examples, under which each run it holds is one level lower again, `h4` or `h5`, as rule 129 describes. An examples block has no heading, as rule 45 says. Here and below, a scenario is a scenario outline too. Fixture: `tests/fixtures/pages`.
45. Under the `h1` come, in this order: the feature's tags, its description, the link to its source (rule 47), the page's contents (rule 46), the buttons of rule 50, and then the feature's background, its scenarios, in the group below when the file has a rule, and its rules, in the order of the file. Under a rule's heading come its tags, its description, its background and its scenarios; under a scenario's, its tags, its description, the backgrounds it starts with, as [Backgrounds](#backgrounds) describes, its steps, headed after those backgrounds as rule 95 says, and, for an outline, the list of its examples, each holding its own runs (rule 129); and under a background's, its description and its steps. Fixture: `tests/fixtures/pages`.
    - **Tags** are a list, each tag as written, with its `@`, a link to its tag's page, as [Tags](#tags), rule 105, describes, followed by its link to another site when it has one (rule 107).
    - **A description** is one paragraph that keeps its line breaks. Its blank lines are not kept, since the `gherkin` crate does not keep them.
    - **Steps** are a numbered list, each step its keyword as written and its text, such as `Given a customer named "Ana"`, followed by its data table or doc string.
    - **A data table** is a table whose first row is its header: its cells are header cells, each heading its column, and the cells of the other rows are data cells. Each cell is its text as rule 6 reads it, with `\|` read as `|`.
    - **A doc string** is preformatted text, its content as [Doc strings](#doc-strings) describes, captioned by its media type when it has one.
    - **The group of the scenarios outside every rule**, in a file with a rule and a scenario outside every rule, is a block like a rule, whose heading reads gherkin-glass's own text, `Outside any rule`, and has the `id` `outside_rules`, which contains `_`, as rule 32 says of the page's own `id`s, so that no anchor takes it, not even a scenario's named "Outside any rule". Under its heading come those scenarios. A file without a rule, or whose scenarios are all inside rules, has no group.
    - **The list of an outline's examples** follows its steps: a paragraph, `Runs once for each row of these examples:`, left out when none of the outline's examples blocks has a row, as rule 33 counts them, whose `id` is the outline's anchor followed by `_scenarios`, such as `withdraw-cash_scenarios`, an `id` of the page's own, kept apart from every anchor as rule 32 says, then a list with one item for each examples block, in the order of the file. An item is not a heading, so a screen reader moves through the examples with its list item key, and hears how many there are, a plain list with its markers, so that each item shows a bullet and a screen reader names it as a list item, which tells the next examples block from the last of the runs before it. It has the examples block's anchor as its `id`, and holds a button whose text is the block's heading as rule 43 makes it, such as `Examples: Books`, followed, when the block has no row, because it has no table or only a header, by a space and `(nothing to run)`, such as `Examples: Small rooms (nothing to run)` or `Examples 2 (nothing to run)`. After the button come the paragraph naming the block's keyword when rule 43 gives it one, the block's tags, its description and its table, or only its tags and its description when it has no table, then, when the table has a row, the block of the runs its rows produce (rule 129). A block with no such paragraph, no table, no tag and no description has nothing to show: its item holds a button with that text that opens nothing, marked `aria-disabled="true"` and with no `aria-expanded`, which a screen reader announces as unavailable and which the keyboard still reaches as it reaches the others. It looks disabled too, with no arrow and in normal weight rather than bold, and in the theme's muted text colour, which keeps the contrast of rule 117.
46. The page's contents are a navigation landmark named "Contents", with a list of links to each of the page's rules and scenarios, and to the group of the scenarios outside every rule (rule 45), in the order of the file, the scenarios of each rule and of the group in a list inside its item. Each link's text is its block's heading, and its address is the page's, then `#` and the block's anchor, or `outside_rules` for the group, as [Addresses](#addresses), rule 235, describes, such as `#billing/refunds#store-credit`. The scenarios an outline's examples produce (rule 129) are not listed. A page with no rule and no scenario has no contents. Fixture: `tests/fixtures/pages`.
47. When `source_link` is set, the page has a link to its feature file's source, which reads `Source: ` followed by the file's path below the input folder. Without `source_link`, the page has no such link. Fixtures: `tests/fixtures/pages` and `tests/fixtures/configuration/configured`.

## Previewing a site

`ghg serve` builds a site and serves it over HTTP on the reader's own machine, so that it can be looked at before it is published. A site gherkin-glass builds is meant to be served, by `ghg serve` or by any static web server or host, and opening its pages straight from disk is not supported ([design note 0026](design/0026-sites-are-served.md)).

### Serving

56. `ghg serve` reads the configuration file and the command line as `ghg build` does, and has the options of `ghg build` but `--message-format`, which [A report for programs](#a-report-for-programs), rule 231, describes, and they mean the same. It builds the site into the output folder, as `ghg build` would, then serves that folder, unless it reads no feature file, as [A build with no feature file](#a-build-with-no-feature-file), rule 230, describes. That build is a site without versions, as `ghg build`'s is, and checks the output folder as `ghg build`'s does, as [Pages](#pages), rule 38, describes. To serve versions or previews, add them with `ghg version add` or `ghg preview add`, then serve the output folder with `--no-build`, as rule 57 describes. When the configuration, the input or the output folder stops the build, it reports it as `ghg build` does, as rule 20 describes, serves nothing, and exits with status 1. Fixture: `tests/fixtures/serve/built`.
57. `--no-build` serves the output folder as it is, without reading the input or building anything. Fixture: `tests/fixtures/serve/site`.
58. It listens on the address `127.0.0.1`, so that nothing on the network reaches it unless asked, at port 8000. `--host <address>` listens on another address, such as `0.0.0.0` for every network the machine is on, and `--port <number>` on another port. Port 0 asks the operating system for a free port. A port that is not a whole number from 0 to 65535 is a mistake on the command line, as rule 19 describes, and reads `The option --port needs a whole number from 0 to 65535, not <value>.` Fixture: `tests/fixtures/serve/site`.
59. When the port is already in use, at that address or at every address, as another server listening on `0.0.0.0` does, it serves nothing, never choosing another port by itself, prints `Port <port> is already in use. Choose another with --port.` to standard error, and exits with status 1. When it cannot listen for any other reason, such as an address the machine does not have, it prints `ghg serve cannot listen at <address>, port <port>: <reason>`, the reason in the operating system's words, and exits with status 1. Fixture: `tests/fixtures/serve/site`.
60. Once it listens, it prints `The site is served at <address>. Press Control+C to stop.` to standard output, where the address is the one to open in a browser, such as `http://127.0.0.1:8000/`, with the port the operating system chose for port 0. When it listens on every network, as with `0.0.0.0` or `::`, which a browser cannot open, the address printed is this machine's own, `127.0.0.1` or `[::1]`. It serves until it is stopped, as rules 199 to 202 describe. Fixture: `tests/fixtures/serve/site`.

### What it answers

61. It answers `GET` and `HEAD` requests. A request's path names a file below the served folder, its parts decoded from percent-encoding as UTF-8, and its query left aside. A path ending in `/` names the `index.html` file of that folder. A path naming a folder without the `/` is redirected, with status 301, to the same path with the `/`, so that the page's relative links work. Fixture: `tests/fixtures/serve/site`.
62. A file is served with status 200, exactly as it is, and with the content type the `mime_guess` crate gives for its extension, regardless of case, followed by `; charset=utf-8` when that type is text. An extension it does not know, and a file with none, is served as `application/octet-stream`. So the files a site holds are served as `text/html; charset=utf-8` for `.html`, `text/css; charset=utf-8` for `.css`, `text/javascript; charset=utf-8` for `.js` and `application/json` for `.json`. Fixture: `tests/fixtures/serve/site`.
63. Every answer says `Cache-Control: no-cache`, so that a browser asks again for a file before using its copy. Fixture: `tests/fixtures/serve/site`.
64. A path with no file, a path with an empty part, a part `.` or a part `..`, or a path that cannot be decoded, is answered with status 404 and the plain text sentence `Nothing is at this address in the site.` No request's path leads outside the served folder, though a symbolic link inside it is followed. Any method other than `GET` and `HEAD` is answered with status 405 and the sentence `ghg serve answers only GET and HEAD requests.` Fixture: `tests/fixtures/serve/site`.

### Watching

65. `--watch` watches the input folder, everything in it, its `.ghg-ignore` files among them, and the configuration file, whether it exists yet or not, and the front page's template as the configuration file, as [The front page](#the-front-page), rule 191, describes. A change that may change what a build reads makes it read the configuration file again and rebuild the whole site: a change to the configuration file, to a `.ghg-ignore` file, to a file the `.ghg-ignore` rules select, whether it was there before the change or only after it, so that a file made, changed, moved or removed counts, or to a folder holding such a file. Any other change rebuilds nothing, such as an editor's swap file, a file the rules leave out, or a file merely opened or read. When the watching may have missed a change, it rebuilds. An editor's burst of changes is one rebuild, and a change made during a rebuild starts another once it is done. A change to the configuration file, or a change the watching may have missed, makes it read the configuration file and the command line again, as rule 56 describes, then stop watching, dropping the changes still waiting, and watch again, on the input folder they now name and on the configuration file, before it rebuilds. So a change in a folder that is no longer the input is never seen. When the configuration stops that rebuild, as rule 67 describes, the watching stays as it was. Fixture: `tests/fixtures/serve/built`.
66. With `--watch`, every version of the site, the first one included, is built in memory and served from there, so the output folder is never written or deleted, nor checked as rule 38 describes, and the site's data, as [The site's data](#the-sites-data) describes, is served from memory with the rest. A new version is served only once all of it is built, so no half-built page is ever served. `ghg build` writes the output folder. Fixture: `tests/fixtures/serve/built`.
67. When a rebuild is served, it prints `The site was rebuilt.` to standard output. When the configuration or the input stops a rebuild, it prints the report `ghg build` would print to standard error, then `The site was not rebuilt, so the last site that built is still served.`, and carries on serving that site. When the first build stops, ghg serve stops, as rule 56 describes. Fixture: `tests/fixtures/serve/built`.
68. `--watch` and `--no-build` together are a mistake on the command line, as rule 19 describes, which reads `The options --watch and --no-build cannot be used together.` When watching cannot start as ghg serve starts, such as when the system's limit on watched folders is reached, it prints `ghg serve cannot watch <path> for changes: <reason>` to standard error, the reason in the operating system's or the `notify` crate's words, and exits with status 1. When watching cannot start again once ghg serve runs, as rule 65 describes, such as when the input folder now named does not exist yet, it prints the same sentence to standard error and does not exit: it does not rebuild, carries on serving the last site that built, unchanged, and still watches the configuration file, so that its next change tries to watch and rebuild again. Fixture: `tests/fixtures/serve/built`.

### Reloading

69. With `--watch`, every page served as `text/html` has one element added, `<script type="module" src="/__ghg/reload.js?build=<number>"></script>`, just before its last `</body>`, or at its end when it has none, where the number is that of the version it comes from, counted from 1. Nothing else of the page changes, and without `--watch` nothing is added. Fixture: `tests/fixtures/serve/built`.
70. With `--watch`, the path `/__ghg/build` answers the number of the version being served, as plain text, and `/__ghg/reload.js` answers the reload script. Without `--watch`, both are paths of the site like any other. Fixture: `tests/fixtures/serve/built`.
71. The reload script asks `/__ghg/build` once a second, and reloads the page when the number differs from its page's. While ghg serve does not answer, it keeps asking. Fixture: `tests/fixtures/serve/reload`, in the browser, by `tests/browser/reload.mjs`.
72. Before reloading, it remembers the heading the reader was in, among the headings drawn on the page, which leaves out those inside a collapsed block: when an element of the page has focus and some of it is in the window, the last heading with an `id` at or before that element in the page, and otherwise the last heading with an `id` whose top is at or above the top of the window. After the reload, which draws the page of the same address again, if the page still has a heading with that `id`, it scrolls the heading to the top of the window and moves focus to it, so that a sighted reader keeps their place and a screen reader resumes there rather than at the top. A focused element scrolled out of the window, such as the heading focused by the last reload after the reader scrolled on with the mouse, does not count. When there is no such heading, the page opens as any page does. The script says nothing of its own, so it has no interface text. Fixture: `tests/fixtures/serve/reload`, in the browser, by `tests/browser/reload.mjs`.

### Stopping

199. `ghg serve`, with or without `--no-build` or `--watch`, stops gracefully when it is asked to: on macOS and Linux, on `SIGINT`, which Control+C sends, `SIGTERM`, which `kill` and process managers send, and `SIGHUP`, which a closed terminal sends; on Windows, on Control+C and Control+Break. It then stops taking requests, lets those it is answering finish, stops watching under `--watch`, prints `The site is no longer served.` to standard output, and exits with status 0, as any command that has done its work, unless it is asked again meanwhile, as rule 202 describes. `SIGKILL` and `SIGSTOP`, which no program can handle, still stop or pause it at once, and so does closing its console on Windows, since Windows then ends the program as soon as ghg has been told; Control+Z still pauses it, as job control does; and Control+D, the end of the terminal's input rather than a signal, does nothing, since ghg serve reads nothing from the terminal. Fixtures: `tests/fixtures/serve/site`, with a request whose body never comes for the wait, and `tests/fixtures/serve/built`.
200. When it is asked to stop while a build runs, the first build or, under `--watch`, a rebuild, it lets that build finish, so that an output folder is never left half written, says what the build ended with, as rules 56 and 67 describe, and only then stops as rule 199 describes. After the first build, it stops without starting to serve; when that build was stopped by the configuration, the input or the output folder, it exits with status 1, as rule 56 says. Fixture: the tests of `src/controllers/site_controller.rs` and `src/services/server.rs`, since no test of the command can send a signal while a build runs and know it came then.
201. Before anything else, ghg serve asks the operating system to tell it of those signals. When it refuses, ghg serve builds and serves nothing, prints `ghg serve cannot handle Control+C and the signals that stop it: <reason>` to standard error, the reason in the operating system's or the `ctrlc` crate's words, and exits with status 1. Fixture: the tests of `src/controllers/site_controller.rs` and of `src/errors/serve_error.rs`, since no test can make the operating system refuse.
202. When it is asked to stop again while it waits for the requests being answered, as a client that stops reading can make it wait for ever, it ends at once, prints nothing more, and exits with status 130, the status a shell gives a command that Control+C ended. Only a request that comes while it waits counts: one that came while a rebuild finished does not. Fixture: `tests/fixtures/serve/site`, with a request whose body never comes.

## Accessibility

Every page gherkin-glass writes or draws is meant to be read and used by everyone: with a screen reader, with the keyboard alone, and in a light or a dark colour scheme. The browser check holds every page to the rules below on every pull request, and a page that breaks one fails it, as a failing test does ([AGENTS.md](../AGENTS.md), rule 3).

The check builds every fixture whose build makes a site, each with `--output` naming a folder of its own, serves the site with `ghg serve --no-build`, as rule 57 describes, so that it is checked as a reader gets it, and opens each of its pages in Chromium, with Playwright, at its address, as [Addresses](#addresses) describes, and checks it once the script has drawn it, as rule 240 describes, both opened at its address and reached by a link from another page. Every rule below is checked on every one of those pages, and on `tests/fixtures/accessibility/failing`, a page that breaks each rule, which the check must find. A feature file or configuration file under `tests/fixtures/` that is in neither a fixture the check builds nor one it names as making no site fails the check, so that no new fixture is left out of it.

### The rules checked

73. Every page passes [axe-core](https://www.npmjs.com/package/axe-core) 4.14.0 with every rule tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` or `wcag22aa`, which are WCAG 2.2 at levels A and AA, and with `color-contrast-enhanced`, the contrast of 7 to 1 that level AAA asks for, which axe-core leaves off unless asked. Rules axe-core tags `experimental` or `deprecated` are left out, as axe-core itself leaves them out of a run by tags. The other criteria of level AAA are followed where reasonable, but not checked. Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`.
74. Every page passes rule 73 twice: once with the browser's colour scheme light, and once dark, as `prefers-color-scheme` reads them. The themes a reader can pick on the page are checked the same way, each once, from when they are built ([#10](https://github.com/marlon-sousa/gherkin-glass/issues/10)). Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`, which has text whose contrast fails in the dark scheme only.
75. From the start of a page once it is drawn, Tab moves focus to every link, button and other control the page shows, each once, in the order they come in the page, and the next Tab leaves the page. Nothing the page hides, such as the content of a collapsed block, is reached, and the folder tree is one stop, as rule 91 describes. The check counts once the tree is built, or its checkbox disabled. Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`, whose links are reached out of order.
76. Enter and Space on a block's button each collapse or expand it, as rule 52 describes, and on a folder page's feature's button each show or hide its contents, as rule 84 describes, and Enter on "Collapse all" and on "Expand all" acts as rule 53 describes. Fixtures: every fixture whose build makes a site and has a block, and `tests/fixtures/accessibility/failing`, whose block's button Space does not turn over.
221. A page fits a window 320 CSS pixels wide, as WCAG 2.2's success criterion 1.4.10, Reflow, asks: at that width it does not scroll sideways, since nothing on it is wider than the window: a long word, such as a file's name, a tag or an address, breaks where it must, and a code block, such as a doc string, scrolls sideways within itself. The check opens each page at that width too, with what the page hides shown, such as collapsed blocks, and compares the page's width with the window's ([#149](https://github.com/marlon-sousa/gherkin-glass/issues/149)). Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`, a paragraph of which is wider than the window.

## Folder pages

Every folder of feature files has a page listing its subfolders and its features, and the input folder's page is the site's home page. Following their links reaches every page of the site, with no folder tree and no search, and the folder tree ([#7](https://github.com/marlon-sousa/gherkin-glass/issues/7)) links to them. Every page, a feature's or a folder's, starts with a breadcrumb of the folders above it.

### Where they are

77. Each folder of the input that holds a feature file, itself or in a folder at any depth below it, has a page, named by its path below the input folder followed by `/`, as [Addresses](#addresses), rule 235, describes, such as `#billing/` for the folder `billing`. The input folder's page is the home page, whose name is empty, and the site has it even when the input holds no feature file, which only `ghg serve --watch` builds, as [A build with no feature file](#a-build-with-no-feature-file), rule 230, describes. A folder with no feature file at any depth below it has no page. The home page of a site without versions, and of a preview, is also its front page, written in its shell, as [The front page](#the-front-page) describes; a version's home page is drawn as every other folder's page is. Fixture: `tests/fixtures/pages`.
78. A feature file and a folder never share a page, since a folder's page ends with `/`, so `index.feature` is the page `index` and `billing.feature` the page `billing`, beside the folder's page `billing/`, and folders whose paths differ only in the case of their letters, such as `Billing` and `billing`, are two pages, as rule 37 compares names. Fixtures: `tests/fixtures/same-page`, and the tests of `src/policies/collecting/page_collisions.rs` for folders in another case, which a checkout cannot hold side by side on every system.
79. Every link to a shell, or to the versions page, names its `index.html`, such as `v1.0.0/index.html`, `../index.html` or `../v1.0.0/index.html#billing/`, and is relative, so that it works on any server, one that does not answer a folder's own address with its `index.html` included. Fixtures: `tests/fixtures/pages` and `tests/fixtures/versions`.

### What a folder page holds

80. A folder page's `lang` is `en`, the language of gherkin-glass's own text. In a feature's link and the list of its contents, rule 83, the feature text, each name in a `<bdi>` of its own as rule 43 isolates it, has the `lang` of the feature's page, as rule 42 gives it, and gherkin-glass's own words around it have none of their own, so that they are read in English. Fixture: `tests/fixtures/pages`, which has a feature in Portuguese.
81. The page's only `h1` is the folder's name, and on the home page the site's title, which is `--title`, or the configuration's `title`, or `Feature files` without either, as rule 17 describes. The page's title is the folder's path below the input folder, a comma, a space and the site's title, such as `billing/archive, Banking`, and on the home page the site's title alone, each followed on a version by the version, as rule 269 describes. A home page that is the front page of a site with a template takes its `h1` and its title from the template instead, as [The front page](#the-front-page), rule 187, describes. Fixture: `tests/fixtures/pages`, built once with a `title` and once without.
82. Under the `h1`, the home page has the site's totals, a list of four counts: the folders below the input folder that have a page, the feature files, the rules and the scenarios, such as `3 folders` and `1 scenario`. A scenario outline counts as one scenario, whatever its examples hold, scenarios inside rules count, and backgrounds do not. Fixture: `tests/fixtures/pages`.
83. Then every folder page has the folder's subfolders, as a list under an `h2` that reads `Folders`, and the feature files in the folder itself, as a list under an `h2` that reads `Features`. The subfolders are sorted by their names, and the features by their files' names, the names compared by their character codes as rule 15 compares them, in the order the descriptor lists its features, as rule 252 describes, so that the script compares no names. A folder with no subfolder that has a page has no `Folders` heading and no list, and one with no feature file of its own has no `Features` heading and no list. Fixture: `tests/fixtures/pages`.
    - **A subfolder** is a link to its page, whose text is its name.
    - **A feature** is a link to its page, whose text is the feature's heading, as rule 43 makes it, followed by its count of scenarios, counted as rule 82 counts them, such as `2 scenarios`.
    - **A feature's contents** follow it when its page has contents, rule 46: the same list of links to its rules, its scenarios and the group of its scenarios outside every rule, each address the feature's page followed by `#` and the block's anchor, such as `#billing/refunds#store-credit`.
84. A feature with contents has its count of scenarios as a button, which says with `aria-expanded` whether its contents are shown, and whose accessible name is the count followed by ` of ` and the feature's heading, such as `2 scenarios of Feature: Refunds`. Its contents are hidden when the page is drawn. Pressing the button shows them when they are hidden, and hides them when they are shown. The browser remembers the choice as rule 54 says, kept under the folder page's address and the link's. A feature without contents has its count as text, with no button. A folder page has no "Collapse all" or "Expand all" buttons. Fixtures: `tests/fixtures/pages`, in the browser by rule 76, and the script's own tests, `script/test/adapters/dom_page.test.ts`, on `tests/fixtures/pages/drawn/site/folder/billing/index.html`.

### The breadcrumb

85. Every page, a feature's, a folder's, one of [Tags](#tags), the page of [Step sentences](#step-sentences) or the page of search results, has a breadcrumb before its main content: a navigation landmark named "Breadcrumb", holding a numbered list of links. The first is to the home page, whose text is the site's title; on a page of a version, two links come first instead, as rule 267 describes. Then comes one to the page of each folder above the page, from the outermost in, whose text is the folder's name, and last one to the page itself, whose text is its `h1`'s, marked with `aria-current="page"`; on the page of search results, it reads `Search results` whatever its `h1` says, as rule 216 describes. The home page's breadcrumb holds only its link to itself, and, on a version, the link to the versions page before it. Fixtures: `tests/fixtures/pages` and `tests/fixtures/versions`.

## The folder tree

Beside the content of every page, a feature's, a folder's, a tag's, the step sentences' or the search results', a tree of the input's folders, features, rules and scenarios helps a reader find their way in a large suite, with the current page marked. A checkbox shows or hides it. Everything the tree links is also linked from the folder pages, so a reader who hides it loses nothing. It follows the WAI-ARIA Authoring Practices [Navigation Treeview example](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-navigation/).

### Before the content

86. Every page's body starts with the dialog of [A page opened from disk](#a-page-opened-from-disk), rule 182, closed unless the page is opened from disk, and then a link that reads "Skip to content", whose address is `##ghg_main`, which names the page's `main`, as [Addresses](#addresses), rule 236, describes. The link is the first thing on the page a keyboard reaches, and it is out of sight until it has the focus. After it come the checkbox and the button of rule 87, then the folder tree, then the breadcrumb of rule 85, then the search box of [Search](#search), rule 151, and then the page's `main`, so that following the link passes over all of them. The versions page, which has none of them, is one exception, as [Versions](#versions), rule 127, describes, and the page of search results, whose search box is in its `main`, under its `h1` (rule 217), the other. Fixture: `tests/fixtures/pages`.

### Showing and hiding it

87. A window 48em wide or wider shows the checkbox, which reads "Show the folder tree" and is checked while the tree is shown, beside the content. Checking it shows the tree, and unchecking it hides it, from every reader, a screen reader's included. A narrower window shows in its place a button that reads "Folder tree", a disclosure as in the WAI-ARIA Authoring Practices' disclosure navigation example, whose `aria-expanded` says whether the tree is shown and whose `aria-controls` names the tree. Fixtures: the script's own tests, `script/test/adapters/dom_tree_switch.test.ts`, `script/test/adapters/media_width.test.ts`, `script/test/policies/tree_state.test.ts` and `script/test/services/folder_tree.test.ts`, and the browser check, `tests/browser/narrow.mjs`, which loads a page at each width, resizes it across 48em both ways, with the focus in the tree too, and presses the button and Escape.
    - **On a narrow window** the tree starts hidden on every page. Pressing the button shows the tree above the content, in the same order for the keyboard as on the screen, and pressing it again hides it. Escape, pressed inside the tree, hides it and moves the focus to the button.
    - **Both controls are in the shell**, as rule 241 describes, and the stylesheet shows the one that fits the window's width.
    - **Resizing the window across 48em** switches between the two at once, in both directions. A window made narrow starts with the tree hidden, and a window made wide shows it as the checkbox says. When a resize hides the tree while the keyboard focus is inside it, or hides the checkbox or the button while the focus is on it, the focus moves to the control the resize shows, the button on a narrow window and the checkbox on a wide one ([#111](https://github.com/marlon-sousa/gherkin-glass/issues/111)).
88. The shell is written with the checkbox checked and the tree shown when `show_tree` is `true`, its default, and with the checkbox unchecked and the tree hidden when it is `false`, as the descriptor's starting states say (rule 252). When a page is drawn, the reader's remembered choice wins over the configured state. The browser remembers the choice whenever the reader checks or unchecks the box, once for the whole site and not page by page, kept under the address of the site's root folder, so that two sites on one host keep their own. A browser that keeps nothing gets the same pages, which remember nothing. The button's state is never remembered, and never changes the choice the checkbox keeps. Fixtures: `tests/fixtures/pages`, built once with each setting, and the script's own tests, `script/test/policies/tree_state.test.ts` and `script/test/services/folder_tree.test.ts`.

### What it holds

89. The tree is a navigation landmark named "Folder tree", holding a tree, in WAI-ARIA's sense, named the same, which the script builds from the descriptor and the objects of the page's shell, as [The site's data](#the-sites-data) describes. Every item of the tree is a link, and the items are those listed below, in this order. In a feature's item, and in the items inside it, the feature text, each name in a `<bdi>` of its own as rule 43 isolates it, has the `lang` of the feature's page, as rule 42 gives it, and the tree's own words have none of their own. Fixtures: `tests/fixtures/pages`, with its drawn pages, and the script's own tests, `script/test/adapters/dom_tree.test.ts`.
    - **The home page**, whose text is the site's title, as rule 81 gives it, with nothing inside it.
    - **Then the input folder's subfolders and its features**, in the order of rule 83: the subfolders first, each linked to its page with its name as its text, and then the features, each linked to its page with the feature's heading, as rule 43 makes it, as its text.
    - **Inside a folder's item**, its own subfolders and features, in the same way and the same order.
    - **Inside a feature's item**, its page's contents, as rule 46 lists them: its rules, its scenarios and the group of its scenarios outside every rule, in the order of the file, each linked to the block's address on its page, as rule 235 makes it, or to `outside_rules` for the group, with the block's heading as its text, and the scenarios of a rule or of the group inside its item.
90. When a page is drawn, the item of the current page is marked with `aria-current="page"`, and it and every item it is inside are expanded. Every other item is collapsed, unless the reader expanded it before: the browser remembers each item's state whenever the reader expands or collapses it, once for the whole site, kept by the item's address, as rule 88 keeps the choice to show the tree. A remembered state never collapses an item the current page is inside. Fixtures: the script's own tests, `script/test/adapters/dom_tree.test.ts`, `script/test/policies/tree_state.test.ts` and `script/test/services/folder_tree.test.ts`.
91. The tree is one stop of the Tab key, on the current page's item, or on the first item when the current page has none. Its keys are those of the WAI-ARIA example. Fixtures: the script's own tests, `script/test/adapters/dom_tree.test.ts`, and the browser check, which presses Down and Up in the tree of every page that shows one.
    - **Down and Up** move to the next or the previous item that is not inside a collapsed item.
    - **Right** expands a collapsed item, and on an expanded item moves to the first item inside it. **Left** collapses an expanded item, and on any other moves to the item it is inside, if there is one.
    - **Home** and **End** move to the first and the last item that is not inside a collapsed item.
    - **Enter** and **Space** follow the item's link.
    - **A letter or digit** moves to the next item whose text starts with it, ignoring case, among those not inside a collapsed item, from the first again after the last.
    - **`*`** expands every item at the same level as the focused one, inside the same item.
92. Pressing an item's marker, the sign before its text that says whether it is expanded, expands or collapses it; pressing anywhere else on the item follows its link. An item with nothing inside it has no marker. Fixtures: the script's own tests, `script/test/adapters/dom_tree.test.ts`.
93. The reader can expand any of them where it is.

## Tags

Tags are how a suite is organised: by area, by ticket, by what a scenario needs. The site has a page for every tag, listing the scenarios that carry it, so that "what checks this?" is answered in one page, and an index of every tag.

A tag page's address is part of what is promised, like an anchor: changing how it is made is a major version ([CONTRIBUTING.md](../CONTRIBUTING.md), "Releases").

### The tag pages and their addresses

100. Every tag written in the input, on a feature, a rule, a scenario, a scenario outline or an examples block, has a page of the site, named `tags/<name>`, at the address `#tags/<name>`, as [Addresses](#addresses), rule 237, describes. Tags are told apart by their exact text, so `@Slow` and `@slow` are two tags. The name is made from the tag without its `@` by rules 27 to 29, so `@needs:db` is `needs-db`; a tag that leaves nothing, such as `@🚀`, takes `tag` instead. Taking the tags in the order of rule 102, each takes its name, or, when an earlier tag already has it, the first of that name followed by `-2`, `-3` and so on that is free. So `@Slow` is `slow` and `@slow` is `slow-2`, and `@index` is `index`, since the index of tags is `#tags/`. The names are worked out by ghg and written in the descriptor, as rule 252 describes. A tag page keeps its address as long as its tag, and the tags before it in that order whose names are its name or its name followed by `-` and a number, stay as they are. Fixture: `tests/fixtures/tags`.
101. The index of every tag is the page `tags/`, at the address `#tags/`. The pages whose names start with `tags/` are only the tag pages and their index: a feature file whose page would start with it, as rule 36 names its page, compared exactly as rule 37 compares names, stops the build, whether or not a tag page has its name. Each such file is a problem reported with those of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as `<path>: has its page, <page>, in the folder tags, which holds the tag pages.` Fixture: `tests/fixtures/tags-folder`.
102. The index's title and its only `h1` read `Tags`. Under the `h1` is a list of every tag, ordered by its text lower-cased, then, for tags that lower-case alike, by its text as written, each compared by its character codes, as rule 15 compares names. Each item is a link to the tag's page, whose text is the tag as written with its `@`, followed by a comma, a space and how many scenarios carry it, as rule 103 counts them, such as `@slow, 3 scenarios`, `@billing, one scenario` or `@draft, no scenarios`. When no tag is written in the input, the list is replaced by the sentence `No feature file has a tag.` Fixtures: `tests/fixtures/tags` and `tests/fixtures/pages`, which has tags, and `tests/fixtures/configuration/default`, which has none.
103. A scenario carries a tag when the tag is written on the scenario itself, on one of its examples blocks, on its rule, or on its feature. A scenario outline is one scenario, however many rows its examples have. Backgrounds carry no tags. Fixture: `tests/fixtures/tags`.
104. A tag's page has the title and the only `h1` `Tag @<tag>`, with the tag as written, such as `Tag @slow`. Under the `h1` comes its link to another site when it has one (rule 107). Then, for each feature file on which the tag is written anywhere, in the order of rule 15, comes an `h2` whose text is a link to the feature's page, reading the page's title, as rule 43 makes it, such as `Feature: Refunds, billing/refunds.feature`. Under it is a list of the feature's scenarios that carry the tag, in the order of the file, each a link to the scenario's anchor on the feature's page, reading the scenario's heading, as rule 43 makes it. A scenario that carries the tag only through its examples, its rule or its feature, and not itself, is followed by a comma, a space and `through its examples`, `through its rule` or `through its feature`, the first of those three that has the tag. A feature on which the tag is written but none of whose scenarios carries it, such as a feature with no scenarios, has under its `h2` the sentence `None of its scenarios carries the tag.` in place of the list. Fixture: `tests/fixtures/tags`.
105. The index and the tag pages are written in English, the language of gherkin-glass's own text, and have the `lang` `en`. Each starts as every page does, with the skip link, the folder tree's checkbox and button, the folder tree and the breadcrumb of rules 85 and 86. The index's breadcrumb has a link to the home page, then one to itself whose text is `Tags`, and a tag page's has a link to the home page, then one to the index whose text is `Tags`, then one to itself whose text is its `h1`'s. The home page has, after its totals (rule 82) and before its folders, a paragraph holding a link to the index whose text is `Tags`, even when no tag is written in the input. In each link whose text is a feature's heading, the `h2` and the scenarios of rule 104, the feature text, each name in a `<bdi>` of its own as rule 43 isolates it, has the `lang` of its feature's page, as rule 42 makes it, when that is not `en`, and gherkin-glass's own words around it have none of their own. Every tag shown on a feature's page, as rule 45 lists it, is a link to its tag's page, at its address, as rule 237 makes it, encoded as rule 238 says. Fixtures: `tests/fixtures/tags` and `tests/fixtures/pages`.

### Links to other sites

106. The configuration's `tag_links` lists patterns that link tags to other sites, such as an issue tracker. Each is a table written `[[tag_links]]`, with three keys, all needed, all text:
    - `pattern`, a regular expression in the syntax of the [`regex`](https://docs.rs/regex/1/regex/#syntax) crate, matched against the whole tag, with its `@`, such as `@issue-(\d+)`;
    - `address`, the address the tag links to, such as `https://github.com/owner/repo/issues/$1`;
    - `text`, the link's text, such as `Issue $1 on GitHub`, so that a screen reader does not hear two links in a row that sound the same.

    In the address and the text, `$1`, `${1}`, `$name` and `${name}` are replaced by what the pattern's group of that number or name matched, as the `regex` crate's replacement syntax says, and `$$` is a `$`. A `$` that names no group, such as one before a space or at the end, stays as written. In TOML, a pattern is best written between single quotes, as `'@issue-(\d+)'`, where a `\` is kept as written. Fixture: `tests/fixtures/tags`.
107. A tag that a pattern matches has a second link beside its link to its tag page, everywhere a feature's page shows it, and under the `h1` of its tag page: the first matching pattern's, in the order of the file. Its address is the pattern's `address`, with each group's text percent-encoded as rule 47 encodes a path, and its text is the pattern's `text`, with each group's text as matched. The address is used as it comes out, so a relative one would be relative to the page's shell: it is meant to be a whole address, such as one starting with `https://`. A tag no pattern matches has no such link, and neither has one whose link comes out with an empty address, or with a text that is empty or only spaces, as `$1` does when its group matched nothing: the first matching pattern decides, and no later pattern is tried. Fixture: `tests/fixtures/tags`, whose `@later` matches a pattern whose text comes out empty.
108. A mistake in `tag_links` stops the run, as rule 26 describes, reported with that rule's problems, sorted with them by line. Every mistake of every table is reported, a table's pattern and its address and text being checked whenever they are given as text, even when another of its keys is missing or mistaken. `tag_links` given as anything but a list of tables reads `tag_links must be a list of tables, each written [[tag_links]].`, at its line. A table that lacks a key reads `tag_links.<key> is missing.`, at the line of its `[[tag_links]]`, once for each key it lacks. A pattern that is not a regular expression reads `tag_links.pattern is not a regular expression: <reason>`, where the reason is the short description the `regex` crate's parser, `regex-syntax`, gives, such as `unclosed group`, at the pattern's line, and one too large to build within the `regex` crate's default size limit, such as `@(a{1000}){1000}`, reads `tag_links.pattern is too large a regular expression.` An address or a text that names a group the pattern does not have, the first such group in it, such as `$2` for a pattern with one group, or `$1a`, which names the group `1a`, reads `tag_links.address names the group <group>, which the pattern does not have.`, or the same with `tag_links.text`, at its line. A key a table may not have, a key given something other than text, and an empty text read as rule 26 says, with the key named as `tag_links.<key>`. Fixture: `tests/fixtures/configuration/mistaken-tags`.

## Highlighting and themes

Parts of every step are highlighted, so that steps are quicker to scan, and a reader picks the theme a page is shown in. Colour never carries meaning alone: highlighting only colours text that already says what it is, and every theme reaches the contrast below.

### Highlighting

109. In every step, of a background, a scenario or a scenario outline, at the top of a feature or inside a rule, the keyword is highlighted as written, such as `Given`, `And`, `*` or `Dado`, and so are the quoted parameters, the placeholders and the numbers of the text after it, found as rules 111 to 113 say. Nothing else is highlighted: not data tables, doc strings, names or descriptions. On a page, each highlighted part is an element of its own around its text, a `span` whose class is `ghg-keyword`, `ghg-parameter`, `ghg-number` or `ghg-placeholder`, and a placeholder inside a parameter is inside the parameter's. ghg finds the parts, as rules 110 to 113 say, and writes them with each step in its object, as rule 250 describes, so that the script only draws them. Fixture: `tests/fixtures/highlighting`, with its store committed beside it in `expected` and its drawn pages in `drawn`.
110. Highlighting never adds, removes or changes a character, so a step reads the same with it and without it, to the eye and to a screen reader. Each highlighted part is told apart by its own text: the keyword begins the step, a parameter keeps its quotes, a placeholder its angle brackets, and a number is made of digits. Fixture: `tests/fixtures/highlighting`.
111. A quoted parameter runs from a double quote, `"`, to the next double quote of the step, both included, such as `"hello"` or `""`. A double quote just after a backslash, `\"`, neither opens nor closes a parameter, whatever comes before the backslash, and a double quote with no other after it is plain text. Single quotes make no parameter, since they are also apostrophes, as in `the user's 'name'`. Inside a parameter, placeholders are highlighted, and numbers are not. Fixture: `tests/fixtures/highlighting`.
112. A placeholder is `<`, a name, and `>`, where the name is not empty and is exactly one of the header cells of the examples tables of the step's own scenario outline, such as `<amount>` in an outline whose examples have an `amount` column. Anywhere else, in a step of a background or of a scenario without examples, or with a name that is no column's, `<` and `>` are plain text. Fixture: `tests/fixtures/highlighting`.
113. A word is a run of letters, digits, combining marks and `_`, where letters and digits are the characters Unicode gives the Alphabetic or Numeric property, with any single point or comma between two of them. A word made only of the digits 0 to 9, and points and commas between them, is a number, such as `10`, `3.5` or `1.000,50`; any other word is plain text, such as `R2D2`, `3rd`, `v1.2`, `2.x`, `x_1` or `٣`, so no number is found inside a word. A `-` just before a number is part of it, as in `-3`, unless a word ends just before the `-`, as in `2026-11-10` or `item-4`, where only the digits after it are a number. A point or comma after a number's last digit is not part of it. Fixture: `tests/fixtures/highlighting`.

### Themes

114. Every page can be shown in a light theme and in a dark theme. Every page, a feature's, a folder's, a tag's, the step sentences' or the search results', has a group of three radio buttons named Theme, with the other reader options at its top, after the folder tree's checkbox and button of rule 87: System, the default, which follows the theme the reader's system prefers, as the browser reports it, and changes with it while the page is open; Light; and Dark. The shell and the versions page are written with System chosen; the script shows the reader's choice once it runs. Fixtures: `tests/fixtures/pages`, and `script/test/services/theme_switching.test.ts`.
115. The browser remembers the choice, as it does the other reader options, for every page served from the same origin, the same scheme, host and port, and every such page then opens in it, as does a page the browser shows again from its cache, going back or forward. Sites that share an origin, such as the GitHub Pages sites of one owner, share the choice. When the browser keeps nothing, as some private windows do, the choice holds for the page it was made on. Fixture: `script/test/services/theme_switching.test.ts`.
116. A page is drawn in the chosen theme from the start, never first in another: a script in the head of the shell and of the versions page, which runs before the page is drawn, applies the remembered choice, and the page's own script, which runs after, does the rest. Fixtures: `tests/fixtures/pages`, and `script/test/policies/theme_choice.test.ts`, which checks that the head reads the choice where the page's script keeps it.
117. In every theme, text and every highlighted part reach a contrast of at least 7:1 against every background they are written on, WCAG's AAA level, and lines that carry no text, such as borders, at least 3:1 against the background. Contrast is as WCAG 2.2 defines it. Each shell and the versions page hold their themes' colours, the accent colours of their build among them, in a `style` element in their head, so that no page is drawn before it has them. The browser check checks every page in each theme a reader can pick: axe-core checks the text, as rule 73 says, and the check itself checks the lines, every border of every part shown and the outline of a focused link, since axe-core has no rule for them. A line is measured as it is seen: a colour that is not opaque is blended over what is behind it, and what is behind it is the background of its own part, for a border, or of the parts around it, for an outline, blended over theirs down to the first one that is opaque. Fixtures: every fixture's pages, in the browser check, once it is built ([#2](https://github.com/marlon-sousa/gherkin-glass/issues/2)); `tests/fixtures/accessibility/failing`, which has a border, a translucent border and a focus outline with too little contrast; `tests/fixtures/pages`, for the `style` element of its shell.

### The accent colours

118. Each theme has an accent colour, for links and for the outline around what has the keyboard focus. Links are also underlined, so that colour is not all that tells them apart from the text around them. `accent_light` sets the light theme's, and `accent_dark` the dark theme's, each by default a colour that passes rule 119. Setting one leaves the other at its default. An accent colour is text: `#` and six or three hexadecimal digits, in capitals or small letters, such as `"#0b4f9c"` or `"#08c"`. Anything else stops the run, as rule 26 says, at the line of the value, reading `<key> must be a colour in hexadecimal, in quotes, such as "#0b4f9c".` Fixtures: `tests/fixtures/configuration/accents`, `tests/fixtures/highlighting`, whose pages hold the accent colours it sets, and `tests/fixtures/configuration/not-colour`.
119. gherkin-glass computes the contrast of each accent colour against each background of its own theme, as rule 117 does. An accent that reaches less than 7:1 against any of them stops the run, as rule 26 says, at the line of its value, reading `<key> is <colour>, which reaches only <ratio>:1 against the <theme> theme's background <background>. It needs at least 7:1.`, where the theme is `light` or `dark`, the background is the one of that theme the colour contrasts least with, both colours are written as `#` and six small hexadecimal digits, and the ratio is rounded down to two decimals, so that 6.999 reads `6.99`. Fixture: `tests/fixtures/configuration/faint-accents`.

## Versions

A site can hold several versions of the same suite, each with a folder of its own, such as `v1.2.0/` and `main/`, with a page listing them, so that a reader reads the version they use, and a link to a version never changes under them. In gherkin-glass 2.0 the versions share one store of the site's data, so that a feature file the same in several versions is stored once, as [The site's data](#the-sites-data) describes, and a version is added and removed with commands of its own ([#173](https://github.com/marlon-sousa/gherkin-glass/issues/173)). The configuration file's `version_name` and the option `--version-name` of gherkin-glass 1 are gone.

### Adding a version

120. `ghg version add <name>` reads the input as `ghg build` does, with the same options and the same configuration file, as rules 21 to 26 and 232 to 234 describe, and adds to the output folder the version of that name, built from it. `ghg version` alone, or with a subcommand other than `add` and `remove`, is a mistake on the command line, as rule 19 describes, and so is `ghg version add` without a name. One run adds one version, from its one input folder. gherkin-glass does not read git: to add several versions, check each out into a folder of its own, such as with one checkout step per version in a workflow, and run ghg once for each. Fixture: `tests/fixtures/versions`.
121. The name of a version, and of a preview, as [A preview](#a-preview) describes, is one folder name. It is made of the letters `a` to `z` and `A` to `Z`, the digits `0` to `9`, and the characters `.`, `-`, `_` and `+`; it starts with a letter or a digit, and does not end with `.`. It is not `assets`, `data` or `index.html`, which the versions page and the site's data use, `ghg-site.json`, the output folder's marker, or `previews`, the folder of the previews, nor a name Windows keeps for a device, `con`, `prn`, `aux`, `nul`, `com1` to `com9` or `lpt1` to `lpt9`, alone or before a dot, such as `nul.txt`, all of them whatever their capitals. A name that cannot be one is a mistake on the command line, as rule 19 describes, which reads `<name> cannot be the name of a version or a preview. Such a name is made of letters, digits, dots, hyphens, underscores and plus signs, starts with a letter or a digit, does not end with a dot, and is not assets, data, index.html, ghg-site.json, previews, or a name Windows keeps for a device, such as con or nul.` Names of versions that differ only in their capitals, such as `main` and `Main`, cannot both be in one output folder, since a file system that does not tell capitals apart would put them in the same folder, as rule 124 describes, and the same holds for the names of previews. Fixture: `tests/fixtures/versions`.
122. A version is written as its shell, `<output>/<name>/index.html`, as [How a page is drawn](#how-a-page-is-drawn), rule 241, describes, its descriptor, `data/versions/<name>.json`, and the objects it names that the store does not hold yet, as [The site's data](#the-sites-data) describes; with it, `ghg version add` writes again `data/versions.json`, `data/pages.json` and the versions page, writes the folder `assets/<ghg>/` of rule 39 when it is not there, and removes what no descriptor references any more, as rule 255 describes. Every link in a site is relative, so a version works wherever its output folder is served, under any path, with no base address to set. A marked output folder that holds versions is safe, as rule 38 requires, when it holds only what its marker lists and what the patterns of [What the output folder keeps](#what-the-output-folder-keeps) keep, as rule 227 describes. A version whose descriptor is in the store but whose folder is missing stops the run before the input is read, writes and deletes nothing, and reports `<output>/<name>: the site's data holds this version, but its folder is missing, so the output folder is left as it is.` The one exception is `ghg version remove` of that version itself, which goes ahead, as rule 257 describes. An output folder that is missing or empty is marked, and one that holds anything without a marker is refused, as rule 38 describes. Fixture: `tests/fixtures/versions`.

### A version that is already there

123. When the store already holds the version, `replace_existing_version` decides. When it is `true`, its default, the version's shell and descriptor are written again, and what no descriptor references any more is removed, as rule 255 describes, so that nothing of the earlier build of that version is left but what another version or a preview shares. Nothing is written or removed until the input has been read without a problem and the output folder checked again, right before the version is written, so that a build whose input has a problem leaves the earlier one as it was, and the files are written in the order rule 38 gives. When it is `false`, the run stops before the input is read, writes nothing, and reports `<folder>: the version <name> is already built, and replace_existing_version is false.`, as rule 20 describes. A version the store does not hold is added. Fixture: `tests/fixtures/versions`.
124. `ghg version add` into an output folder that holds a site without versions, built with `ghg build`, stops before the input is read, writes nothing, and reports `<output>: a site without versions is built here, so build it with ghg build, or add versions into another folder.` A version whose name differs from one the store holds only in its capitals stops the run the same way, on every system, whatever `replace_existing_version` says, with `<folder>: the output folder holds a version whose name differs from this one only in its capitals, which some systems would put in the same folder, so it is left as it is.` A preview whose name differs from one the store holds only in its capitals stops `ghg preview add` the same way, with `<folder>: the output folder holds a preview whose name differs from this one only in its capitals, which some systems would put in the same folder, so it is left as it is.` Fixtures: `tests/fixtures/versions`, and `tests/fixtures/only` for a preview.
125. In these reports, `<folder>` is the version's folder: the output folder's path, as rule 16 shows the input folder's, then `/` on every system, then the version's name; for a preview, it is the output folder's path, then `/previews/` and the preview's name. An output folder that cannot be looked into reads `<output>: cannot be read: <reason>`, a file that cannot be removed `<path>: cannot be written: <reason>`, and a marker that cannot be written `<output>: cannot be written: <reason>`, where the reason is the operating system's words. Fixture: `tests/fixtures/versions`.

### Removing a version

257. `ghg version remove <name>` takes `--config`, `--output`, `--keep-in-output` and `--message-format`, which mean what they mean for `ghg build`, and reads nothing of the input. It checks the output folder as rule 38 describes, except that the version being removed may have lost its folder: the stop of rule 122 for a version whose descriptor is in the store but whose folder is missing does not apply to it, so that removing it is the cleanup that state asks for, while another version in that state still stops the run. It then removes the version's folder and its descriptor, writes again `data/versions.json`, `data/pages.json` and the versions page, and removes what no descriptor references any more, as rule 255 describes, so that the objects only that version had go with it. The descriptor is removed before the folder, and the marker written first, as rule 38 says, so that a command stopped half way leaves a folder no descriptor names, which the marker still lists and the next command that writes the output folder removes, as rule 255 describes. Removing the last version removes the versions page, `data/versions.json` and `data/pages.json` too. When the output folder holds no version of that name, or is missing, it writes and removes nothing, prints `<output>: holds no version <name>, so nothing was removed.` to standard error, and exits with status 0, so that a workflow may remove a version that may not be there. Without a name, it is a mistake on the command line, as rule 19 describes. It exits with status 0 when it removed the version, and with status 1 when the output folder stops it, as rule 20 describes. Fixture: `tests/fixtures/versions`, whose expected output folder after removing a version is committed beside the one before.

### The versions page

126. Every `ghg version add` and `ghg version remove` writes the versions page again, `index.html` in the output folder, linking the stylesheet, the script and the icon of `assets/<ghg>/` of the ghg that writes it, as rule 39 describes. ## Step sentences

A page lists every distinct step sentence in the suite, grouped by keyword and sorted, each with how often it is used and links to the steps that use it, so that the suite's vocabulary can be read at a glance and near-duplicates found.

### What a sentence is

133. A step's sentence is its text after the keyword, without its doc string or data table, in Unicode NFC. Two steps have the same sentence when their texts are the same once every slot is replaced as rules 134 and 135 say; letters, spaces and everything else are compared exactly, so `the user logs in` and `The user logs in` are two sentences. Fixture: `tests/fixtures/step-sentences`.
134. A quoted value is a slot: a `"`, the text up to the next `"` on the step, and that `"`. In the sentence, a slot is shown as `"…"`, so `the user "ana" logs in` and `the user "bia" logs in` are one sentence, `the user "…" logs in`. An empty value, `""`, is a slot too. A `"` just after a backslash, `\"`, neither opens nor closes a slot, and a `"` with no other after it is text, as rule 111 says of highlighting. Other quotation marks, such as `'`, `“` and `”`, are text, so that apostrophes stay words. Fixture: `tests/fixtures/step-sentences`.
135. In a step of a scenario outline, a placeholder is a slot too, shown as `"…"` like a quoted value: a `<`, the name of a column of the outline's examples, which is not empty, and a `>`, the name ending at the first `>` after the `<`. So a step with `<name>` where another has a quoted value, or another placeholder, at the same place is the same sentence. Slots are found from the start of the step, and where a quoted value and a placeholder overlap, the one that opens first is the slot, so a placeholder inside a quoted value, as in `"<name>"`, is part of that one slot. A placeholder matches its column when both are the same in NFC. Outside an outline, and where the name is not one of its columns, `<` and `>` are text. Fixture: `tests/fixtures/step-sentences`.
136. Nothing else is a slot: numbers are text, so `I withdraw 10` and `I withdraw 20` are two sentences. Fixture: `tests/fixtures/step-sentences`.

### How the sentences are grouped and sorted

137. Sentences are grouped by the kind of step: Given, When or Then, in that order, whatever the language of the file. A step written with `And` or `But`, or their equivalents in the file's language, is of the kind of the step before it in its block, and of the kind Given when it is the first of its block. A step written with `*` is a Given step, as the `gherkin` crate reads it, wherever it is, so an `And` or `But` step after it is a Given step too. The same text in two kinds is two sentences, one in each group. A group with no sentences is not shown. Fixture: `tests/fixtures/step-sentences`.
138. Within a group, sentences are sorted by their text lower-cased, and, between two that lower-case the same, by their character codes, so capital letters come first. The order is the same on every run. ghg works it out and writes it in the descriptor, as rule 252 describes, so that the script sorts nothing. Fixture: `tests/fixtures/step-sentences`.

### Where each sentence is used

139. Each sentence says how many times it is used, counting every step that has it, even two in the same scenario. Fixture: `tests/fixtures/step-sentences`.
140. Each sentence links to every step that uses it, through the anchor ([Anchors](#anchors)) of the block the step is in: its scenario, scenario outline, or background. A step of a scenario outline links to the outline, not to the scenarios its rows produce. A background's step is used once, by the background, and links to the background's own heading, whether the checkbox of [Backgrounds](#backgrounds), rule 98, is checked or not: the copies of its steps inside each scenario are not counted again. The links are in the order of the features' paths, sorted as rule 15 describes, and in file order within a feature. Fixtures: `tests/fixtures/step-sentences`, and `tests/fixtures/backgrounds`, whose two sites, written with the box checked and unchecked, list the same sentences.
141. Beside each link are the step's values, the text of each of its slots exactly as written, not normalised, quotes and angle brackets included, such as `"ana"` or `<name>`, in the order they appear in the step. Fixture: `tests/fixtures/step-sentences`.

### The page

142. The site has one page of step sentences, `steps`, at the address `#steps`, as rule 237 describes, whether or not any feature has a step. A feature file whose page would also be `steps`, as rule 36 names it, such as `steps.feature` at the input folder's root, stops the build, the names compared exactly as rule 37 compares them, so `Steps.feature` is a page of its own. Like a folder's page, it has the skip link, the checkbox of the folder tree, the Theme group, the tree and the breadcrumb, as rules 85 to 93 and 114 to 117 describe, its breadcrumb holding the link to the home page and then one to the page itself, which reads `Step sentences`; the folder tree has no item for it, since it lists folders and features. A sentence whose first use is in a file whose language, as rule 42 writes it, is not `en` has that language as its heading's `lang`. Fixture: `tests/fixtures/step-sentences`.

Each item is a link to the use's block on its feature's page, at the block's address, as rule 235 makes it and rule 238 encodes it, such as `#saque%20em%20conta#saque`. ## Search

Every page but the versions page has a search box over the names, steps, tags and examples of the site's features, rules, backgrounds, scenarios and examples blocks. The pages' script makes the documents to search from the site's data, the descriptor of the page's shell and the objects it names, the first time the search box is used, and builds the index from them in the browser with [MiniSearch](https://www.npmjs.com/package/minisearch). The search box goes straight to one result, and its link to the page of search results lists every result, grouped by feature, at an address that holds the words searched for ([#122](https://github.com/marlon-sousa/gherkin-glass/issues/122)).

### The documents

147. The documents are a list the script makes, with one entry for each feature, each rule, each background, each scenario, scenario outlines included, and each examples block of the shell's descriptor. The backgrounds a scenario shows inside it (rule 95) and the scenarios an outline produces from its rows have no entry of their own. The entries follow the order of the descriptor's features, which is that of rule 15, and within a file, the feature comes first, then its blocks in file order: its background, its scenarios and its rules, each rule followed by its background and its scenarios, and each outline by its examples blocks. Fixture: `tests/fixtures/search`, checked by `script/test/policies/search_documents.test.ts`.
148. Each entry holds these parts, each taken from the objects as rules 248 to 250 describe:

    | Member | Holds |
    | --- | --- |
    | `kind` | `feature`, `rule`, `background`, `scenario`, `scenario-outline` or `examples`, the block's kind in English, which the script puts into words from the interface catalogue. |
    | `name` | The block's name as written, or empty text for a block with no name. |
    | `feature` | The name of the feature whose page the entry is on, empty text for a feature with no name, or `null` for the feature's own entry. |
    | `rule` | The name of the rule the background, the scenario or the examples block is in, or empty text for a rule with no name. It is `null` for a rule, a feature, and a block outside any rule. |
    | `outline` | The name of the outline an examples block is in, or empty text for an outline with no name. It is `null` for every other entry. |
    | `place` | The place of an examples block among its outline's examples blocks, counted from 1, as rule 43 numbers them. It is `null` for every other entry. |
    | `steps` | A list of the text of each step of a background or a scenario, as written, without its keyword, its data table or its doc string, so `<amount>` in an outline stays as it is. It is an empty list for a feature, a rule and an examples block, whose backgrounds' steps are in the backgrounds' own entries. |
    | `tags` | A list of the block's own tags, each with its `@`, in file order. An outline's entry adds the tags of its examples blocks, in file order, each tag once. Tags a block inherits from the blocks around it are not repeated, and a background's list is empty, since a background has no tags. |
    | `cells` | A list of the text of each cell of an examples block's table, row by row from its header, each as rule 45 reads it. It is an empty list for an examples block with no table, and for every other entry. |
    | `page` | The name of the entry's page, as rule 36 makes it. It is not percent-encoded: the script encodes it when it makes the link, as rule 238 says. |
    | `anchor` | The block's anchor ([Anchors](#anchors)), or empty text for a feature, which is its page. No two entries have the same page and anchor. |

    Fixture: `tests/fixtures/search`, checked by `script/test/policies/search_documents.test.ts`.

## Releases

gherkin-glass is downloaded and run, with nothing else to install. A release is made by the release workflow, `.github/workflows/release.yml`, when a maintainer pushes a version's tag, and holds an archive for each platform, a checksums file, notes, and, for a version without a pre-release part or a release candidate, the crate on crates.io (rule 167). The names of the archives and what they hold are what [gherkin-glass-action](https://github.com/marlon-sousa/gherkin-glass-action) and `cargo binstall` rely on, so they are part of what is promised, like the command line.

The workflow's own checks test these rules: on every tag before anything is published, and on every pull request that changes how releases are made, which builds, packs and checks every archive without publishing anything. Their scripts are in `.github/release/`.

### What makes a release

160. Pushing a tag `v<version>` releases that version, and nothing else does. The tag is refused, and nothing is published, unless the version is the one `Cargo.toml` gives the crate, the tagged commit is on `main`, and `CHANGELOG.md` has notes for the version, under the heading `## [<version>]`. Every reason a tag is refused is reported, not only the first. Fixture: `tests/fixtures/release/changelogs`, checked by `.github/release/test-gate.sh`.

### The archives

161. A release has one archive for each of six targets, all 64-bit, named `ghg-<tag>-<target>.tar.gz`, or `ghg-<tag>-<target>.zip` for Windows, such as `ghg-v0.1.0-x86_64-unknown-linux-musl.tar.gz`, where the tag is the one pushed and the target is the Rust target the binaries were built for:

    | Target | Platform | Archive |
    | --- | --- | --- |
    | `x86_64-unknown-linux-musl` | Linux on x86-64 | `.tar.gz` |
    | `aarch64-unknown-linux-musl` | Linux on ARM64 | `.tar.gz` |
    | `x86_64-apple-darwin` | macOS on Intel | `.tar.gz` |
    | `aarch64-apple-darwin` | macOS on Apple silicon | `.tar.gz` |
    | `x86_64-pc-windows-msvc` | Windows on x86-64 | `.zip` |
    | `aarch64-pc-windows-msvc` | Windows on ARM64 | `.zip` |

    Checked by `.github/release/check-archive.sh` and `.github/release/check-binstall.sh` on every build, and the first by `.github/release/test-check-archive.sh` with archives it makes.
162. Each archive holds, at its root and not inside a folder, every binary the crate declares, `ghg` and `cargo-ghg`, ending in `.exe` on Windows, and the licence files `LICENSE-MIT` and `LICENSE-APACHE`, and nothing else. Checked by `.github/release/check-archive.sh` on every build, and by `.github/release/test-check-archive.sh` with archives it makes.
163. A release has one checksums file, `SHA256SUMS`, with one line for each archive, in the form `sha256sum` writes and checks: the archive's SHA-256 in lower-case hexadecimal, two spaces, and the archive's name. Checked by the release workflow, which writes it and checks every archive against it with `sha256sum --check` before attaching them.
164. Each binary needs nothing installed beyond what every system of its kind has. On Linux it is statically linked, with musl, so it runs on any distribution. On Windows it links the C runtime into itself, so it needs neither the Visual C++ runtime nor the Universal C Runtime installed. On macOS, which allows no fully static binary, it loads only the libraries of macOS itself, under `/usr/lib` and `/System/Library`. Checked by `.github/release/check-binary.sh`, which also runs `ghg --version`, and checks it prints `ghg` and the version, wherever the machine running the check can run the binary: every target but macOS on Intel, which is built on Apple silicon.

### The notes and the crate

165. The notes of a release are the section of `CHANGELOG.md` for its version. That section is written before the tag, from what [git-cliff](https://git-cliff.org/) prints with the template in `cliff.toml`: the heading `## [<version>]`, then the changelog entries that the commits since the previous tag carry as trailers, under `### Added`, `### Changed`, `### Fixed` and `### Removed`, in that order and each only when it has entries, one list item per entry, oldest commit first. A commit whose subject does not follow [Conventional Commits](https://www.conventionalcommits.org/), such as a merge commit, adds nothing, nor does a trailer of any other kind, such as `Refs #N` or `Changelog: none`. Fixture: `tests/fixtures/release`, checked by `.github/release/test-notes.sh`.
166. A version with a pre-release part, such as `0.2.0-rc.1`, is released on GitHub as a pre-release. Checked by the tests of the `create-release` action of [itinera-dev/actions](https://github.com/itinera-dev/actions), which makes the release.
167. A version without a pre-release part, such as `0.2.0`, and a release candidate, whose pre-release part starts with the identifier `rc`, such as `0.2.0-rc.1`, are published to crates.io as the crate at the same version, before the GitHub release is made, and only after every archive has been built and checked and every check of `.github/workflows/rust.yml` passes on the tagged commit: the formatting, the lints, the tests, the script's checks and the browser check. A version already on crates.io is not published again, so a release whose GitHub release failed can be run again. The one exception is the first version published to crates.io, which a maintainer may have to publish by hand before its tag is pushed, as [CONTRIBUTING.md](../CONTRIBUTING.md), "Releases", says. Any other pre-release, such as an alpha, `0.1.0-alpha.1`, or a beta, `0.1.0-beta.1`, is not published to crates.io ([#101](https://github.com/marlon-sousa/gherkin-glass/issues/101)); it is released on GitHub all the same, once the archives and the checks have passed, with its archives, its checksums and its version of the project's site, and is installed from its archives or through gherkin-glass-action, by naming it in its input `ghg-version`, never with `cargo install gherkin-glass` or `cargo binstall gherkin-glass`, which read crates.io. Which versions go to crates.io is checked by `.github/release/test-crates-io.sh`, with the tags it holds, which the release workflow runs; the publishing itself is checked by publishing: a pull request that changes how releases are made packs the crate without publishing it.
168. `cargo binstall gherkin-glass` downloads the release archive for the machine's target, as `[package.metadata.binstall]` in `Cargo.toml` names it, and installs both binaries from it. Checked by `.github/release/check-binstall.sh`.

## The front page

188. The template holds exactly one marker, outside any list, quote or table. A template with none stops the build with `<file>: has no marker <!-- ghg:contents --> on a line of its own, where ghg puts its part of the front page.`, the second marker with `<file>:<line>: holds a second marker <!-- ghg:contents -->, but ghg puts its part of the front page in one place only.`, and a marker inside a list, a quote or a table, or on a line with other text, with `<file>:<line>: the marker <!-- ghg:contents --> must be on a line of its own, outside any list, quote or table.` Fixture: `tests/fixtures/front-page`.

Raw HTML, any other HTML in the template, stops the build with `<file>:<line>: raw HTML cannot be written in a front page; only the marker <!-- ghg:contents --> and other comments can.` Every such problem stops the build as rule 186 says, before anything is cleared or written, and the first in the template is the one reported. ## A site of only some feature files

A reviewer of a pull request that changes feature files, such as one that proposes a new conformance tier, wants to read the feature files it changes or adds as pages, not as a diff. So ghg builds a site of a list of feature files alone, which a command such as `git diff --name-only` prints, decided in issue [#128](https://github.com/marlon-sousa/gherkin-glass/issues/128). ghg knows nothing of git: it reads a list of paths.

### The list

204. `--only <file>`, an option of `ghg build`, `ghg serve`, `ghg version add` and `ghg preview add`, builds the site from the feature files the list in that file names, alone. `--only -` reads the list from standard input instead, so that `git diff --name-only origin/main...HEAD | ghg build --only -` builds a site of the files a branch changes. The list is text, one path on each line, each as written, relative to the current folder, as every path on the command line is, or absolute; a line feed or a carriage return and a line feed ends a line, and an empty line, or one of white space only, names nothing. A list that cannot be read, such as a file that does not exist or standard input that is not UTF-8, stops the run before the input is read, with `<file>: cannot be read: <reason>`, the file as it was given, `-` for standard input, and the reason in the operating system's words, as rule 20 describes. A list that names no path, empty or of empty or blank lines only, such as standard input with nothing on it, reads no feature file, so nothing is built, as [A build with no feature file](#a-build-with-no-feature-file), rule 229, describes, and what ghg prints reads `<file>: names no path, so there is nothing to build.`; so does a list that names paths, none of them a feature file of the input, as rule 208 describes. `--only` with `ghg serve --no-build`, which builds nothing, is a mistake on the command line, as rule 19 describes, which reads `The options --only and --no-build cannot be used together.` The configuration file has no key for it, since the list changes with every run. Fixtures: `tests/fixtures/only`, with its `changed.txt`, given as a file and on standard input, and given with `--no-build`, and its `empty.txt`, of empty lines only, given as a file, and nothing on standard input.
205. A listed path names a file of the input when, made absolute from the current folder, with each `.` part left out and each `..` part taking away the part before it, it is inside the input folder made absolute the same way. Such a file is read when the input folder and its `.ghg-ignore` rules would read it, as rules 1 to 5 describe. Every other listed path is passed over without a problem, so that the list of every file a pull request changes needs no filter: a path that does not exist, such as that of a removed file, which leaves nothing to show; one the rules leave out, such as a file that is not a feature file or one in a folder a `.ghg-ignore` leaves out; a folder; and a path outside the input folder, such as `src/main.rs`. A listed file that is read but cannot be, such as a feature file with a syntax error, fails the build as rule 14 describes. git prints paths from the repository's root, so the list it prints names the right files when ghg runs from the root, where `ghg.toml` usually is; from a folder below it, `git diff --name-only --relative` prints them from there. git writes a path with a character outside ASCII in quotes and escapes unless its setting `core.quotePath` is `false`, as in `git -c core.quotePath=false diff --name-only`, and such a quoted line names no file. Fixtures: `tests/fixtures/only`, whose list names a feature file with `./` before it, a removed file, a file a `.ghg-ignore` leaves out, a file that is not a feature file, a folder and paths outside the input folder, and a list that names a feature file that cannot be parsed, given on standard input.

### The site

206. The site is built as if the files of rule 205 that are read were the only feature files of the input: only the folders on the way to one of them are looked into, so that nothing another folder or file holds is reported, such as a feature file that cannot be parsed, and its folder pages, its folder tree, its tag pages, its step sentences, its search documents and the pages that clash, as rules 37, 78, 101, 142 and 215 describe, are those of these files alone. Fixture: `tests/fixtures/only`, beside whose listed files are a file that is not Gherkin, a feature of a listed file's folder and a folder of features, none of them listed.
207. Every page of such a site, but the versions page, has as the first thing in its `main` a paragraph marked `role="note"` that reads `This site shows only the feature files given with --only.`, so that a reader does not take a feature that is not there for one that was removed. Fixture: `tests/fixtures/only`.
208. When none of the listed paths names a file that is read, nothing is built, as from an input with no feature file, as [A build with no feature file](#a-build-with-no-feature-file), rule 229, describes, and what ghg prints names the list: `<file>: names no feature file of the input, so no site was built.`, the file as it was given, `-` for standard input. Under `ghg serve --watch`, which builds such a site in memory, as rule 230 describes, its home page, after the links to the index of tags and to the step sentences (rule 146), reads `No feature file was given with --only.` Fixture: `tests/fixtures/only`, with `nothing.toml` and `nothing.txt`, which `tests/previewing_a_site.rs` serves with `--watch`, and the browser check, `tests/browser/accessibility.mjs`, checks in both colour schemes.

## What the output folder keeps

A host may need files of its own in the folder it serves, beside the site: GitHub Pages, deploying from a branch, runs Jekyll unless a `.nojekyll` file is at the root of what it serves, and with a custom domain it keeps a `CNAME` file there. So whoever runs ghg names what ghg leaves alone in its output folder, rather than ghg knowing any host's files, as issue [#156](https://github.com/marlon-sousa/gherkin-glass/issues/156) decided.

### The patterns

224. `--keep-in-output <pattern>`, an option of `ghg build`, `ghg serve` and the four commands of versions and previews, `ghg version add` and `remove` and `ghg preview add` and `remove`, names what ghg leaves alone in the output folder. It is given once for each pattern, such as `--keep-in-output .nojekyll --keep-in-output CNAME`, and is one of the two options that may be given more than once, with `--tag-link`, which rule 233 describes; a value is one pattern, never several joined, since a comma or a space may be part of a file's name. The configuration file's `keep_in_output` key takes a list of patterns, such as `keep_in_output = [".nojekyll", "CNAME"]`. Given on the command line, the patterns win over the key's, as rule 25 says, which are then not used. Fixture: `tests/fixtures/keep-in-output`.
225. Each pattern is written in the [gitignore syntax](https://git-scm.com/docs/gitignore#_pattern_format), as a rule of `.ghg-ignore` is (rule 3), and is matched against the paths inside the output folder, never against the input: `.nojekyll` names a file or a folder of that name anywhere in the output folder, `/CNAME` only the one at its root, `drafts/` only folders, and `*`, `?` and `**` match as in gitignore. What a pattern matches is kept, files and folders alike, and so is everything in a folder kept. When several patterns match a path, the last decides, so that a pattern starting with `!` keeps nothing, and leaves to ghg what an earlier pattern keeps, as in gitignore; what is in a folder kept stays kept whatever a later pattern says. A pattern that matches nothing is no problem, and nor is one that names nothing, such as one starting with `#`, which gitignore reads as a comment. Fixture: `tests/fixtures/keep-in-output`.
226. A pattern that is not valid in the gitignore syntax, such as `{draft`, stops the run before the input is read, with `<pattern> is not a pattern in the gitignore syntax: <reason>`, where the reason is the [`ignore`](https://crates.io/crates/ignore) crate's words. Given with `--keep-in-output`, it is a mistake on the command line, as rule 19 describes, and so is an empty pattern, such as `--keep-in-output=`. Given in `keep_in_output`, it is a problem of the configuration file, as rule 26 describes, at the line of the pattern; there, an empty pattern reads `keep_in_output must not be empty.`, and a value that is not a list of text, or a list holding anything but text, `keep_in_output must be a list of text, each in quotes.` Fixture: `tests/fixtures/keep-in-output`.

### What is kept

227. What a pattern keeps, ghg never writes, empties, moves or deletes, whether it builds a site without versions, adds or removes a version or a preview, or replaces an earlier one, as rules 38, 123 and 255 describe: what ghg removes is only what it wrote and nothing references any more, and what is kept stays as it was. It is not listed in the output folder's marker, ghg does not look into a folder kept, and it counts neither as something ghg did not write nor as something that makes the output folder not empty. So an output folder that holds only what is kept, such as a checkout of a `gh-pages` branch holding `.nojekyll` and `.git`, with `--keep-in-output .nojekyll --keep-in-output .git`, is marked as an empty one is, and a marked one that holds what is kept beside what ghg wrote is still safe. A folder ghg did not write that holds something kept is not itself something ghg did not write, though anything else in it, not kept, is. All of this holds for `ghg serve` as for `ghg build`; under `ghg serve --watch`, which neither checks nor writes the output folder, as rule 66 says, the patterns change nothing. Fixture: `tests/fixtures/keep-in-output`.
228. A pattern that keeps what ghg writes stops the run, which writes and deletes nothing. What ghg writes is the files of the site or the version being built, the marker, every file the marker lists, of an earlier build or of another version, and every folder that holds one of them, every version's folder among them, but not the output folder itself. A pattern keeps it when it matches it, or a folder it is in, whatever the case of their letters, since a file system that does not tell capitals apart would put `Assets` and `assets` in one folder, such as `assets` or `data`, since every site has `assets/` and `data/`, `*.html`, or `v1.0` when the version built is `v1.0`. Something kept that is in a folder ghg writes, whatever the case of their letters, stops the run the same way, such as `assets/custom.css`, kept by `custom.css`, since ghg writes into that folder and removes from it what nothing references. The report reads `<output>/<path>: the pattern <pattern> keeps this, but ghg writes it or the folder it is in, so the output folder is left as it is.`, where the path is the first such thing in the order of rule 15, a folder named rather than what is in it, and the pattern the one that keeps it, as rule 20 describes. It is checked before the input is read, with what the output folder holds and what its marker lists, and again right before the site is written, with the files of the site built, so that a pattern that keeps a file only the build knows it writes, such as a new object of the store, is found before anything is written. Fixture: `tests/fixtures/keep-in-output`.

## A build with no feature file

An input that holds no feature file is not a mistake, such as a suite whose first feature is not written yet, or a pull request that changes no feature file, but there is nothing to show, so a build writes nothing rather than an empty site that would be published.

229. When `ghg build` reads no feature file, as [Reading the input](#reading-the-input) describes, and the input holds nothing that stops the build, as rules 14 and 16 describe, it writes nothing: no page, no marker, not even the output folder. It prints to standard error why, which names what it read from: `<input>: the input folder holds no feature file, so no site was built.`, the input folder as rule 16 shows it; with `--only`, the sentence of rule 208 for a list that names no feature file of the input, and that of rule 204 for a list that names no path. It prints nothing to standard output, and exits with status 0. `ghg version add` adds no version, and the versions page is left as it was, and `ghg preview add` adds no preview. The output folder is still checked first, before the input is read, as rule 38 and rules 123 to 125 describe, so an output folder that is not safe still stops the build, and an input folder that does not exist still stops it, as rule 16 describes. Fixtures: `tests/fixtures/no-features`, whose input holds a file that is not a feature file and a feature file its `.ghg-ignore` leaves out, and `tests/fixtures/only`, with `nothing.toml` and `nothing.txt`, and with `empty.txt` and nothing on standard input.
230. `ghg serve` without `--watch`, which builds into the output folder, does the same: it writes nothing, prints the sentence of rule 229, serves nothing, and exits with status 0. `ghg serve --watch`, which builds in memory and writes nothing, as rule 66 describes, serves the site all the same, whose home page counts no feature, and, once it says where it serves, as rule 60 describes, prints to standard error that the site served is empty: `<input>: the input folder holds no feature file, so the site served shows none.`, or, with `--only`, `<file>: names no feature file of the input, so the site served shows none.`, or `<file>: names no path, so the site served shows none.` A rebuild that reads no feature file is served the same way: after `The site was rebuilt.`, it prints that sentence again. ## A report for programs

A program that runs `ghg build`, such as a GitHub Action, reads how the build ended from one JSON object, rather than from the exit status and the sentences meant for a person.

231. `--message-format <format>`, an option of `ghg build`, `ghg version add`, `ghg version remove`, `ghg preview add` and `ghg preview remove`, and not of `ghg serve`, takes `human`, the default, or `json`. With `json`, once the command ends, standard output holds one JSON object, on one line, ended by a line feed, whatever the build ended with; standard error holds the same sentences as without the option, and the exit status is the same. Any other value is a mistake on the command line, as rule 19 describes, which reads `The option --message-format takes human or json, not <value>.`, and a mistake on the command line prints no JSON. The configuration file has no key for it, since it concerns the program that runs one build. The object always has these keys, each `null` when it does not apply:
    - `outcome`: `built`, when the site, the version or the preview was written; `nothing-to-build`, when no feature file was read, as rule 229 describes; `removed`, when a version or a preview was removed, as rules 257 and 258 describe; `nothing-to-remove`, when there was none of that name; or `stopped`, when the configuration, the input, the output folder or the front page stopped the command, as rule 20 describes.
    - `output`: the output folder, from the current folder, as the messages of a build show it; `version`: the version's name, as rule 120 describes, or `null` for a site without versions and a preview; and `preview`: the preview's name, as rule 211 describes, or `null` for a site and a version; all three `null` unless the outcome is `built` or `removed`.
    - `features`: how many feature pages the site, the version or the preview has, and `scenarios`: how many scenarios they hold, counted as rule 82 counts them; both `null` unless the outcome is `built`.
    - `notes`: a list of what ghg says of a build that was not stopped, in the order it prints them, each an object with `kind`, which a program can rely on, and `message`, the sentence it prints: `no-title`, the hint of rule 17; `large-site-data`, the warning of [Search](#search), rule 150; `nothing-to-build`, the sentence of rule 229; and `nothing-to-remove`, the sentence of rule 257 or 258. It is empty when there is nothing to say.
    - `errors`: a list of every problem that stopped the build, in the order of the report, each an object with `path`, `line`, a number or `null`, and `message`, the parts of its line of the report, as rule 16 describes them, such as `{"path": "empty.feature", "line": 1, "message": "Syntax error."}`. It is empty unless the outcome is `stopped`.

    Fixtures: `tests/fixtures/constructs`, which builds, `tests/fixtures/no-features`, which has nothing to build, `tests/fixtures/unreadable`, which stops the build, and `tests/fixtures/versions` and `tests/fixtures/only`, which add and remove a version and a preview.
