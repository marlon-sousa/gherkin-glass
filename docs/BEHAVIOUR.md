## Reading the input

Before anything is built, gherkin-glass finds the feature files under the input folder and reads every one of them. If any file cannot be read, the build stops and nothing is written.

### Which files are read

1. By default, a file is read when its name ends in `.feature`. Every other file is left out. Fixture: `tests/fixtures/input-files`.
2. By default, every hidden file or folder, one whose name starts with a dot, is left out with everything in it, even a file whose name ends in `.feature`. Fixture: `tests/fixtures/input-files`.
3. A file named `.ghg-ignore` changes these defaults, and nothing else does. It uses the [gitignore syntax](https://git-scm.com/docs/gitignore#_pattern_format) and may sit in any folder of the input. Its rules apply to the paths in that folder and everything below it, as a `.gitignore` file's rules do. Fixture: `tests/fixtures/input-files`.
   - A rule leaves out what it matches, such as `drafts/` or `old-*.feature`.
   - A rule starting with `!` reads again what the defaults or an earlier rule leave out, such as `!*.story` for files ending in `.story`, or `!.github/` for a hidden folder.
   - When several rules match a path, the last matching rule of the `.ghg-ignore` file nearest to the path decides. The defaults decide only when no rule in any `.ghg-ignore` file matches.
   - A path left out with its folder cannot be read again by a rule, because the folder is not looked into, as in git.
   - A `.ghg-ignore` file is never read as a feature, whatever the rules say.
4. No other file decides what is read: not `.gitignore` files, not `.ignore` files, not git's own exclude files, and not the ignore files of the folders above the input. Fixture: `tests/fixtures/input-files`.
5. Symbolic links are not followed, whether they point to a file or to a folder. Fixture: created by the test, since a symbolic link cannot be relied on in a checkout on every system.

### What is read

6. Each file is read as UTF-8 with the [`gherkin`](https://crates.io/crates/gherkin) crate: its feature, backgrounds, rules, scenarios, scenario outlines and their examples, steps, data tables, doc strings, tags and descriptions. Fixture: `tests/fixtures/constructs`.
7. A file written in any spoken language Gherkin supports is read with that language's keywords, given by a `# language:` line at the top of the file. A file without one is read in English. Fixture: `tests/fixtures/constructs`, which has a file in Portuguese.
8. Comments, the lines starting with `#`, are not kept.

### Doc strings

A doc string is the text between two delimiter lines, `"""` or three backticks, under a step. gherkin-glass keeps it as the author wrote it, as [Gherkin's own reference](https://cucumber.io/docs/gherkin/reference/#doc-strings) describes. Fixture: `tests/fixtures/doc-strings`.

9. Text after the opening delimiter, such as `json` in `"""json`, is the doc string's media type, kept apart from its content. A doc string without it has no media type.
10. The content is the lines between the opening and the closing delimiter, joined by line breaks, without a line break before the first line or after the last. A line of the content that starts with `#` is content, not a comment. From a `#` anywhere in a line of the content, a delimiter later on that line does not close the doc string.
11. Each line of the content loses as much of its leading indentation as the opening delimiter has, counting a space or a tab as one character. A line indented less loses all of it. A line indented more keeps the difference.
12. Inside a doc string opened with `"""`, an escaped delimiter `\"\"\"` reads as `"""`. Inside one opened with three backticks, three escaped backticks read as three backticks.
13. A file whose lines end in a carriage return and a line feed is read as if they ended in a line feed alone.

### Files that cannot be read

14. A file that cannot be read fails the build: a feature file that cannot be parsed, such as an empty file or one with only comments, or that cannot be read, such as one that is not UTF-8; a `.ghg-ignore` file with a rule that is not valid, whose other rules still apply; and a folder of the input that cannot be listed, the input folder itself included. There is no option to carry on without it. Fixture: `tests/fixtures/unreadable`.
15. Every such file is reported before the build stops, not only the first. The report has one line per problem, sorted by path, folder by folder, so that a folder's contents stay together, and then by line. Names are compared by their character codes, so capital letters come before small ones. The report is the same on every run. Fixture: `tests/fixtures/unreadable`.
16. Each line reads `<path>:<line>: <message>`, where the path is relative to the input folder, with `/` between folders on every system, the line is where the parser stopped, or the file's last line when it stopped past the end, and the message is the parser's. When the parser has no message of its own, only the list of what it expected, the message is `Syntax error.` A problem with no line, such as a file that cannot be read, reads `<path>: <message>`. A file that cannot be read has the message `cannot be read: <reason>`, a folder that cannot be listed `cannot be listed: <reason>`, a file that changed while it was being read `changed while it was being read`, and a `.ghg-ignore` rule that is not valid the `ignore` crate's message, where the reason is the operating system's words. A problem with the input folder itself shows its path as it was given, and an input folder that does not exist, the default `features` among them, reads `<path>: the input folder does not exist. Create it, or name another with input in ghg.toml or with --input.` Fixture: `tests/fixtures/unreadable`.

## The command line and its configuration

The command is `ghg`. How it builds a site is set by a configuration file, `ghg.toml`, kept with the feature files, and by options on the command line, which override it, so that a site builds the same way locally and in CI. Every sentence it prints is gherkin-glass's own interface text, except the messages of the libraries and the operating system it passes on, which are named where they appear.

### Commands

17. `ghg build` reads the input, as [Reading the input](#reading-the-input) describes, and when every file can be read, writes the site into the output folder, as [Pages](#pages) and [Folder pages](#folder-pages) describe. When it has written the site, it prints nothing to standard output and exits with status 0. Standard error is empty too, unless the site has no title, from `--title` or the configuration's `title`: then it holds the hint `The site has no title, so its home page is called Feature files. Set title in ghg.toml, or give --title.`; and unless the search documents are large, when it holds the warning of [Search](#search), rule 150. Either way the status is still 0. Fixtures: `tests/fixtures/configuration/default` and `tests/fixtures/pages`.
18. `ghg --help`, or `-h`, prints the commands and their options to standard output and exits with status 0, as it does after a command, such as `ghg build --help`. `ghg --version`, or `-V`, prints `ghg` and its version, such as `ghg 0.1.0`, the same way. Fixture: `tests/fixtures/configuration/default`.
19. A mistake on the command line stops the run before anything is read. It prints one message to standard error, naming what was typed wrong when something was, and exits with status 2. The mistakes are: no command; a command ghg does not have; an option the command does not have; an option without its value, or with an empty one, such as `--input=`; a value given to an option that takes none, such as `--help=yes`; an option given more than once; an argument the command does not take; and a version name that cannot be one, as [Versions](#versions), rule 121, describes. Fixture: `tests/fixtures/configuration/default`.
20. When the configuration file or the input stops a build, the report goes to standard error, one line per problem, nothing goes to standard output, and the status is 1. A configuration file with a problem stops the run before the input is read. Fixtures: `tests/fixtures/configuration/mistaken` and `tests/fixtures/unreadable`.

### The options of ghg build

An option's value follows it, as `--input specs`, or is joined to it by `=`, as `--input=specs`. Paths on the command line are relative to the current folder. One more option, `--version-name <name>`, makes a build versioned, as [Versions](#versions), rule 120, describes.

21. `--config <file>` reads that configuration file instead of `ghg.toml` in the current folder. A file given this way that cannot be read, because it does not exist or for any other reason, stops the run with `<file>: cannot be read: <reason>`, the file shown as it was given and the reason in the operating system's words. Fixture: `tests/fixtures/configuration/configured`.
22. `--input <folder>` reads that folder as the input, whatever the configuration file's `input` says, `--output <folder>` writes the site into that folder, whatever the configuration file's `output` says, and `--title <text>` is the site's title, whatever the configuration file's `title` says. `--front-page <file>` is the front page's template, whatever the configuration file's `front_page` says, as [The front page](#the-front-page), rule 183, describes. Fixtures: `tests/fixtures/configuration/configured`, `tests/fixtures/pages` for `--title`, and `tests/fixtures/front-page` for `--front-page`.

### The configuration file

23. Without `--config`, the configuration file is `ghg.toml` in the current folder, and only there: the folders above are not searched. When there is none, every setting takes its default, and that is not a problem. A `ghg.toml` that is there but cannot be read, such as a folder of that name or a file that is not UTF-8, stops the run with `ghg.toml: cannot be read: <reason>`, as rule 21 describes. Fixture: `tests/fixtures/configuration/configured`.
24. The file is written in [TOML](https://toml.io/). Paths in it, and the defaults of the keys that take a path, are relative to the folder the file is in, whichever folder ghg runs from. Without a file, the defaults are relative to the current folder. It may set these keys, and the features that need more add them here as they are built:

    | Key | Takes | Default | What it sets |
    | --- | --- | --- | --- |
    | `input` | text | `features` | The input folder, the folder of feature files to read. It must exist, as rule 16 says. |
    | `allow_unnamed` | `true` or `false` | `true` | Whether features, rules and scenarios may have no name, as [Anchors](#anchors), rule 35, describes. |
    | `output` | text | `site` | The output folder, where the site is written, as [Pages](#pages), rule 38, describes. |
    | `source_link` | text | none | The address of each feature file's source, as [Pages](#pages), rule 47, describes. Without it, pages have no link to their source. |
    | `collapse_rules` | `true` or `false` | `false` | Whether rules start collapsed, as [Pages](#pages), rule 51, describes; checked by `tests/fixtures/pages`. |
    | `collapse_scenarios` | `true` or `false` | `false` | Whether scenarios, scenario outlines, backgrounds and the scenarios an outline's examples produce start collapsed, as [Pages](#pages), rule 51, describes; checked by `tests/fixtures/pages`. |
    | `title` | text | `Feature files` | The site's title, as [Folder pages](#folder-pages), rule 81, describes; checked by `tests/fixtures/pages`. |
    | `show_tree` | `true` or `false` | `true` | Whether the folder tree is shown when a reader first opens the site, as [The folder tree](#the-folder-tree), rule 88, describes; checked by `tests/fixtures/pages`. |
    | `inline_backgrounds` | `true` or `false` | `true` | Whether pages start with the backgrounds inside each scenario expanded and those in their own place collapsed, or the opposite, as [Backgrounds](#backgrounds), rule 97, describes; checked by `tests/fixtures/backgrounds`. |
    | `tag_links` | a list of tables, each written `[[tag_links]]` | none | The links from tags to other sites, as [Tags](#tags), rule 106, describes; checked by `tests/fixtures/tags`. |
    | `accent_light` | a colour, as text | `"#0b4f9c"` | The light theme's accent colour, as [The accent colours](#the-accent-colours) describes. |
    | `accent_dark` | a colour, as text | `"#8cc4ff"` | The dark theme's accent colour, as [The accent colours](#the-accent-colours) describes. |
    | `version_name` | text | none | The version the build is, which makes it a versioned build, as [Versions](#versions), rule 120, describes. Without it, the build is not versioned. |
    | `replace_existing_version` | `true` or `false` | `true` | Whether an earlier build in the output folder is replaced: a site without versions, as [Pages](#pages), rule 38, describes, or a version of one, as [Versions](#versions), rule 123, describes. |
    | `front_page` | text | none | The front page's template, a Markdown file, as [The front page](#the-front-page), rule 183, describes; checked by `tests/fixtures/front-page`. Without it, the front page is ghg's own. |

    Fixture: `tests/fixtures/configuration/configured`.
25. A setting given on the command line wins over the file's key of the same meaning, and the file's key wins over the default. Fixture: `tests/fixtures/configuration/configured`.
26. A key the file may not set, a table among them, or a value of the wrong type, is never ignored: it stops the run. Every such problem in the file is reported, sorted by line, each as `<file>:<line>: <message>`, the file shown as given and the line that of the key, or for a value that cannot be used, such as one of the wrong type, that of its value. An unknown key reads `ghg has no setting named <key>.`, a key that takes text and was given something else `<key> must be text, in quotes.`, a key that takes `true` or `false` and was given something else `<key> must be true or false.`, a path, an address, a title or a name given as empty text `<key> must not be empty.`, a `version_name` that cannot be a version name the sentence of [Versions](#versions), rule 121, and a key that takes a colour and was given something else, or an accent colour with too little contrast, the messages of rules 118 and 119. The keys of a table of `tag_links` are named with it, such as `tag_links.pattern`, and rule 108 adds their own messages. A file that is not valid TOML, such as one with a key given twice or text without quotes, is reported once, at the line where the [`toml`](https://crates.io/crates/toml) crate stopped, with that crate's message. Fixtures: `tests/fixtures/configuration/mistaken`, `tests/fixtures/configuration/mistaken-pages`, `tests/fixtures/configuration/mistaken-tags`, `tests/fixtures/configuration/not-boolean`, `tests/fixtures/configuration/empty-input`, `tests/fixtures/configuration/not-toml`, `tests/fixtures/configuration/not-colour`, `tests/fixtures/configuration/faint-accents` and `tests/fixtures/versions`.

## Anchors

Every scenario, scenario outline, rule, background and examples block of a feature has an anchor, made from its name by the rule below, and so does every scenario an outline produces from a row of its examples ([#13](https://github.com/marlon-sousa/gherkin-glass/issues/13)). A scenario outline is any scenario with examples, whatever its keyword. A link to a block keeps working as long as its file, its name and the blocks before it on its page that share its anchor stay as they are; an outline's rows keep theirs as long as the rows before them do. A block's anchor is the `id` of its heading on its feature's page, as [Pages](#pages) describes. A row's anchor is the `id` of the heading of the scenario it produces, as [An outline's examples as scenarios](#an-outlines-examples-as-scenarios), rule 130, describes.

The rule is part of what is promised: changing it is a major version ([CONTRIBUTING.md](../CONTRIBUTING.md), "Releases").

### The anchor rule

27. The name is normalised to Unicode NFC and lower-cased, and the anchor is in NFC. Fixture: `tests/fixtures/anchors`.
28. Apostrophes, `'` and `’`, are removed. Fixture: `tests/fixtures/anchors`.
29. Every run of characters other than letters and digits becomes one `-`, and there is no `-` at either end. Letters and digits are the characters Unicode gives the Alphabetic or Numeric property. A combining mark, such as Devanagari's virama, stays when it follows a letter, a digit or another mark that stays, and so does a zero width joiner or non-joiner between one that stays and a letter or digit, as Persian writes inside words; anywhere else, such as the variation selector after an emoji, it is a gap like any other character. Fixture: `tests/fixtures/anchors`.
30. Letters outside a to z, such as `ã` or `ç`, are kept, not transliterated or percent-encoded: "Saque em conta poupança" becomes `saque-em-conta-poupança`. Fixture: `tests/fixtures/anchors`, which has a feature in Portuguese.
31. A block with no name takes the keyword written in the file instead, made into an anchor by rules 27 to 29, such as `background`, `contexto` or `esquema-do-cenário`. So does a block whose name leaves nothing after rule 29, such as `???`. When the keyword leaves nothing too, as the emoji keywords of Gherkin's `em` language do, the anchor is the block's kind in English: `background`, `rule`, `scenario`, `scenario-outline` or `examples`. Fixture: `tests/fixtures/anchors`.
32. Anchors are unique on a page. Taking the blocks in file order, each takes the anchor rules 27 to 31 make, or, when an earlier block already has it, the first of that anchor followed by `-2`, `-3` and so on that no earlier block has. So an unnamed rule's background, after the feature's, is `background-2`. The `id`s gherkin-glass gives the page's own parts, such as the skip link's target, `ghg_main`, each contain `_`, which no anchor contains, so that no anchor is ever taken by one of them, nor one of them by an anchor. Fixture: `tests/fixtures/anchors`, and `tests/fixtures/pages` for the page's own `id`s.
33. A scenario produced from a row of an outline's examples takes the outline's anchor, then `-row-`, then the row's number, counted from 1 across all the outline's examples blocks in file order, without their header rows, such as `withdraw-cash-row-3`. These anchors are made after every other anchor on the page, in file order, and one that an earlier anchor already has is made unique as rule 32 says. Fixture: `tests/fixtures/anchors`.
34. A feature has no anchor of its own: it is the page. Fixture: `tests/fixtures/anchors`, where a scenario named as its feature takes the anchor unnumbered.

### Blocks without a name

35. Backgrounds and examples blocks may always be unnamed. Features, rules and scenarios, outlines included, may be unnamed while `allow_unnamed` is `true`, its default. When it is `false`, each unnamed feature, rule, scenario and scenario outline is a problem that stops the build, reported with the problems of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as rules 15 and 16 describe, at the line of its keyword. The messages are `The feature has no name, and allow_unnamed is false.`, and the same with `rule`, `scenario` or `scenario outline` in place of `feature`. Fixtures: `tests/fixtures/configuration/unnamed` and `tests/fixtures/configuration/unnamed-allowed`.

## Pages

Each feature file becomes one page of the site, which a screen reader can move through by heading, scenario by scenario, and which reads well for everyone. A site is meant to be served over HTTP, by any static web server or host or by `ghg serve` ([#26](https://github.com/marlon-sousa/gherkin-glass/issues/26)), and is not opened from disk ([design note 0026](design/0026-sites-are-served.md)). A page opened from disk says so, as [A page opened from disk](#a-page-opened-from-disk) describes.

### The site

36. The site has one page for each feature file, and one for each folder of feature files, as [Folder pages](#folder-pages) describes. A feature file's page is at the file's path below the input folder with its last extension replaced by `.html`, or with `.html` added when its name has none, as for `README`, or when its only dot is its first character, as for `.feature`, which becomes `.feature.html`. So `billing/refunds.feature` becomes `billing/refunds.html`, and `stories/read.story`, read through a `.ghg-ignore` rule, becomes `stories/read.html`. Folders are separated by `/` on every system. Fixture: `tests/fixtures/pages`.
37. Two files whose pages would have the same path, such as `a.feature` and `a.story`, stop the build, and so do two whose pages' paths differ only in the case of their letters, such as `A.feature` and `a.feature`, since some file systems do not tell them apart. Each such file after the first, in the order of rule 15, is a problem reported with those of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as `<path>: has the same page, <page>, as <first path>.`, where the page is its own. Fixture: `tests/fixtures/same-page`, and the tests of `src/policies/collecting/page_collisions.rs` for letters in another case, which a checkout cannot hold side by side on every system.
38. The site is written into the output folder, `site` by default, or the folder `output` or `--output` names. The output folder and the folders in it are made as needed. The output folder is ghg's once ghg has marked it, with a file at its root that lists every file ghg wrote there: `ghg-site.json` for a site without versions, `ghg-versions.json` for versions of a site, as [Versions](#versions), rule 122, describes. ghg marks only an output folder that is missing or empty. A marker ghg cannot read, or one that lists a path with an empty, `.` or `..` folder or file name in it, such as `../notes.txt`, which would lead outside the output folder, counts as no marker. Of the versions page's files a marker lists, only those found in the output folder are removed before the page is written again. Before every build, before the input is read, the output folder must be safe:
    - An output folder that holds anything and no marker, or a file or a symbolic link in its place, is never written into: the run stops before the input is read, writes and deletes nothing, and reports `<output>: this is not a site ghg built, so it is left as it is. Build into an empty or new folder.`
    - A marked output folder must hold only what ghg wrote there. For a build without a version name, that is the marker and the files of the site it lists, with the folders that hold them; a file it lists that is gone is no problem. Anything else, a file, a link or a folder, stops the run the same way, and reports `<output>/<path>: ghg did not write this, so the output folder is left as it is.`, where the path is the first such thing in the order of rule 15, a folder named rather than what is in it.
    - A build without a version name into an output folder marked for versions stops the same way, and reports `<output>: the output folder holds versions of a site, so build with a version name, or into another folder.`
    - In a safe output folder, an earlier site is emptied and replaced when `replace_existing_version` is `true`, its default, so that no file of it is left. It is emptied only once the input has been read without a problem, and the output folder checked again, right before the site is written, so that a build whose input has a problem leaves the earlier one as it was. The marker is written before the site's files, so that it lists them even when one cannot be written. When `replace_existing_version` is `false`, the run stops before the input is read, writes nothing, and reports `<output>: a site is already built here, and replace_existing_version is false.`

    Since ghg may empty a marked output folder at any build, anything put there by hand can be lost, so the output folder is never a folder that holds anything else.

    In these reports, `<output>` is the output folder as it was given, and an output folder that cannot be looked into reads `<output>: cannot be read: <reason>`, and one that cannot be emptied or marked `<output>: cannot be written: <reason>`. A file that cannot be written, or a folder that cannot be made for it, stops the build, which reports `<path>: cannot be written: <reason>`, the path being the output folder as it was given followed by the path in it of the file being written, and the reason in the operating system's words, as rule 20 describes. The files written before it stay. Fixtures: `tests/fixtures/pages`, and an output folder that cannot be written, created by the test.
39. Beside the pages, the site has `assets/gherkin-glass.css`, its stylesheet, and `assets/gherkin-glass.js`, the script of its behaviour, an ES module. Both are built into ghg and are the same in every site a version of ghg builds. Every page links them by a relative address, as every link in the site is, so that a site works at any address, below a path such as GitHub Pages' `/<repository>/` included. The site also has `assets/tree.json`, the data of its folder tree, written for each site, which the script fetches at an address relative to its own, as [The folder tree](#the-folder-tree), rule 89, describes. Fixture: `tests/fixtures/pages`.

### What a page holds

40. A page's content is in its HTML as it is written, never built by its script: every heading, anchor, link, list and table is there as the page loads. The exceptions are the folder tree, which the script builds from the site's shared data, as [The folder tree](#the-folder-tree) describes, since everything it links is also linked from the folder pages; and what search finds, its status and its results, which the script writes as the reader searches ([Search](#search)). Fixture: `tests/fixtures/pages`.
41. The feature's own text, its keywords included, is shown as written in the file. gherkin-glass's own text, such as "Contents" and "Collapse all", is in English, whatever language the file is written in. Fixture: `tests/fixtures/pages`, which has a feature in Portuguese.
42. The page's `lang` is the language of its feature file, as rule 7 reads it, and `en` for a file without a `# language:` line. ## Previewing a site

`ghg serve` builds a site and serves it over HTTP on the reader's own machine, so that it can be looked at before it is published. A site gherkin-glass builds is meant to be served, by `ghg serve` or by any static web server or host, and opening its pages straight from disk is not supported ([design note 0026](design/0026-sites-are-served.md)).

### Serving

56. `ghg serve` reads the configuration file and the command line as `ghg build` does, and has the options of `ghg build`, which mean the same. It builds the site into the output folder, as `ghg build` would, then serves that folder. That build checks the output folder as `ghg build`'s does, as [Pages](#pages), rule 38, and [Versions](#versions), rules 123 to 125, describe, and a versioned build serves the output folder, whose `index.html` is the versions page. When the configuration, the input or the output folder stops the build, it reports it as `ghg build` does, as rule 20 describes, serves nothing, and exits with status 1. Fixture: `tests/fixtures/serve/built`.
57. `--no-build` serves the output folder as it is, without reading the input or building anything. Fixture: `tests/fixtures/serve/site`.
58. It listens on the address `127.0.0.1`, so that nothing on the network reaches it unless asked, at port 8000. `--host <address>` listens on another address, such as `0.0.0.0` for every network the machine is on, and `--port <number>` on another port. Port 0 asks the operating system for a free port. A port that is not a whole number from 0 to 65535 is a mistake on the command line, as rule 19 describes, and reads `The option --port needs a whole number from 0 to 65535, not <value>.` Fixture: `tests/fixtures/serve/site`.
59. When the port is already in use, at that address or at every address, as another server listening on `0.0.0.0` does, it serves nothing, never choosing another port by itself, prints `Port <port> is already in use. Choose another with --port.` to standard error, and exits with status 1. When it cannot listen for any other reason, such as an address the machine does not have, it prints `ghg serve cannot listen at <address>, port <port>: <reason>`, the reason in the operating system's words, and exits with status 1. Fixture: `tests/fixtures/serve/site`.
60. Once it listens, it prints `The site is served at <address>. Press Control+C to stop.` to standard output, where the address is the one to open in a browser, such as `http://127.0.0.1:8000/`, with the port the operating system chose for port 0. When it listens on every network, as with `0.0.0.0` or `::`, which a browser cannot open, the address printed is this machine's own, `127.0.0.1` or `[::1]`. It serves until it is stopped. Fixture: `tests/fixtures/serve/site`.

### What it answers

61. It answers `GET` and `HEAD` requests. A request's path names a file below the served folder, its parts decoded from percent-encoding as UTF-8, and its query left aside. A path ending in `/` names the `index.html` file of that folder. A path naming a folder without the `/` is redirected, with status 301, to the same path with the `/`, so that the page's relative links work. Fixture: `tests/fixtures/serve/site`.
62. A file is served with status 200, exactly as it is, and with the content type the `mime_guess` crate gives for its extension, regardless of case, followed by `; charset=utf-8` when that type is text. An extension it does not know, and a file with none, is served as `application/octet-stream`. So the files a site holds are served as `text/html; charset=utf-8` for `.html`, `text/css; charset=utf-8` for `.css`, `text/javascript; charset=utf-8` for `.js` and `application/json` for `.json`. Fixture: `tests/fixtures/serve/site`.
63. Every answer says `Cache-Control: no-cache`, so that a browser asks again for a file before using its copy. Fixture: `tests/fixtures/serve/site`.
64. A path with no file, a path with an empty part, a part `.` or a part `..`, or a path that cannot be decoded, is answered with status 404 and the plain text sentence `Nothing is at this address in the site.` No request's path leads outside the served folder, though a symbolic link inside it is followed. Any method other than `GET` and `HEAD` is answered with status 405 and the sentence `ghg serve answers only GET and HEAD requests.` Fixture: `tests/fixtures/serve/site`.

### Watching

65. `--watch` watches the input folder, everything in it, its `.ghg-ignore` files among them, and the configuration file, whether it exists yet or not, and the front page's template as the configuration file, as [The front page](#the-front-page), rule 191, describes. A change that may change what a build reads makes it read the configuration file again and rebuild the whole site: a change to the configuration file, to a `.ghg-ignore` file, to a file the `.ghg-ignore` rules select, whether it was there before the change or only after it, so that a file made, changed, moved or removed counts, or to a folder holding such a file. Any other change rebuilds nothing, such as an editor's swap file, a file the rules leave out, or a file merely opened or read. When the watching may have missed a change, it rebuilds. An editor's burst of changes is one rebuild, and a change made during a rebuild starts another once it is done. A change to the configuration file, or a change the watching may have missed, makes it read the configuration file and the command line again, as rule 56 describes, then stop watching, dropping the changes still waiting, and watch again, on the input folder they now name and on the configuration file, before it rebuilds. So a change in a folder that is no longer the input is never seen. When the configuration stops that rebuild, as rule 67 describes, the watching stays as it was. Fixture: `tests/fixtures/serve/built`.
66. With `--watch`, every version of the site, the first one included, is built in memory and served from there, so the output folder is never written or deleted, nor checked as rule 38 describes. A version name, as [Versions](#versions) describes, changes nothing then: the site is served as a build without one serves it. A new version is served only once all of it is built, so no half-built page is ever served. `ghg build` writes the output folder. Fixture: `tests/fixtures/serve/built`.
67. When a rebuild is served, it prints `The site was rebuilt.` to standard output. When the configuration or the input stops a rebuild, it prints the report `ghg build` would print to standard error, then `The site was not rebuilt, so the last site that built is still served.`, and carries on serving that site. When the first build stops, ghg serve stops, as rule 56 describes. Fixture: `tests/fixtures/serve/built`.
68. `--watch` and `--no-build` together are a mistake on the command line, as rule 19 describes, which reads `The options --watch and --no-build cannot be used together.` When watching cannot start as ghg serve starts, such as when the system's limit on watched folders is reached, it prints `ghg serve cannot watch <path> for changes: <reason>` to standard error, the reason in the operating system's or the `notify` crate's words, and exits with status 1. When watching cannot start again once ghg serve runs, as rule 65 describes, such as when the input folder now named does not exist yet, it prints the same sentence to standard error and does not exit: it does not rebuild, carries on serving the last site that built, unchanged, and still watches the configuration file, so that its next change tries to watch and rebuild again. Fixture: `tests/fixtures/serve/built`.

### Reloading

69. With `--watch`, every page served as `text/html` has one element added, `<script type="module" src="/__ghg/reload.js?build=<number>"></script>`, just before its last `</body>`, or at its end when it has none, where the number is that of the version it comes from, counted from 1. Nothing else of the page changes, and without `--watch` nothing is added. Fixture: `tests/fixtures/serve/built`.
70. With `--watch`, the path `/__ghg/build` answers the number of the version being served, as plain text, and `/__ghg/reload.js` answers the reload script. Without `--watch`, both are paths of the site like any other. Fixture: `tests/fixtures/serve/built`.
71. The reload script asks `/__ghg/build` once a second, and reloads the page when the number differs from its page's. While ghg serve does not answer, it keeps asking. Fixture: `tests/fixtures/serve/reload`, in the browser, by `tests/browser/reload.mjs`.
72. Before reloading, it remembers the heading the reader was in, among the headings drawn on the page, which leaves out those inside a collapsed block: when an element of the page has focus and some of it is in the window, the last heading with an `id` at or before that element in the page, and otherwise the last heading with an `id` whose top is at or above the top of the window. After the reload, if the page still has a heading with that `id`, it scrolls the heading to the top of the window and moves focus to it, so that a sighted reader keeps their place and a screen reader resumes there rather than at the top. A focused element scrolled out of the window, such as the heading focused by the last reload after the reader scrolled on with the mouse, does not count. When there is no such heading, the page opens as any page does. The script says nothing of its own, so it has no interface text. Fixture: `tests/fixtures/serve/reload`, in the browser, by `tests/browser/reload.mjs`.

## Accessibility

Every page gherkin-glass writes is meant to be read and used by everyone: with a screen reader, with the keyboard alone, and in a light or a dark colour scheme. The browser check holds every page to the rules below on every pull request, and a page that breaks one fails it, as a failing test does ([AGENTS.md](../AGENTS.md), rule 3).

The check builds every fixture whose build makes a site, each with `--output` naming a folder of its own, serves the site with `ghg serve --no-build`, as rule 57 describes, so that it is checked as a reader gets it, and opens each of its pages in Chromium, with Playwright. Every rule below is checked on every one of those pages, and on `tests/fixtures/accessibility/failing`, a page that breaks each rule, which the check must find. A feature file or configuration file under `tests/fixtures/` that is in neither a fixture the check builds nor one it names as making no site fails the check, so that no new fixture is left out of it.

### The rules checked

73. Every page passes [axe-core](https://www.npmjs.com/package/axe-core) 4.14.0 with every rule tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` or `wcag22aa`, which are WCAG 2.2 at levels A and AA, and with `color-contrast-enhanced`, the contrast of 7 to 1 that level AAA asks for, which axe-core leaves off unless asked. Rules axe-core tags `experimental` or `deprecated` are left out, as axe-core itself leaves them out of a run by tags. The other criteria of level AAA are followed where reasonable, but not checked. Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`.
74. Every page passes rule 73 twice: once with the browser's colour scheme light, and once dark, as `prefers-color-scheme` reads them. The themes a reader can pick on the page are checked the same way, each once, from when they are built ([#10](https://github.com/marlon-sousa/gherkin-glass/issues/10)). Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`, which has text whose contrast fails in the dark scheme only.
75. From the start of a page as it loads, Tab moves focus to every link, button and other control the page shows, each once, in the order they come in the page, and the next Tab leaves the page. Nothing the page hides, such as the content of a collapsed block, is reached, and the folder tree is one stop, as rule 91 describes. The check counts once the tree is built, or its checkbox disabled. Fixtures: every fixture whose build makes a site, and `tests/fixtures/accessibility/failing`, whose links are reached out of order.
76. Enter and Space on a block's button each collapse or expand it, as rule 52 describes, and on a folder page's feature's button each show or hide its contents, as rule 84 describes, and Enter on "Collapse all" and on "Expand all" acts as rule 53 describes. Fixtures: every fixture whose build makes a site and has a block, and `tests/fixtures/accessibility/failing`, whose block's button Space does not turn over.

## Folder pages

Every folder of feature files has a page listing its subfolders and its features, and the input folder's page is the site's home page. Following their links reaches every page of the site, with no folder tree and no search, and the folder tree ([#7](https://github.com/marlon-sousa/gherkin-glass/issues/7)) links to them. Every page, a feature's or a folder's, starts with a breadcrumb of the folders above it.

### Where they are

77. Each folder of the input that holds a feature file, itself or in a folder at any depth below it, has a page at `index.html` in the same folder of the site, such as `billing/index.html` for the folder `billing`. The input folder's page is the home page, `index.html` at the site's root, and it is written even when the input holds no feature file. A folder with no feature file at any depth below it has no page. Fixture: `tests/fixtures/pages`.
78. A feature file whose page would be at the path of a folder's page, such as `index.feature`, or `billing/Index.story` read through a `.ghg-ignore` rule, stops the build, the letters compared without regard to case as rule 37 compares them. It is a problem reported with those of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as `<path>: has the same page, <page>, as the page of the folder <folder>.`, where the page is its own and the folder is the folder's path below the input folder, or, for a file in the input folder itself, as `<path>: has the same page, <page>, as the home page.` So do two folders whose paths below the input folder differ only in the case of their letters, such as `Billing` and `billing`: each such folder after the first, in the order of rule 15, is reported once, as `<folder>: has the same page, <page>, as the folder <first folder>.`, where the page is its own. Fixtures: `tests/fixtures/same-page`, and the tests of `src/policies/collecting/page_collisions.rs` for folders in another case, which a checkout cannot hold side by side on every system.
79. Every link to a folder's page names its `index.html`, such as `billing/index.html` or `../index.html`, and is relative, so that it works on any server, one that does not answer a folder's own address with its `index.html` included. Fixture: `tests/fixtures/pages`.

### What a folder page holds

80. A folder page's `lang` is `en`, the language of gherkin-glass's own text. A feature's link and the list of its contents, rule 83, have the `lang` of the feature's page, as rule 42 gives it. Fixture: `tests/fixtures/pages`, which has a feature in Portuguese.
81. The page's only `h1` is the folder's name, and on the home page the site's title, which is `--title`, or the configuration's `title`, or `Feature files` without either, as rule 17 describes. The page's title is the folder's path below the input folder, a comma, a space and the site's title, such as `billing/archive, Banking`, and on the home page the site's title alone. A home page that is the front page of a site with a template takes its `h1` and its title from the template instead, as [The front page](#the-front-page), rule 187, describes. Fixture: `tests/fixtures/pages`, built once with a `title` and once without.
82. Under the `h1`, the home page has the site's totals, a list of four counts: the folders below the input folder that have a page, the feature files, the rules and the scenarios, such as `3 folders` and `1 scenario`. A scenario outline counts as one scenario, whatever its examples hold, scenarios inside rules count, and backgrounds do not. Fixture: `tests/fixtures/pages`.
83. Then every folder page has the folder's subfolders, as a list under an `h2` that reads `Folders`, and the feature files in the folder itself, as a list under an `h2` that reads `Features`. The subfolders are sorted by their names, and the features by their files' names, the names compared by their character codes as rule 15 compares them. A folder with no subfolder that has a page has no `Folders` heading and no list, and one with no feature file of its own has no `Features` heading and no list. Fixture: `tests/fixtures/pages`.
    - **A subfolder** is a link to its page, whose text is its name.
    - **A feature** is a link to its page, whose text is the feature's heading, as rule 43 makes it, followed by its count of scenarios, counted as rule 82 counts them, such as `2 scenarios`.
    - **A feature's contents** follow it when its page has contents, rule 46: the same list of links to its rules and scenarios, each address the feature's page followed by `#` and the block's anchor, such as `refunds.html#store-credit`.
84. A feature with contents has its count of scenarios as a button, which says with `aria-expanded` whether its contents are shown, and whose accessible name is the count followed by ` of ` and the feature's heading, such as `2 scenarios of Feature: Refunds`. Its contents are hidden when the page loads. Pressing the button shows them when they are hidden, and hides them when they are shown. The browser remembers the choice as rule 54 says, kept under the folder page's path and the link's address. A feature without contents has its count as text, with no button. A folder page has no "Collapse all" or "Expand all" buttons. Fixtures: `tests/fixtures/pages`, in the browser by rule 76, and the script's own tests, `script/test/adapters/dom_page.test.ts`, on `tests/fixtures/pages/expected/billing/index.html`.

### The breadcrumb

85. Every page, a feature's, a folder's, one of [Tags](#tags) or the page of [Step sentences](#step-sentences), has a breadcrumb before its main content: a navigation landmark named "Breadcrumb", holding a numbered list of links. ## The folder tree

Beside the content of every page, a feature's, a folder's, a tag's or the step sentences', a tree of the input's folders, features, rules and scenarios helps a reader find their way in a large suite, with the current page marked. A checkbox shows or hides it. Everything the tree links is also linked from the folder pages, so a reader who hides it loses nothing. It follows the WAI-ARIA Authoring Practices [Navigation Treeview example](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-navigation/).

### Before the content

86. Every page's body starts with the dialog of [A page opened from disk](#a-page-opened-from-disk), rule 182, closed unless the page is opened from disk, and then a link that reads "Skip to content", whose address is `#ghg_main`, the `id` of the page's `main`. The link is the first thing on the page a keyboard reaches, and it is out of sight until it has the focus. After it come the checkbox of rule 87, then the folder tree, then the breadcrumb of rule 85, then the search box of [Search](#search), rule 151, and then the page's `main`, so that following the link passes over all of them. The versions page, which has none of them, is the one exception, as [Versions](#versions), rule 127, describes. Fixture: `tests/fixtures/pages`.

### Showing and hiding it

87. The checkbox reads "Show the folder tree", and is checked while the tree is shown. Checking it shows the tree, and unchecking it hides it, from every reader, a screen reader's included. Fixtures: the script's own tests, `script/test/adapters/dom_tree.test.ts` and `script/test/services/folder_tree.test.ts`.
88. The page's HTML is written with the tree shown when `show_tree` is `true`, its default, and hidden when it is `false`. ## Tags

Tags are how a suite is organised: by area, by ticket, by what a scenario needs. The site has a page for every tag, listing the scenarios that carry it, so that "what checks this?" is answered in one page, and an index of every tag.

A tag page's address is part of what is promised, like an anchor: changing how it is made is a major version ([CONTRIBUTING.md](../CONTRIBUTING.md), "Releases").

### The tag pages and their addresses

100. Every tag written in the input, on a feature, a rule, a scenario, a scenario outline or an examples block, has a page of the site at `tags/<name>.html`. Tags are told apart by their exact text, so `@Slow` and `@slow` are two tags. The name is made from the tag without its `@` by rules 27 to 29, so `@needs:db` is `needs-db`; a tag that leaves nothing, such as `@🚀`, takes `tag` instead. Taking the tags in the order of rule 102, each takes its name, or, when an earlier tag already has it or it is `index`, the first of that name followed by `-2`, `-3` and so on that is free. So `@Slow` is `slow` and `@slow` is `slow-2`, and `@index` is `index-2`. A tag page keeps its address as long as its tag, and the tags before it in that order whose names are its name or its name followed by `-` and a number, stay as they are. Fixture: `tests/fixtures/tags`.
101. The index of every tag is `tags/index.html`. The folder `tags` of the site holds only the tag pages and their index: a feature file whose page would be in it, as rule 36 makes its page's path, comparing the folder's name without regard to case, as rule 37 does, stops the build, whether or not a tag page has its path. Each such file is a problem reported with those of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as `<path>: has its page, <page>, in the folder tags, which holds the tag pages.` Fixture: `tests/fixtures/tags-folder`.
102. The index's title and its only `h1` read `Tags`. Under the `h1` is a list of every tag, ordered by its text lower-cased, then, for tags that lower-case alike, by its text as written, each compared by its character codes, as rule 15 compares names. Each item is a link to the tag's page, whose text is the tag as written with its `@`, followed by a comma, a space and how many scenarios carry it, as rule 103 counts them, such as `@slow, 3 scenarios`, `@billing, one scenario` or `@draft, no scenarios`. When no tag is written in the input, the list is replaced by the sentence `No feature file has a tag.` Fixtures: `tests/fixtures/tags` and `tests/fixtures/pages`, which has tags, and `tests/fixtures/configuration/default`, which has none.
103. A scenario carries a tag when the tag is written on the scenario itself, on one of its examples blocks, on its rule, or on its feature. A scenario outline is one scenario, however many rows its examples have. Backgrounds carry no tags. Fixture: `tests/fixtures/tags`.
104. A tag's page has the title and the only `h1` `Tag @<tag>`, with the tag as written, such as `Tag @slow`. Under the `h1` comes its link to another site when it has one (rule 107). Then, for each feature file on which the tag is written anywhere, in the order of rule 15, comes an `h2` whose text is a link to the feature's page, reading the page's title, as rule 43 makes it, such as `Feature: Refunds, billing/refunds.feature`. Under it is a list of the feature's scenarios that carry the tag, in the order of the file, each a link to the scenario's anchor on the feature's page, reading the scenario's heading, as rule 43 makes it. A scenario that carries the tag only through its examples, its rule or its feature, and not itself, is followed by a comma, a space and `through its examples`, `through its rule` or `through its feature`, the first of those three that has the tag. A feature on which the tag is written but none of whose scenarios carries it, such as a feature with no scenarios, has under its `h2` the sentence `None of its scenarios carries the tag.` in place of the list. Fixture: `tests/fixtures/tags`.
105. The index and the tag pages are written in English, the language of gherkin-glass's own text, and have the `lang` `en`. Each starts as every page does, with the skip link, the folder tree's checkbox, the folder tree and the breadcrumb of rules 85 and 86. The index's breadcrumb has a link to the home page, then one to itself whose text is `Tags`, and a tag page's has a link to the home page, then one to the index whose text is `Tags`, then one to itself whose text is its `h1`'s. The home page has, after its totals (rule 82) and before its folders, a paragraph holding a link to the index whose text is `Tags`, even when no tag is written in the input. Each link whose text is a feature's own, the `h2` and the scenarios of rule 104, has the `lang` of its feature's page, as rule 42 makes it, when that is not `en`. Every tag shown on a feature's page, as rule 45 lists it, is a link to its tag's page, by a relative address, as every link in the site is (rule 39). The part of a link's address that is a path in the site has each byte other than an ASCII letter, a digit, `-`, `.`, `_`, `~` and `/` percent-encoded, as rule 47 does, so `saque em conta.html` is linked as `saque%20em%20conta.html`. Fixtures: `tests/fixtures/tags` and `tests/fixtures/pages`.

### Links to other sites

106. The configuration's `tag_links` lists patterns that link tags to other sites, such as an issue tracker. Each is a table written `[[tag_links]]`, with three keys, all needed, all text:
    - `pattern`, a regular expression in the syntax of the [`regex`](https://docs.rs/regex/1/regex/#syntax) crate, matched against the whole tag, with its `@`, such as `@issue-(\d+)`;
    - `address`, the address the tag links to, such as `https://github.com/owner/repo/issues/$1`;
    - `text`, the link's text, such as `Issue $1 on GitHub`, so that a screen reader does not hear two links in a row that sound the same.

    In the address and the text, `$1`, `${1}`, `$name` and `${name}` are replaced by what the pattern's group of that number or name matched, as the `regex` crate's replacement syntax says, and `$$` is a `$`. A `$` that names no group, such as one before a space or at the end, stays as written. In TOML, a pattern is best written between single quotes, as `'@issue-(\d+)'`, where a `\` is kept as written. Fixture: `tests/fixtures/tags`.
107. A tag that a pattern matches has a second link beside its link to its tag page, everywhere a feature's page shows it, and under the `h1` of its tag page: the first matching pattern's, in the order of the file. Its address is the pattern's `address`, with each group's text percent-encoded as rule 47 encodes a path, and its text is the pattern's `text`, with each group's text as matched. The address is used as it comes out, so a relative one would point elsewhere from pages at different depths: it is meant to be a whole address, such as one starting with `https://`. A tag no pattern matches has no such link, and neither has one whose link comes out with an empty address, or with a text that is empty or only spaces, as `$1` does when its group matched nothing: the first matching pattern decides, and no later pattern is tried. Fixture: `tests/fixtures/tags`, whose `@later` matches a pattern whose text comes out empty.
108. A mistake in `tag_links` stops the run, as rule 26 describes, reported with that rule's problems, sorted with them by line. Every mistake of every table is reported, a table's pattern and its address and text being checked whenever they are given as text, even when another of its keys is missing or mistaken. `tag_links` given as anything but a list of tables reads `tag_links must be a list of tables, each written [[tag_links]].`, at its line. A table that lacks a key reads `tag_links.<key> is missing.`, at the line of its `[[tag_links]]`, once for each key it lacks. A pattern that is not a regular expression reads `tag_links.pattern is not a regular expression: <reason>`, where the reason is the short description the `regex` crate's parser, `regex-syntax`, gives, such as `unclosed group`, at the pattern's line, and one too large to build within the `regex` crate's default size limit, such as `@(a{1000}){1000}`, reads `tag_links.pattern is too large a regular expression.` An address or a text that names a group the pattern does not have, the first such group in it, such as `$2` for a pattern with one group, or `$1a`, which names the group `1a`, reads `tag_links.address names the group <group>, which the pattern does not have.`, or the same with `tag_links.text`, at its line. A key a table may not have, a key given something other than text, and an empty text read as rule 26 says, with the key named as `tag_links.<key>`. Fixture: `tests/fixtures/configuration/mistaken-tags`.

## Highlighting and themes

Parts of every step are highlighted, so that steps are quicker to scan, and a reader picks the theme a page is shown in. Colour never carries meaning alone: highlighting only colours text that already says what it is, and every theme reaches the contrast below.

### Highlighting

109. In every step, of a background, a scenario or a scenario outline, at the top of a feature or inside a rule, the keyword is highlighted as written, such as `Given`, `And`, `*` or `Dado`, and so are the quoted parameters, the placeholders and the numbers of the text after it, found as rules 111 to 113 say. Nothing else is highlighted: not data tables, doc strings, names or descriptions. On a page, each highlighted part is an element of its own around its text, a `span` whose class is `ghg-keyword`, `ghg-parameter`, `ghg-number` or `ghg-placeholder`, and a placeholder inside a parameter is inside the parameter's. Fixture: `tests/fixtures/highlighting`, with the pages committed beside it in `expected`.
110. Highlighting never adds, removes or changes a character, so a step reads the same with it and without it, to the eye and to a screen reader. Each highlighted part is told apart by its own text: the keyword begins the step, a parameter keeps its quotes, a placeholder its angle brackets, and a number is made of digits. Fixture: `tests/fixtures/highlighting`.
111. A quoted parameter runs from a double quote, `"`, to the next double quote of the step, both included, such as `"hello"` or `""`. A double quote just after a backslash, `\"`, neither opens nor closes a parameter, whatever comes before the backslash, and a double quote with no other after it is plain text. Single quotes make no parameter, since they are also apostrophes, as in `the user's 'name'`. Inside a parameter, placeholders are highlighted, and numbers are not. Fixture: `tests/fixtures/highlighting`.
112. A placeholder is `<`, a name, and `>`, where the name is not empty and is exactly one of the header cells of the examples tables of the step's own scenario outline, such as `<amount>` in an outline whose examples have an `amount` column. Anywhere else, in a step of a background or of a scenario without examples, or with a name that is no column's, `<` and `>` are plain text. Fixture: `tests/fixtures/highlighting`.
113. A word is a run of letters, digits, combining marks and `_`, where letters and digits are the characters Unicode gives the Alphabetic or Numeric property, with any single point or comma between two of them. A word made only of the digits 0 to 9, and points and commas between them, is a number, such as `10`, `3.5` or `1.000,50`; any other word is plain text, such as `R2D2`, `3rd`, `v1.2`, `2.x`, `x_1` or `٣`, so no number is found inside a word. A `-` just before a number is part of it, as in `-3`, unless a word ends just before the `-`, as in `2026-11-10` or `item-4`, where only the digits after it are a number. A point or comma after a number's last digit is not part of it. Fixture: `tests/fixtures/highlighting`.

### Themes

114. Every page can be shown in a light theme and in a dark theme. Every page, a feature's, a folder's, a tag's or the step sentences', has a group of three radio buttons named Theme, with the other reader options at its top, after the folder tree's checkbox: System, the default, which follows the theme the reader's system prefers, as the browser reports it, and changes with it while the page is open; Light; and Dark. The page's HTML has System chosen; the script shows the reader's choice once it runs. Fixtures: `tests/fixtures/pages`, and `script/test/services/theme_switching.test.ts`.
115. The browser remembers the choice, as it does the other reader options, for every page served from the same origin, the same scheme, host and port, and every such page then opens in it, as does a page the browser shows again from its cache, going back or forward. Sites that share an origin, such as the GitHub Pages sites of one owner, share the choice. When the browser keeps nothing, as some private windows do, the choice holds for the page it was made on. Fixture: `script/test/services/theme_switching.test.ts`.
116. A page is drawn in the chosen theme from the start, never first in another: a script in the page's head, which runs before the page is drawn, applies the remembered choice, and the page's own script, which runs after, does the rest. Fixtures: `tests/fixtures/pages`, and `script/test/policies/theme_choice.test.ts`, which checks that the head reads the choice where the page's script keeps it.
117. In every theme, text and every highlighted part reach a contrast of at least 7:1 against every background they are written on, WCAG's AAA level, and lines that carry no text, such as borders, at least 3:1 against the background. Contrast is as WCAG 2.2 defines it. Each page holds its themes' colours, the accent colours of its site among them, in a `style` element in its head, so that no page is drawn before it has them. The browser check checks every page in each theme a reader can pick: axe-core checks the text, as rule 73 says, and the check itself checks the lines, every border of every part shown and the outline of a focused link, since axe-core has no rule for them. A line is measured as it is seen: a colour that is not opaque is blended over what is behind it, and what is behind it is the background of its own part, for a border, or of the parts around it, for an outline, blended over theirs down to the first one that is opaque. Fixtures: every fixture's pages, in the browser check, once it is built ([#2](https://github.com/marlon-sousa/gherkin-glass/issues/2)); `tests/fixtures/accessibility/failing`, which has a border, a translucent border and a focus outline with too little contrast; `tests/fixtures/pages`, for the `style` element.

### The accent colours

118. Each theme has an accent colour, for links and for the outline around what has the keyboard focus. Links are also underlined, so that colour is not all that tells them apart from the text around them. `accent_light` sets the light theme's, and `accent_dark` the dark theme's, each by default a colour that passes rule 119. Setting one leaves the other at its default. An accent colour is text: `#` and six or three hexadecimal digits, in capitals or small letters, such as `"#0b4f9c"` or `"#08c"`. Anything else stops the run, as rule 26 says, at the line of the value, reading `<key> must be a colour in hexadecimal, in quotes, such as "#0b4f9c".` Fixtures: `tests/fixtures/configuration/accents`, `tests/fixtures/highlighting`, whose pages hold the accent colours it sets, and `tests/fixtures/configuration/not-colour`.
119. gherkin-glass computes the contrast of each accent colour against each background of its own theme, as rule 117 does. An accent that reaches less than 7:1 against any of them stops the run, as rule 26 says, at the line of its value, reading `<key> is <colour>, which reaches only <ratio>:1 against the <theme> theme's background <background>. It needs at least 7:1.`, where the theme is `light` or `dark`, the background is the one of that theme the colour contrasts least with, both colours are written as `#` and six small hexadecimal digits, and the ratio is rounded down to two decimals, so that 6.999 reads `6.99`. Fixture: `tests/fixtures/configuration/faint-accents`.

## Versions

A site can hold several versions of the same suite, each in a folder of its own, such as `v1.2.0/` and `main/`, with a page listing them, so that a reader reads the version they use, and a link to a version never changes under them.

### A versioned build

120. A build is versioned when it is given a version name, with `--version-name <name>` or with `version_name` in the configuration file, and the option wins over the key. Giving a name is the only way: without one, the build is not versioned. One run builds one version, from its one input folder. gherkin-glass does not read git: to build several versions, check each out into a folder of its own, such as with one checkout step per version in a workflow, and run ghg once for each. Fixture: `tests/fixtures/versions`.
121. A version name is one folder name. It is made of the letters `a` to `z` and `A` to `Z`, the digits `0` to `9`, and the characters `.`, `-`, `_` and `+`; it starts with a letter or a digit, and does not end with `.`. It is not `assets` or `index.html`, which the versions page uses, or `ghg-versions.json`, the output folder's marker, nor a name Windows keeps for a device, `con`, `prn`, `aux`, `nul`, `com1` to `com9` or `lpt1` to `lpt9`, alone or before a dot, such as `nul.txt`, all of them whatever their capitals. A name that cannot be a version name reads `<name> cannot be a version name. A version name is made of letters, digits, dots, hyphens, underscores and plus signs, starts with a letter or a digit, does not end with a dot, and is not assets, index.html, ghg-versions.json, or a name Windows keeps for a device, such as con or nul.` Given with `--version-name`, it is a mistake on the command line, as rule 19 describes; given with `version_name`, it is a problem of the configuration file, as rule 26 describes. Names that differ only in their capitals, such as `main` and `Main`, cannot both be built into one output folder, since a file system that does not tell capitals apart would put them in the same folder, as rule 124 describes. Fixture: `tests/fixtures/versions`.
122. A versioned build writes into a folder named after the version, inside the output folder, such as `<output>/v1.2.0/`, the site an unversioned build writes into the output folder itself. Every link in a site is relative, so a version works wherever it is served, under any path, with no base address to set. The output folder's marker, `ghg-versions.json`, lists the files of the versions page and every version built there, with the files of its folder. A marked output folder is safe, as rule 38 requires, when it holds the marker, one folder for each version the marker lists and the files the marker lists in it, and the versions page's files, and nothing else: a folder the marker does not list, or a file it does not list, stops the run before the input is read, writes and deletes nothing, and reports `<output>/<path>: ghg did not write this, so the output folder is left as it is.`, as rule 38 describes. A version the marker lists whose folder is missing stops it the same way, with `<output>/<name>: the marker lists this version, but its folder is missing, so the output folder is left as it is.` An output folder that is missing or empty is marked, and one that holds anything without a marker is refused, as rule 38 describes. Fixture: `tests/fixtures/versions`.

### A version that is already there

123. When the marker already lists the version, `replace_existing_version` decides. When it is `true`, its default, the version's folder is removed and the new build written in its place, so that no file of an earlier build of that version is left. It is removed only once the input has been read without a problem, right before the site is written, so that a build whose input has a problem leaves the earlier one as it was. The marker is written before the version's files, listing them, so that the output folder stays safe when one cannot be written; the versions page is then not written, as rule 38 describes for any build. When it is `false`, the run stops before the input is read, writes nothing, and reports `<folder>: the version <name> is already built, and replace_existing_version is false.`, as rule 20 describes. A version the marker does not list is added, with its folder and its entry in the marker. Fixture: `tests/fixtures/versions`.
124. A versioned build into an output folder marked as a site without versions, with the marker of rule 38, stops before the input is read, writes nothing, and reports `<output>: a site without versions is built here, so build without a version name, or into another folder.` A version whose name differs from one the marker lists only in its capitals stops the run the same way, on every system, whatever `replace_existing_version` says, with `<folder>: the output folder holds a version whose name differs from this one only in its capitals, which some systems would put in the same folder, so it is left as it is.` Fixture: `tests/fixtures/versions`.
125. In these reports, `<folder>` is the version's folder: the output folder's path, as rule 16 shows the input folder's, then `/` on every system, then the version's name. An output folder that cannot be looked into reads `<output>: cannot be read: <reason>`, a version's folder that cannot be removed `<folder>: cannot be written: <reason>`, and a marker that cannot be written `<output>: cannot be written: <reason>`, where the reason is the operating system's words. Fixture: `tests/fixtures/versions`.

### The versions page

126. Every versioned build writes the versions page, `index.html` in the output folder, with the stylesheet and the script it uses in `assets/` beside it. ## An outline's examples as scenarios

An outline is compact to write, but its reader has to put each row of its examples into its steps in their head. So each outline also shows its rows as the scenarios they produce, decided in issue [#13](https://github.com/marlon-sousa/gherkin-glass/issues/13).

129. Under an outline's examples blocks, inside its content, comes a block whose heading reads "Examples as scenarios", a colon, a space and the outline's name, or its keyword as written when it has none, such as `Examples as scenarios: Withdraw cash`, so that each outline's block has a name of its own. The heading is one level below the outline's, and has the `id` that is the outline's anchor followed by `_scenarios`, such as `withdraw-cash_scenarios`. It holds one scenario for each row of the outline's examples blocks, the rows of rule 33 in their order. An outline whose examples have no row, because each has no table or only a header, has no such block. Fixture: `tests/fixtures/pages`, whose `outlines.feature` has an outline with two examples blocks, an outline without a name, and one whose examples have no row.
130. Each such scenario is a block whose heading is one level below that of rule 129 and has the row's anchor of rule 33 as its `id`. Its heading reads the outline's name, or its keyword as written when it has none, then a space and, in brackets, each column's name, a colon, a space and the row's value, separated by a comma and a space, in the order of the table, such as `Withdraw cash (amount: 10, balance: 90)`. In the headings of rules 129 and 130, the outline's name, each column's name and each value are isolated from the words around them, each with a `<bdi>` of its own. Fixture: `tests/fixtures/pages`.
131. Under each such scenario's heading come the outline's steps, as rule 45 lists them, with every placeholder replaced by the row's value: in the steps' text, in every cell of their data tables, header cells included, and in their doc strings' content and media type. A placeholder is a column's name between `<` and `>`, such as `<amount>`. When several columns share a name, the first one's value is used. A placeholder that names no column stays as written, and a value put in place of a placeholder is never searched for placeholders itself. Such a scenario has no tags, no description and no backgrounds of its own, since its outline shows them. A column whose name is empty names no placeholder, since `<>` is none. Its steps are highlighted as [Highlighting](#highlighting) says of a scenario without examples, so nothing in them is a placeholder. Such scenarios are not listed on tag pages, since an outline is one scenario (rule 103). Fixtures: `tests/fixtures/pages`, and the outlines of `tests/fixtures/highlighting`, `tests/fixtures/backgrounds` and `tests/fixtures/tags`.
132. The block of rule 129 and the scenarios in it collapse and expand as rules 49 to 55 describe, with the starting states of rule 51, so that following a link to a row's anchor expands the scenario, the block of rule 129 and the outline around them. Fixtures: `tests/fixtures/pages`, and `script/test/adapters/dom_page.test.ts`.

## Step sentences

A page lists every distinct step sentence in the suite, grouped by keyword and sorted, each with how often it is used and links to the steps that use it, so that the suite's vocabulary can be read at a glance and near-duplicates found.

### What a sentence is

133. A step's sentence is its text after the keyword, without its doc string or data table, in Unicode NFC. Two steps have the same sentence when their texts are the same once every slot is replaced as rules 134 and 135 say; letters, spaces and everything else are compared exactly, so `the user logs in` and `The user logs in` are two sentences. Fixture: `tests/fixtures/step-sentences`.
134. A quoted value is a slot: a `"`, the text up to the next `"` on the step, and that `"`. In the sentence, a slot is shown as `"…"`, so `the user "ana" logs in` and `the user "bia" logs in` are one sentence, `the user "…" logs in`. An empty value, `""`, is a slot too. A `"` just after a backslash, `\"`, neither opens nor closes a slot, and a `"` with no other after it is text, as rule 111 says of highlighting. Other quotation marks, such as `'`, `“` and `”`, are text, so that apostrophes stay words. Fixture: `tests/fixtures/step-sentences`.
135. In a step of a scenario outline, a placeholder is a slot too, shown as `"…"` like a quoted value: a `<`, the name of a column of the outline's examples, which is not empty, and a `>`, the name ending at the first `>` after the `<`. So a step with `<name>` where another has a quoted value, or another placeholder, at the same place is the same sentence. Slots are found from the start of the step, and where a quoted value and a placeholder overlap, the one that opens first is the slot, so a placeholder inside a quoted value, as in `"<name>"`, is part of that one slot. A placeholder matches its column when both are the same in NFC. Outside an outline, and where the name is not one of its columns, `<` and `>` are text. Fixture: `tests/fixtures/step-sentences`.
136. Nothing else is a slot: numbers are text, so `I withdraw 10` and `I withdraw 20` are two sentences. Fixture: `tests/fixtures/step-sentences`.

### How the sentences are grouped and sorted

137. Sentences are grouped by the kind of step: Given, When or Then, in that order, whatever the language of the file. A step written with `And` or `But`, or their equivalents in the file's language, is of the kind of the step before it in its block, and of the kind Given when it is the first of its block. A step written with `*` is a Given step, as the `gherkin` crate reads it, wherever it is, so an `And` or `But` step after it is a Given step too. The same text in two kinds is two sentences, one in each group. A group with no sentences is not shown. Fixture: `tests/fixtures/step-sentences`.
138. Within a group, sentences are sorted by their text lower-cased, and, between two that lower-case the same, by their character codes, so capital letters come first. The order is the same on every run. Fixture: `tests/fixtures/step-sentences`.

### Where each sentence is used

139. Each sentence says how many times it is used, counting every step that has it, even two in the same scenario. Fixture: `tests/fixtures/step-sentences`.
140. Each sentence links to every step that uses it, through the anchor ([Anchors](#anchors)) of the block the step is in: its scenario, scenario outline, or background. A step of a scenario outline links to the outline, not to the scenarios its rows produce. A background's step is used once, by the background, and links to the background's own heading, whichever form [Backgrounds](#backgrounds), rule 97, gives the page: the copies of its steps shown inside each scenario are not counted again. The links are in the order of the features' paths, sorted as rule 15 describes, and in file order within a feature. Fixtures: `tests/fixtures/step-sentences`, and `tests/fixtures/backgrounds`, whose two sites, inline and linked, list the same sentences.
141. Beside each link are the step's values, the text of each of its slots exactly as written, not normalised, quotes and angle brackets included, such as `"ana"` or `<name>`, in the order they appear in the step. Fixture: `tests/fixtures/step-sentences`.

### The page

142. The site has one page of step sentences, `steps.html` at its root, whether or not any feature has a step. A feature file whose page would also be `steps.html`, as rule 36 makes it, such as `steps.feature` at the input folder's root, stops the build, and so does one whose page differs from it only in the case of its letters, such as `Steps.feature`, as rule 37 says. It is a problem reported with those of [Files that cannot be read](#files-that-cannot-be-read), sorted with them, as `<path>: has the same page, steps.html, as the step sentences.` Fixtures: `tests/fixtures/step-sentences`, `tests/fixtures/pages`, and `tests/fixtures/same-page`, and the tests of `src/policies/collecting/page_collisions.rs` for letters in another case.
143. Its `lang` is `en`, its only `h1` reads `Step sentences`, and its title is `Step sentences`, a comma, a space and the site's title, as rule 81 gives it, such as `Step sentences, Banking`. Like a folder's page, it has the skip link, the checkbox of the folder tree, the Theme group, the tree and the breadcrumb, as rules 85 to 93 and 114 to 117 describe, its breadcrumb holding the link to the home page and then one to the page itself, which reads `Step sentences`; the folder tree has no item for it, since it lists folders and features. Each group is an `h2` that reads `Given`, `When` or `Then`, in English whatever the language of the files. Each sentence is an `h3` that reads the sentence. A sentence whose first use is in a file whose language, as rule 42 writes it, is not `en` has that language as its heading's `lang`. Fixture: `tests/fixtures/step-sentences`.

Each item is a link to the use's block on its feature's page, by a relative address: the page's path as rule 36 makes it, percent-encoded as rule 47 encodes a path, then `#` and the block's anchor, such as `saque%20em%20conta.html#saque`. When the step has values, the link is followed by `, with ` and its values, separated by a comma and a space, each value in an element of its own. The block's heading and the values have the `lang` of their file when it is not `en`, as rule 143 says. Fixture: `tests/fixtures/step-sentences`.

## Search

Every page has a search box over the names, step text and tags of the site's features, rules and scenarios. The build writes the documents to search, and the pages' script fetches them the first time the search box is used, and builds the index from them in the browser with [MiniSearch](https://www.npmjs.com/package/minisearch). A page that is never searched never loads them.

### The documents

147. The documents are one file, `assets/search.json` at the site's root, beside the pages' script. It holds a JSON array with one entry for each feature, each rule and each scenario, scenario outlines included. Backgrounds, examples blocks and the scenarios an outline produces from its rows have no entry of their own. The entries follow the order the files are read in, which is that of rule 15, and within a file, the feature comes first, then its scenarios and rules in file order, each rule followed by its scenarios. Fixture: `tests/fixtures/search`.
148. Each entry is an object with these members, every one of them always there:

    | Member | Holds |
    | --- | --- |
    | `kind` | `feature`, `rule`, `scenario` or `scenario-outline`, the block's kind in English, which the results list puts into words from the interface catalogue. |
    | `name` | The block's name as written, or empty text for a block with no name. |
    | `feature` | The name of the feature whose page the entry is on, empty text for a feature with no name, or `null` for the feature's own entry. |
    | `rule` | The name of the rule the scenario is in, or empty text for a rule with no name. It is `null` for a rule, a feature, and a scenario outside any rule. |
    | `steps` | A list of the text of each step, as written, without its keyword, its data table or its doc string, so `<amount>` in an outline stays as it is. A feature's entry holds the steps of the feature's background, a rule's those of the rule's background, and either holds an empty list when there is none. |
    | `tags` | A list of the block's own tags, each with its `@`, in file order. An outline's entry adds the tags of its examples blocks, in file order, each tag once. Tags a block inherits from the blocks around it are not repeated. |
    | `page` | The address of the entry's page, relative to the site's root, with `/` between folders, as rule 36 makes it. It is not percent-encoded: the script encodes it when it makes the link. |
    | `anchor` | The block's anchor ([Anchors](#anchors)), or empty text for a feature, which is its page. No two entries have the same page and anchor. |

    Fixture: `tests/fixtures/search`.
149. The file is written without spaces or line breaks between the tokens of its JSON, with letters outside ASCII written as themselves in UTF-8, not escaped. It is the same on every build of the same input. Fixture: `tests/fixtures/search`.

### The size of the documents

150. There is no size at which the documents fail the build. When the file is larger than 5 MB, 5,000,000 bytes, the build still writes it, and `ghg build` then prints this warning to standard error, after the hint of rule 17 when there is one, and exits as it would without it: `The search documents are <size> MB, larger than the 5 MB above which search can be slow to start, mostly on phones.`, where the size is in millions of bytes with one decimal, rounded up, so that it never reads 5.0. A suite of scenarios with six steps each reaches 5 MB at about 8,000 to 9,000 entries: 11,000 such entries took 6.3 MB. Fixture: created by the test, since a suite that large is too big to commit.

### The search box

151. Every page but the versions page has a search landmark between its breadcrumb and its `main`, as rule 86 says: a form with the role `search`, the only one on the page, so it needs no name. It holds a search field, labelled "Search features, rules and scenarios", a status, and the list of results, which is empty as the page loads. All three are in the page's HTML; the script only fills the status and the results, as rule 40 allows. The versions page, above every version's site, has no search box, since each version has its own documents. Fixture: `tests/fixtures/pages`.
152. The script fetches `assets/search.json`, at an address resolved against its own, when the first letter is typed in the field, and builds the index from it; taking the focus alone fetches nothing. While a search waits for the documents, the status reads `Loading search.`. When a search finds that they cannot be fetched or read, the status reads `Search could not be loaded.`, the field stays usable, and the next search tries again. Fixture: `tests/fixtures/search`, checked by `script/test/services/searching.test.ts` and `script/test/adapters/dom_search_box.test.ts`.
153. A search runs once the person has paused typing for 300 milliseconds, or at once when they press Enter, over each entry's name, steps and tags. It finds the entries that hold every word of the search, a word matching the start of a longer word, or a word one letter in five away from it, rounded to the nearest, so a word of three to seven letters may be one letter away, and one of eight to twelve, two. A match in a name counts most, then one in a tag, then one in a step; doc strings and data tables are not searched. An empty search empties the results and the status at once. Fixture: `tests/fixtures/search`, checked by `script/test/services/searching.test.ts`.
154. The status is a live region, so that a screen reader reads it without moving the focus, and it changes only when a search runs, an empty search included. When a search gives the same words as the one before, the status is emptied for a moment, so that a screen reader reads them again. It reads `No results.`, `Results: <count>.`, or, when there are more than 50, `Results: <count>. The first 50 are listed.` Fixture: `tests/fixtures/search`, checked by `script/test/services/searching.test.ts` and `script/test/policies/search_results.test.ts`.
155. The results are a list of links, best match first, at most 50. Each link leads to its entry's page and anchor, by an address relative to the page, and reads the entry's name, then what it is and where, each name of a block, a feature or a rule that has none reading `no name`: `<name>, feature`, `<name>, rule in <feature>`, `<name>, scenario in <feature>`, `<name>, scenario in <rule>, <feature>`, and the same with `scenario outline` for an outline. Names are shown as written, isolated from the words around them, so that a name written right to left reads in its own direction. Nothing but the words marks the best match. Fixture: `tests/fixtures/search`, checked by `script/test/policies/search_results.test.ts` and `script/test/adapters/dom_search_box.test.ts`.
156. Enter in the field moves the focus to the first result, and does nothing when there is none. Enter never submits the form, and an Enter that ends the composition of a character, as the input methods of Chinese and Japanese use it, is left to the input method. Escape in the field empties it, the results and the status. Fixture: `tests/fixtures/search`, checked by `script/test/services/searching.test.ts` and `script/test/adapters/dom_search_box.test.ts`, and in the browser by the accessibility check, `tests/browser/accessibility.mjs`, on one page of every site.

Where the release binaries are, so that `cargo binstall` downloads one instead of compiling, is declared with the release workflow ([#16](https://github.com/marlon-sousa/gherkin-glass/issues/16)).

157. `cargo install gherkin-glass` installs two commands: `ghg`, the command the rest of this document describes, and `cargo-ghg`, the cargo plugin. The published crate holds everything both are built from. Fixture: the crate's own list of files, as `cargo package --list` gives it, checked against the files of the repository.
158. `cargo ghg`, followed by anything `ghg` takes, behaves exactly as `ghg` followed by the same: it prints the same to standard output and to standard error, and exits with the same status. So `cargo ghg build --input specs` is `ghg build --input specs`, its paths relative to the current folder, `cargo ghg --version` prints `ghg` and its version, such as `ghg 0.1.0`, `cargo ghg` alone is the mistake of no command, and `cargo help ghg` prints the help of rule 18. Every sentence names the command `ghg`, as it does when `ghg` is run. Fixtures: `tests/fixtures/configuration/default` and `tests/fixtures/configuration/configured`.

Run by itself, without `ghg` first, it behaves as `ghg` too, so `cargo-ghg build` is `ghg build`. Fixture: `tests/fixtures/configuration/default`.

## Releases

gherkin-glass is downloaded and run, with nothing else to install. A release is made by the release workflow, `.github/workflows/release.yml`, when a maintainer pushes a version's tag, and holds an archive for each platform, a checksums file, notes, and, for a version without a pre-release part or a release candidate, the crate on crates.io (rule 167). The names of the archives and what they hold are what the GitHub Action ([#17](https://github.com/marlon-sousa/gherkin-glass/issues/17)) and `cargo binstall` rely on, so they are part of what is promised, like the command line.

The workflow's own checks test these rules: on every tag before anything is published, and on every pull request that changes how releases are made, which builds, packs and checks every archive without publishing anything. Their scripts are in `.github/release/`.

### What makes a release

160. Pushing a tag `v<version>` releases that version, and nothing else does. The tag is refused, and nothing is published, unless the version is the one `Cargo.toml` gives the crate, the tagged commit is on `main`, and `CHANGELOG.md` has notes for the version, under the heading `## [<version>]`. Every reason a tag is refused is reported, not only the first. Fixture: `tests/fixtures/release/changelogs`, checked by `.github/release/test-gate.sh`.

### The archives

161. A release has one archive for each of five targets, all 64-bit, named `ghg-<tag>-<target>.tar.gz`, or `ghg-<tag>-<target>.zip` for Windows, such as `ghg-v0.1.0-x86_64-unknown-linux-musl.tar.gz`, where the tag is the one pushed and the target is the Rust target the binaries were built for:

    | Target | Platform | Archive |
    | --- | --- | --- |
    | `x86_64-unknown-linux-musl` | Linux on x86-64 | `.tar.gz` |
    | `aarch64-unknown-linux-musl` | Linux on ARM64 | `.tar.gz` |
    | `x86_64-apple-darwin` | macOS on Intel | `.tar.gz` |
    | `aarch64-apple-darwin` | macOS on Apple silicon | `.tar.gz` |
    | `x86_64-pc-windows-msvc` | Windows on x86-64 | `.zip` |

    Checked by `.github/release/check-archive.sh` and `.github/release/check-binstall.sh` on every build, and the first by `.github/release/test-check-archive.sh` with archives it makes.
162. Each archive holds, at its root and not inside a folder, every binary the crate declares, `ghg` and `cargo-ghg`, ending in `.exe` on Windows, and the licence files `LICENSE-MIT` and `LICENSE-APACHE`, and nothing else. Checked by `.github/release/check-archive.sh` on every build, and by `.github/release/test-check-archive.sh` with archives it makes.
163. A release has one checksums file, `SHA256SUMS`, with one line for each archive, in the form `sha256sum` writes and checks: the archive's SHA-256 in lower-case hexadecimal, two spaces, and the archive's name. Checked by the release workflow, which writes it and checks every archive against it with `sha256sum --check` before attaching them.
164. Each binary needs nothing installed beyond what every system of its kind has. On Linux it is statically linked, with musl, so it runs on any distribution. On Windows it links the C runtime into itself, so it needs neither the Visual C++ runtime nor the Universal C Runtime installed. On macOS, which allows no fully static binary, it loads only the libraries of macOS itself, under `/usr/lib` and `/System/Library`. Checked by `.github/release/check-binary.sh`, which also runs `ghg --version`, and checks it prints `ghg` and the version, wherever the machine running the check can run the binary: every target but macOS on Intel, which is built on Apple silicon.

### The notes and the crate

165. The notes of a release are the section of `CHANGELOG.md` for its version. That section is written before the tag, from what [git-cliff](https://git-cliff.org/) prints with the template in `cliff.toml`: the heading `## [<version>]`, then the changelog entries that the commits since the previous tag carry as trailers, under `### Added`, `### Changed`, `### Fixed` and `### Removed`, in that order and each only when it has entries, one list item per entry, oldest commit first. A commit whose subject does not follow [Conventional Commits](https://www.conventionalcommits.org/), such as a merge commit, adds nothing, nor does a trailer of any other kind, such as `Refs #N` or `Changelog: none`. Fixture: `tests/fixtures/release`, checked by `.github/release/test-notes.sh`.
166. A version with a pre-release part, such as `0.2.0-rc.1`, is released on GitHub as a pre-release. Checked by the tests of the `create-release` action of [itinera-dev/actions](https://github.com/itinera-dev/actions), which makes the release.
167. A version without a pre-release part, such as `0.2.0`, and a release candidate, whose pre-release part starts with the identifier `rc`, such as `0.2.0-rc.1`, are published to crates.io as the crate at the same version, before the GitHub release is made, and only after every archive has been built and checked and every check of `.github/workflows/rust.yml` passes on the tagged commit: the formatting, the lints, the tests, the script's checks and the browser check. A version already on crates.io is not published again, so a release whose GitHub release failed can be run again. The one exception is the first version published to crates.io, which a maintainer may have to publish by hand before its tag is pushed, as [CONTRIBUTING.md](../CONTRIBUTING.md), "Releases", says. Any other pre-release, such as an alpha, `0.1.0-alpha.1`, or a beta, `0.1.0-beta.1`, is not published to crates.io ([#101](https://github.com/marlon-sousa/gherkin-glass/issues/101)); it is released on GitHub all the same, once the archives and the checks have passed, with its archives, its checksums and its version of the project's site, and is installed from its archives or through the action, by naming it, as rule 170 says, never with `cargo install gherkin-glass` or `cargo binstall gherkin-glass`, which read crates.io. Which versions go to crates.io is checked by `.github/release/test-crates-io.sh`, with the tags it holds, which the release workflow runs; the publishing itself is checked by publishing: a pull request that changes how releases are made packs the crate without publishing it.
168. `cargo binstall gherkin-glass` downloads the release archive for the machine's target, as `[package.metadata.binstall]` in `Cargo.toml` names it, and installs both binaries from it. Checked by `.github/release/check-binstall.sh`.

## The GitHub Action

A step of a GitHub Actions workflow that says `uses: marlon-sousa/gherkin-glass@v1` installs `ghg` on the runner and, when asked, builds a site with it. The action is in this repository, in `action.yml`. It is a composite action of shell steps only, run by bash, with no Node and no other action, so it runs alike on Linux, macOS and Windows runners. Besides bash and the usual command line tools, it uses curl, tar, sha256sum or shasum, and on Windows unzip or PowerShell, which GitHub's own runners all have.

When the action stops, it says why in one sentence, which the workflow's log shows as an error, and the step fails. The fixtures of these rules are the releases the test serves, made by `tests/action.rs` itself, and `tests/fixtures/action`, the folder it builds in.

### Installing

169. The action always installs `ghg`, and puts its folder on the `PATH` of the job's later steps, so that a workflow can also run `ghg` itself. Fixture: made by the test.
170. The input `version` names the release to install, such as `1.2.0`, or `v1.2.0` with the tag's `v`, a pre-release such as `1.3.0-rc.1` included, written as [Semantic Versioning](https://semver.org/) writes a version without build metadata. Anything that is not a version stops the action with `version must be a version of ghg, such as 1.2.0.` When `version` is empty, its default, the action installs the newest release compatible with its own version, the one in the `Cargo.toml` of the action's commit, as Cargo counts compatibility: the same major version, so that `@v1` never installs a 2.x `ghg`, and while the major version is 0, the same minor version too. Only a published release whose tag is a plain version, such as `v1.2.0`, is counted, never a draft, so a pre-release is installed only when `version` names it. When none is compatible, the action stops with `ghg has no release compatible with this action's version.` Fixture: made by the test.
171. The action installs the release's archive for the runner's system and processor, as [Releases](#releases), rules 161 to 163, describes it: Linux on x86-64 or ARM64, macOS on Intel or Apple silicon, and Windows on x86-64. On any other, it stops with `ghg has no build for <system> on <processor>.`, in the runner's own words for them, such as `Windows on ARM64`. An archive the release does not have stops it with `<archive> cannot be downloaded from the release v<version> of ghg.` Fixture: made by the test.
172. The archive is checked against the release's `SHA256SUMS` file before anything is installed. An archive whose checksum differs stops the action with `<archive> does not match its checksum in SHA256SUMS.`, and one the file does not list with `<archive> is not in the release's SHA256SUMS.` Fixture: made by the test.
173. An installed `ghg` is kept in the runner's tool cache, by version and platform, and a later run that finds it there installs it without downloading it again. GitHub's own runners start every job with an empty tool cache, so there it saves the download only when the action runs again in the same job; a self-hosted runner keeps it from job to job. Fixture: made by the test.

### Building

174. The input `build` is `false` by default. When it is `true`, the action runs `ghg build` after installing it, in the workflow's workspace folder, and the step fails with the build when the build fails, its report in the log. Any value but `true`, `false` or nothing stops the action with `build must be true or false.`, before anything is downloaded. Fixtures: made by the test, and `tests/fixtures/action`.
175. Every option of `ghg build` that sets how a site is built, which is every option but `--help` and `--version`, has an input of the same name without its dashes: `config`, `input`, `output`, `title`, `version-name` and `front-page`. When `build` is `true`, each such input that is not empty is passed to `ghg build` as `--<name>=<value>`; an empty one, the default, is left out, so the configuration file and the defaults still apply. Fixture: `tests/fixtures/action`.
176. The action's inputs and the options of `ghg build` cannot drift apart: the crate's tests, and so `cargo test` and the checks of every pull request, fail when an option has no input of the same name, when an input other than `version` and `build` has no option, or when an input is not passed to the build. Fixture: `action.yml` itself.

### The action's version

177. When a release's tag is a version of 1.0 or later without a pre-release part, such as `v1.2.0`, and no other tag of the repository is a newer such version of the same major version, the release workflow moves the tag of that major version, such as `v1`, to the released commit, once the GitHub release is made. So `uses: marlon-sousa/gherkin-glass@v1` runs the action of the newest 1.x release, which installs that release by default, as rule 170 says. A pre-release, a release before 1.0, and a release older than another of its major version move no tag; before 1.0, the action is used by a release's own tag, such as `@v0.1.0`. Checked by `.github/release/test-action-tag.sh`, with lists of tags it holds, which the release workflow runs.

## The project's own site

The repository's GitHub Pages site, at <https://marlon-sousa.github.io/gherkin-glass/>, shows what gherkin-glass produces, so that anyone can see its pages, and try their reader options and their accessibility, before downloading it. These rules are the repository's promises rather than the command's: what the site holds, and how each release adds to it. Their test is `tests/project_site.rs`, and the files it checks are in `project-site/`.

Each release's site is built once the release is published: the release workflow ([#16](https://github.com/marlon-sousa/gherkin-glass/issues/16)) calls `.github/workflows/site.yml` with the release's tag, which builds the site with the project's own action ([#17](https://github.com/marlon-sousa/gherkin-glass/issues/17)) and `build: true`, so that every release also exercises the action and the binary it publishes. The build is titled "gherkin-glass examples", and is a versioned build ([#12](https://github.com/marlon-sousa/gherkin-glass/issues/12)) named after the tag, such as `v0.1.0`, whose links are all relative, so the site needs no setting for being served below `/gherkin-glass/`.

### What it holds

178. The site's input is the example suite of `project-site/features/`, at its root, and each folder directly under `tests/fixtures/` in a folder of its own, `fixtures/<name>/`, so that the home page links the example suite's folders and features and the `fixtures` folder, whose page links each fixture. The fixtures left out are named in `project-site/fixtures-left-out`, each after a comment saying why: those whose build is meant to fail, those whose cases are runs of the command line rather than pages, and those that are not an input, such as a site already built. Every other fixture is shown, so a new fixture is shown unless it is named there. `project-site/assemble-input.sh` writes the input, and every file of it is read with no problem. Fixtures: `project-site/features` and `tests/fixtures`.
179. The example suite shows every construct the pages show: folders within folders; a feature in a language other than English; tags on features, rules, scenarios and examples blocks; descriptions of features, rules and scenarios; a feature's and a rule's background; scenario outlines with several examples blocks, named and unnamed; data tables, with an escaped `|` in a cell; and doc strings with and without a media type, in both delimiters, with an escaped delimiter. Its site, the suite alone built with `project-site/ghg.toml`, which gives it the title the release gives the project's site, is committed in `project-site/expected`, and every page ghg builds from it is the same as there, byte for byte, so that a change to any page shows in review. Fixtures: `project-site/features` and `project-site/expected`.

### How a release adds to it

180. The site is published from the `gh-pages` branch of the repository. The first release creates it, holding only a `.nojekyll` file, so that GitHub Pages serves every file as it is, those whose names start with `_` included, rather than through Jekyll. The maintainer sets Pages once, under the repository's Settings, Pages: source "Deploy from a branch", branch `gh-pages`, folder root. Fixture: created by the test, in a repository of its own.
181. Each release adds one commit to `gh-pages`, holding only its own version's folder, the versions page, `index.html`, the versions page's own `assets/` folder beside it, and the output folder's marker, `ghg-versions.json`, so every earlier version stays exactly as it was published. Since ghg builds only into a folder that holds nothing but what it wrote, as rule 38 describes, the release builds into a copy of what ghg wrote on `gh-pages`, without `.nojekyll` and git's own files, and puts the copy back before committing. A build that changed anything else publishes nothing and fails, naming what changed. Publishing a version again replaces its folder, and adds no commit when the build is the same. A version whose name is not a single folder name, such as one that is empty, starts with a dot or holds a `/`, or that is named `index.html`, `assets` or `ghg-versions.json`, is refused. Fixture: created by the test, in a repository of its own.

## A page opened from disk

A site is meant to be served, and opening its pages straight from disk is not supported ([design note 0026](design/0026-sites-are-served.md)). A page opened from disk still shows its content, but a browser does not run the page's script from there, so its folder tree, its search and its reader options do not work. So that a reader who opens a page from disk knows why, and what to do instead, the page says so in a dialog, which the reader closes to read the page.

182. Every page, the versions page included, has a closed `dialog` as the first element of its body, before the link of rule 86, named by its first paragraph, "Opened from disk", and described by its second: "This site is meant to be served, so its folder tree and search do not work when a page is opened from disk. Run ghg serve in the folder of your ghg.toml, or serve the site's folder with any web server, then open the address it gives." Its one button reads "I agree". A script written in the page itself, right after the dialog, rather than the page's script file, which is what a browser does not run from disk, opens it as a modal dialog as the page loads when the page's address starts with `file:`, and moves the focus to the dialog itself, so that a screen reader reads its name and what it says; Tab then reaches its button. The button closes it, as Escape does, and the page is then read and used as it is from disk. It opens on every page opened from disk, and never on a page that is served, where it stays closed and so is neither shown nor reached by the keyboard. Fixtures: `tests/fixtures/pages` and `tests/fixtures/versions`, and the browser check, which opens pages of `tests/fixtures/pages` from disk, finds the dialog open with the focus on it, holds it to the rules of [Accessibility](#accessibility) in the light and the dark colour scheme, and closes it with the button, and which finds it closed on every page it checks served.

## The front page

A site's front page, the page at the root of its output folder, can open with an introduction written in Markdown, such as a project's README, around what ghg writes there itself ([#102](https://github.com/marlon-sousa/gherkin-glass/issues/102)).

### The template

183. `--front-page <file>`, and the configuration's `front_page` key, name the front page's template, a file of Markdown; the option wins over the key, and the key's path is relative to the configuration file's folder, as rule 24 says. The front page is the page at the output folder's root: the versions page in a versioned build, as [Versions](#versions), rule 126, describes, and the home page otherwise. Only it takes the template: every other page, each version's own home page included, is written as without one, and every file goes where rules 126, 180 and 181 put it. The action's input `front-page` passes it, as rule 175 describes. Fixture: `tests/fixtures/front-page`, built without versions with `ghg.toml` and as a version with `versioned.toml`.
184. Without a template, the front page is written from ghg's own: a level-one heading, then the marker. The heading, and so the page's `h1` and its title, is the site's title on the home page, as rule 81 describes, and "Versions" on the versions page, as rule 127 describes. ghg's own template is Markdown, read and rendered as any template is, and the site's title is written into it with its Markdown punctuation escaped, so that it reads as plain text: no title is read as HTML or as emphasis, and none stops a build. So every page of a build without a template shows what it showed before templates were, though the `h1` escapes its characters as the Markdown renderer does, such as `&amp;` for `&`. Fixtures: `tests/fixtures/pages` and `tests/fixtures/versions`.
185. ghg's part of the front page is what it writes under the `h1` without a template: on a home page, the totals, the links to the tags' index and to the step sentences, and the folders and features, as rules 82 and 83 describe; on a versions page, the lists of versions, as rule 127 describes. It goes where the template has the marker, the HTML comment `<!-- ghg:contents -->` alone on a line of its own, which Markdown viewers such as GitHub's do not show. Fixture: `tests/fixtures/front-page`.
186. The template is read as the site is written, after the feature files are read and parsed, so that a problem with them is reported first. A template that cannot be read, a missing one among them, stops the build with `<file>: cannot be read: <reason>`, the file as the settings give it and the reason in the operating system's words, before anything is cleared or written. Fixture: `tests/fixtures/front-page/broken`, whose `missing.toml` names a file that does not exist.

### What a template holds

187. The template holds exactly one level-one heading, written with one `#` or underlined with `=`. It is the page's only `h1`, and its text, without its markup, is the page's title. A template with none, or whose only one has no text, stops the build with `<file>: has no level-one heading, written with one #, for the front page's title.`, and the second such heading with `<file>:<line>: holds a second level-one heading, but a front page has one only.` Every other heading keeps the level it is written at. Fixture: `tests/fixtures/front-page`, and the tests of `src/policies/rendering/front_page/markdown_template.rs` for every way a template breaks this rule and those below.
188. The template holds exactly one marker, outside any list, quote or table. A template with none stops the build with `<file>: has no marker <!-- ghg:contents --> on a line of its own, where ghg puts its part of the front page.`, the second marker with `<file>:<line>: holds a second marker <!-- ghg:contents -->, but ghg puts its part of the front page in one place only.`, and a marker inside a list, a quote or a table, or on a line with other text, with `<file>:<line>: the marker <!-- ghg:contents --> must be on a line of its own, outside any list, quote or table.` Fixture: `tests/fixtures/front-page`.
189. ghg's own headings, such as "Folders" or "Releases", are one level below the last heading before the marker, `h2` when the marker follows the `h1` or no heading at all, and keep their `id`s. Since a page's headings go no lower than `h6`, and the pages' script finds a block's heading from `h2` to `h5`, a marker after a level 5 or level 6 heading stops the build with `<file>:<line>: the marker <!-- ghg:contents --> follows a level 5 or level 6 heading, so ghg's own headings would have no level below it.` Fixture: `tests/fixtures/front-page`, whose marker follows an `h2`, so ghg's headings are `h3`.
190. The Markdown is CommonMark, with GitHub's tables, written as HTML in the page's `main`, before and after ghg's part. Links and images are written exactly as the template has them, neither rewritten nor checked, so a relative link is relative to the front page. Every HTML comment other than the marker is left out of the page. Raw HTML, any other HTML in the template, stops the build with `<file>:<line>: raw HTML cannot be written in a front page; only the marker <!-- ghg:contents --> and other comments can.` Every such problem stops the build as rule 186 says, before anything is cleared or written, and the first in the template is the one reported. Fixtures: `tests/fixtures/front-page`, and its `broken/raw-html.toml`.
191. Under `ghg serve --watch`, the template is watched as the configuration file is, whether it exists yet or not, as rule 65 describes: a change to it reads the configuration again and builds the whole site again, reading the template again. A change to the configuration that names another template watches that one instead. Fixture: `tests/fixtures/serve/built`, copied with a template beside it, and the tests of `src/services/server.rs`, `src/policies/serving/burst_merging.rs` and the controller's watch.

### The project's front page

192. The repository's README holds the marker, at the end of its "Status" section, after the part only the site shows that introduces the example suite (rule 193), so the project's site lists its versions there. Each release builds its site with the front page that `project-site/front-page.sh` writes from the README of its own tag, pre-releases included, so that the site's root shows the README of the latest release built. The README's links to files of the repository, such as its licences, are full addresses on GitHub, which work there and on the site. Fixture: `README.md` itself, made into the front page by `project-site/front-page.sh` and built as the template of a versions page by `tests/project_site.rs`, which checks that `.github/workflows/site.yml` makes the front page with the script and passes it.
193. The README holds parts for one of the two places it is read, each marked by HTML comments, which GitHub does not show. A part only the site shows opens with the line `<!-- site-only` and closes with the line `-->`, so GitHub shows nothing of it. A part only GitHub shows opens with the line `<!-- github-only -->` and closes with the line `<!-- end github-only -->`. Each mark is a line of its own, as written, with nothing else on it. `project-site/front-page.sh` writes the front page from the README: it keeps a site-only part without its two lines, leaves out a GitHub-only part with its two lines, and keeps every other line as it is. A part opened inside another, a part never closed, and a closing line outside any part each stop it, with a message naming the line, and nothing is written. The README's site-only parts are a sentence under its opening paragraph that links the repository, where its source, its issues and how to contribute are, and, before the marker, a heading "The example suite" with a sentence saying that each version below is the example suite built with that version of gherkin-glass, so that the version lists are below it. Its GitHub-only part is its "Contributing" section. Fixtures: `README.md` itself, and the cases of `tests/project_site.rs` for each way a mark can be wrong.
